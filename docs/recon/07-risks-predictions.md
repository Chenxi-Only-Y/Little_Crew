# 小剧组 Little Crew — 还会出现什么问题（风险预判）

> 依据：`01-usage.md`（实测基线）+ 本轮实测新增证据。
> 目的：在开工前把「最可能先爆的问题」按**爆发时点**排出来，而不是收集风险清单。
> 注意：本文只写**这次实测确认过**或**有明确机制依据**的问题；纯猜测已剔除。

## 0. 先认一个错

本轮勘察中我曾断言「设置页给场记选的模型静默失效」，**这个结论是错的**——
投毒测试证明配置链路是通的（`01-usage.md` 已更正）。

这件事本身就是风险信号：**系统里同名不同义的东西太多**（`continuity` / `continuity_checker` /

## 1. 【最高】成本失控：没有任何按量成本控制，且重试是乘法

### 实测证据
| 项 | 现状 |
| --- | --- |
| ~~`quota.py`~~ | **已删除**（用户 2026-10-02：开源非商业项目，不替使用者拦成本）。当时的问题：只限"每日创建次数"与每分钟请求数，**完全没有按张/按秒/按金额的预算** |
| LLM 重试 | `_utils.call_deepseek(retries=2)` → 每次调用最多 **3 次** |
| 图像重试 | `image_generator.MAX_RETRIES = 2` → 每张图最多 **3 次** |
| 质量闭环 | `route_quality()` 失败回退重试 ≤ **3 轮** |
| 单次创建的实际出图量 | 最多 `max_images`(默认 8) 个镜头 × 3 次重试 × 3 轮质量重试 = **理论 72 张** |
| LoRA/视频 | 尚未接入，且 LoRA 按步计费、视频按秒计费 |

### 为什么现在不爆、v2 必爆
v1 是「云端便宜小图 + mock 兜底」，量级可控。v2 引入：
- LoRA 训练（百炼按 `max_steps` 计费，推荐 800 步）
- 视频（$0.01–0.10/秒，Sora 2 Pro 一条 5 秒 ≈ $0.30–0.50）
- 白模预演、配音
- **高端模型**（GPT Image $0.04/张、Flux 2 Pro $0.055/张）

一次"创建"可能触发 **20+ 次昂贵调用**，而系统对此**毫不知情、无法拦截**。

### 建议
1. **成本作为一等字段**：每个 provider 调用记录 `{provider, model, unit, units, est_cost}`，落库。
2. **三层预算**：单次创建上限 / 单用户每日金额上限 / 全局熔断。
3. **重试预算**：重试要计入成本并设**总次数上限**（而非每节点各自重试）。
4. **UI 实时显示**：节点上显示"本节点已花费 ¥X.XX"，复用你现有的 `_retry_progress` 呈现方式。

> 这条排在第一位，因为它是**唯一会造成真实金钱损失且事后无法追回**的风险。

## 2. 【高】本地 8GB 的并发冲突：现有设计会直接打架

### 实测证据
| 侧 | 机制 |
| --- | --- |
| 项目侧 | `image_generator.CONCURRENCY = 4` + `ThreadPoolExecutor` 并发出图 |
| local-gen 侧 | `model_manager.py`：**一把全局 `gpu_lock` 把所有推理串行化**；"同一时刻只保留一个 pipeline"；注释明说"并发跑必然 OOM" |

**结论**：一旦接本地 provider，项目的 4 线程并发**在服务端退化成排队**，
而且**等待时间无法预估**（H3 视频 50 步 ≈ 45 分钟）。

### 连带问题
- 项目侧 `time.sleep(1.5)` 的限流间隔在本地场景**毫无意义**（真正瓶颈是显存锁）。
- 用户看到"4 张并行生成"的进度，实际是串行——**UI 承诺与事实不符**。
- OOM 后显存不自动归还（技能踩坑清单记录），连续失败需要 `unload`。

### 建议
- provider 接口暴露**并发能力**（`max_concurrency`），由 provider 自己声明；本地=1，云端=N。
- UI 显示**预计耗时**而非"进度条按张数均分"。
- 本地失败退避策略要含"先 unload 再重试"。

## 3. 【高】隐藏全局状态：多 worker 部署时静默错乱

### 实测证据：**8 个模块级单例**
```
session_store._store   auth._store        profile._store
critic_history._store  image._image_instance
llm._llm_instance      video._service     quality._service
ip_adapter_service._service
```
外加 `runtime_settings` 用 **`threading.local()`** 存 `user` / `session_id`。

### 三重隐患
1. **单例在 import 时固化配置**：`LLMService.__init__` 里 `self.mock = settings.mock_llm`——
   一旦运行中改配置（你的"设置页保存立即生效"承诺），**已创建的单例不会更新**。
   （我在 `01-usage.md §6` 已把这条列为已知问题。）
2. **`threading.local` 在异步/多线程池下会串**：`image_generator` 用线程池并发出图，
   依赖 `_role_local` 区分角色——线程复用时会读到别的任务的 role。
   服务端 `set_context` 也是线程级，跨线程调用的子任务拿不到正确 session。
3. **多 worker 部署直接失效**：`uvicorn --workers N` 下每个进程一套单例 + 一套进程内状态，
   而 `task_runner._JOBS/_THINKING/_CANCEL` 也是进程内的 →
   `cancel` / `resume` / 状态查询**可能落到没有那个任务的进程**。

### 建议
- 单例改为**显式注入**（依赖注入容器），配置读取走函数而非 `__init__` 快照。
- 用户/会话上下文改为**显式参数传递**（`RunContext`），不用 thread-local。
- 长任务状态**落库**（Job 表，已在 `02-refactor-plan.md §2.3` 提出），
  这样 cancel/status 才能跨进程正确。

## 4. 【高】职业 ≠ 节点：注册表的基座假设还没对齐

### 问题
新表是 **16 职业**，现有工作流是 **14 个业务节点**（+9 确认点），两者**不是一一对应**：

| 现象 | 例子 |
| --- | --- |
| 一个职业可能对应多个节点/能力 | `technical_director`（模型选型 + LoRA 调优 + 视频参数）跨越多个环节 |
| 一个节点可能被多职业共享 | `consistency_auditor`（一致性审查）没有独立职业，但被"场记"和"质降总监"的职责覆盖 |
| 节点不对应任何职业 | `art_brief_parser`（美术设定包解析）、`aggregator` |
| 职业不对应任何节点 | `editor`（视频合成服务）、`distributor`（不进主图） |

**如果注册表默认"1 职业 = 1 节点"，画布一开始就会错。**

### 建议
注册表显式区分三层，而不是混成一张表：
```
Role（职业：面向用户，16 个）
  └─ Panel（面板/视图：可多个，决定画布上"看什么"）
       └─ Stage/Node（执行单元：决定"跑什么"，可被多 Role 复用）
```
**这个决定必须在 V0 之前定**，否则注册表结构会返工。

## 5. 【中高】数据兼容：历史会话会在改名后读不出来

### 实测证据
- `sessions` 表现有 **13 行**，其中 `payload` 存的是**旧 key 名**（`story_outline` / `screenwriter` / `images`…）。
- `data/outputs` 有 **166 个文件 / 116MB**，目录名含**旧职业名**（`技术制作部/photographer`）。
- v2 要改名：`showrunner` / `script_editor` / `supervising_editor` / `continuity`…

### 风险
- 改名后旧 payload 可能**读不出来或读错**（尤其 `worfklow` 用 `output_key` 判定"已完成"）。
- 产物路径按"部门/职业"归类，部门从 5 变 7 → 旧文件找不到。
- 用户历史（`我的创作`）会出现空白或错位。

### 建议
- 注册表带 **`legacy_keys: [...]`** 别名映射，读旧数据时兼容。
- 路径解析做"新路径写 + 旧路径读"双兼容，迁移脚本先**干跑报告**再执行。
- 迁移前备份（本次已备份 `C:\Users\OnlyY\AppData\Local\Temp\ds6-recon\little_crew_20261002_144228.db`）。

## 6. 【中高】护栏太薄：6 个测试保护 13 个职业，要重构成 16 个

### 实测证据
- 测试：`6 passed in 1.65s`——**只有 1 个文件**（角色一致性 e2e）。
- 覆盖：确认点续跑、seed 续跑、产物归档、provider 切换、成本、并发——**全都没测**。

### 风险
v2 的链路更长（含 LoRA 训练、白模、配音、时间线），**重试与回环更多**，
一旦重构引入行为偏差，**没有任何自动化手段能发现**——只能等用户投诉。

### 建议（P0 先行，与前端路线解耦）
1. 确认点续跑（含**重启**场景——`01-usage.md §6.1` 已证明会静默重放）
2. `seed` / `start_stage` 续跑
3. 产物归档路径正确性
4. **成本累计**（新增，配合 §1）
5. **provider 降级链**（本地失败→云端→占位图）

## 7. 【中】迁移期新旧并存的具体冲突

「两刀切」策略（后端先行、旧前端继续跑）本身是对的，但有几个具体坑：

| 冲突 | 说明 |
| --- | --- |
| **端点语义变更** | 新的 `/api/sessions/{id}/panel/{role}` 与旧的 `/api/crew/status/{id}` 返回**不同粒度的 payload**，旧前端要能继续用 |
| **认证切换** | 旧前端用 `streamlit-cookies-manager`（JS 可读 cookie），新前端要 HttpOnly/服务端会话 → **过渡期要双读** |
| **状态字段并存** | 旧 `status='review'` 与新状态机（`waiting_review` + checkpoint 校验）要能互认，否则旧前端显示错 |
| ~~**设计 token 双份**~~ | **已消解**：旧前端与 `DESIGN.md` 都已删除，现在只有一份 `web/src/styles/tokens.css` |

### 建议
给迁移期定**明确的"双写/双读"清单**和**下线判据**（什么条件下可以删旧前端），
避免"两套并存"变成永久状态。

## 8. 【中】前端画布的两个技术坑（现在不解决，F2 会返工）

1. **回环 vs DAG**：v2 存在"配音 ↔ 剪辑"回环依赖（`05-roles-v2.md §4.1`）。
   React Flow 是**有向图编辑器**，不校验环；LangGraph 支持环但需要显式条件边。
   **画布上的环怎么表示、后端怎么执行——必须先定**，否则画布画得出、跑不了。
2. **校验要写两遍**：前端预校验 + 后端再校验（`04-frontend-rewrite.md §5.2` 已定）。
   如果两边的规则不来自**同一份注册表 schema**，必然漂移——这正是注册表要下发
   `inputs/outputs` 的原因。

## 9. 【中】v2 有三条新管线完全没有原型

`05-roles-v2.md` 的缺口统计：**🔶 需扩展 10 个 / 🆕 全新 3 个**。

| 新管线 | 现状 | 风险 |
| --- | --- | --- |
| 白模预演（2D） | 零代码 | 相对简单（PIL 绘制），但"走位/机位"的数据结构要先设计 |
| 配音（TTS + BGM） | `video.py` 里是 `pass # TODO` | 音色/情感/混音/时长对齐，是独立领域 |
| 时间线剪辑 | 现只有"FFmpeg 幻灯片拼接"，时长固定 4s | **真实剪辑**（转场/字幕/音画对齐）与现实现差距最大 |

**建议**：这三条各做一个**最小可跑原型**再进画布，否则画布上会出现一堆"点了没反应"的节点。

## 10. 【结构性】v2 范围是 v1 的 3–5 倍，但团队规模没变

v1：13 职业 / 23 节点 / 1 个成熟链路。
v2：16 职业 / 30+ 节点 / 7 部门 / 新增 LoRA 训练 + 白模 + 配音 + 时间线 + 云本地双栈 + 前端重写。

**这是"重写一个产品"，不是"重构一个项目"。** 而本次勘察还发现 v1 有 **6 个未修缺陷**。

### 建议：把 v2 切成"可独立上线的小版本"
```
M0  修 v1 缺陷 + 补护栏            → 可用性提升，零新风险
M1  注册表（16 职业）+ 改名迁移     → v2 骨架可见，旧前端不退化
M2  provider 抽象 + 成本控制        → 支持用户自选云端模型（你最新诉求）
M3  工作流对象化 + 长任务基建        → 支撑后续重管线
M4  三条新管线各自原型（白模/配音/剪辑）
M5  导演台画布前端
```
**每个 M 都能独立交付、独立验收、独立回退**，而不是憋一个大的。

## 11. 关于我自己：同类错误可能再现

本轮勘察我犯过一次"未验证就下结论"（第 0 节）。在这个系统里这类错误的成因是结构性的：
**同一个概念有 3–5 个名字、跨 5 个文件**（`01-usage.md §8`）。

**降低办法**：V0 注册表落地后，让它成为**唯一可查询的事实来源**；
后续我（或任何人）做判断前先查注册表，而不是读代码猜。
