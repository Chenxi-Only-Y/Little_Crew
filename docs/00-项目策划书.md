# 《小剧组 · Little Crew》项目策划书

**版本** `0.4.0-alpha.4` · **编制日期** 2026-10-11 · **许可证** Apache-2.0

---

## 摘要

**小剧组 · Little Crew** 是一个基于多智能体协作的 AIGC 漫剧（动画短剧）生成平台。
它以 **ComfyUI 的节点化架构与 API 为执行底座**，在其上自研**统一中间表示（Unified IR）**
与**多智能体协作协议**，目标是让"一集漫剧"从创意到成片实现**可编排、可校验、可复现、
可结算**的工业化生产。

本项目的技术路线建立在一条判断上：**AIGC 漫剧的瓶颈不在生成质量，而在"创意决策"与
"扩散执行"之间缺少共享表示**。创意决策是**语义级**的（角色一致性、剧情节奏、镜头语言），
扩散执行是**张量级**的（节点图、端口类型、采样步数），两者之间没有桥梁。本项目
用统一 IR 架起这座桥，并让多智能体在这座桥上协作。

## 一、项目背景与问题定义

### 1.1 行业现状

AIGC 内容生产已经从"单张图片生成"走向"成片生产"。漫剧（动画短剧）是其中
商业价值最明确的形态之一：单集时长 1–3 分钟、集数多、角色固定、场景复用，
天然适合流水线化。

但当前的生产工具仍停留在**工具级**：ComfyUI、WebUI 等提供的是"生成一张图/一段视频"
的能力，而**"生产一集剧"**需要的编排、一致性保障、验收、成本控制，
全部依赖人工。

### 1.2 四个结构性困难

| # | 困难 | 本质 |
|---|---|---|
| **P1** | **长程一致性崩塌** | 一集 60–120 镜，角色脸型、服装、场景跨镜漂移；扩散模型没有跨镜记忆 |
| **P2** | **编排粒度错配** | 创意决策是**语义级**的，扩散执行是**张量级**的，两者之间**没有共享表示** |
| **P3** | **验收自证** | 出图的模型自己说"这张没问题"，错误逐帧累积无人拦截 |
| **P4** | **成本与重跑失控** | 单集数百次 GPU 生成，改一个参数导致全量重跑；中断即从头 |

其中 **P2 是靶心** —— P1、P3、P4 的解决都依赖"存在一个能被断言的中间表示"。

### 1.3 为什么现有项目没解决

对 GitHub 生态的系统调研（见 `docs/03`）显示，现有项目落在三个象限，
**没有一个同时满足三个条件**：

| 象限 | 代表项目 | 缺什么 |
|---|---|---|
| 可视化编排 + Agent，**不接执行引擎** | TapCanvas、wind-comic、novella | 产出物无法直接渲染，编排与执行脱节 |
| 执行引擎，**无编排无 Agent** | NiliX、kt-ai-Studio、auto-drama | 停留在节点级封装，没有语义层 |
| 可视化编排 + 执行，**无 Agent** | Novel-Director | 人能编排，但决策仍需人做 |

形式化表达：设 **V** = 可视化节点编排，**A** = Agent 原生执行，**C** = ComfyUI 作执行引擎。

```
TapCanvas / wind-comic / novella   ∈  V ×  A × ¬C
NiliX / kt-ai-Studio / auto-drama  ∈ ¬V × ¬A ×  C
Novel-Director                     ∈  V × ¬A ×  C
─────────────────────────────────────────────────
本课题                              ∈  V ×  A ×  C    ← 空集
```

**这是本项目的立项依据**：`V × A × C` 在当前生态中是空集。

## 二、项目定位与目标

### 2.1 一句话定位

> 以「**语义级节点编排 → 自动编译为 ComfyUI 执行图 → 确定性验收 → 回写共享黑板**」
> 闭环为核心的漫剧工业化生产平台。

### 2.2 两个并列的核心

本项目有**两个**核心，它们构成一个闭环的两端，**不是主从关系**：

```
   ┌──────────────────────────────────────────────┐
   │  多智能体协作                                  │
   │  回答：谁来决定、谁来质疑、谁裁决               │
   └───────────────────┬──────────────────────────┘
                       │ ① Agent 写 IR（分工产出语义图 + 约束）
                       ▼
   ┌──────────────────────────────────────────────┐
   │  统一 IR（Unified IR）                        │
   │  回答：决定以什么形式存在、如何被验证、如何被执行  │
   └───────────────────┬──────────────────────────┘
                       │ ② 编译 → 执行 → 产出
                       ▼
   ┌──────────────────────────────────────────────┐
   │  ComfyUI 执行底座                             │
   └───────────────────┬──────────────────────────┘
                       │ ③ 产物 + 降级原因 + 断言结果 → 回写黑板
                       └──────────► 回到多智能体协作
```

**为什么二者不可分割**：

- **没有 IR**，多智能体协作只能产出**散文**——一堆积木式拼接的提示词，
  无法校验、无法缓存、无法验收。
- **没有多智能体协作**，IR 只是一个**空壳表示**——没人往里写，
  也没有多视角的质疑机制。

### 2.3 三个可量化目标

| # | 目标 | 度量 |
|---|---|---|
| **G1** | 打通端到端出片 | 从一句剧本到一集 60 镜成片，**全自动无人工干预** |
| **G2** | 证明成本可控 | 改一句 IR，**只重跑受影响的镜头**，其余命中缓存；给出实测节省比例 |
| **G3** | 证明验收有效 | 跨模型族盲读门禁能**拦住**人工判定为不合格的产出，给出拦截率 |

## 三、核心技术方案

### 3.1 核心创新点 C1：双层同构 DAG 与统一 IR

**问题**：语义图与执行图是两种完全不同的图，但现有工具只能表达其中一种。

**方案**：定义**统一 IR**，同时承载两种信息：

```jsonc
{
  "irVersion": "little_crew.ir/v1",
  "graphId": "G-ep001-sh005",
  "scope": "shot",
  "bindings": {                      // 资产绑定：语义层引用，编译期解析为具体文件
    "CHAR-0007": {
      "anchorSet": { "front": "char/CHAR-0007/anchor_front_v3.png" },
      "anchorGeneration": 3,
      "loraFile": "linwan_v3.safetensors"
    }
  },
  "nodes": [
    { "id": "n_prompt", "kind": "prompt.text",
      "params": { "text": "雨夜天台, 米色风衣, 回头, 近景, 缓推" },
      "semantic": { "characterRef": "CHAR-0007",
                    "constraintRefs": ["cr_costume_007"] } }
  ],
  "edges": [ /* 两种边，见下 */ ],
  "constraints": [ /* 可执行断言 */ ]
}
```

**关键设计：IR 有两种独立子类型的边。**

| 边类型 | 编译结果 | 作用 |
|---|---|---|
| `data` | 编译为 ComfyUI 的节点连接 | 决定"怎么算" |
| **`constraint`** | **不编译**，生成**可执行断言** | 决定"算出来的必须满足什么" |

**constraint 边是 IR 区别于普通工作流 JSON 的本质**。它让
"这个镜头必须长得像角色 7"从提示词里的一句话，变成一条可判定、可回滚的约束：

```jsonc
{ "type": "constraint",
  "target": "n_save",
  "assertion": { "op": "identity_similarity",
                 "threshold": 0.82,
                 "against": "CHAR-0007.anchor_set" },
  "enforcement": "hard",          // hard | soft | audit
  "onFailure": { "action": "retry_with", "maxAttempts": 3 } }
```

**配套机制：六步规范化 + 内容哈希**（`ir/canonical.py`）

保证"语义等价 ⇒ 哈希相同"，这是三级缓存与产物时效清单的地基。
三级缓存键：

| 级别 | 键 | 语义 |
|---|---|---|
| **T1** | `md5(irHash ‖ catalogHash ‖ ruleVersion)` | 精确复用：同 IR + 同环境 + 同规则 |
| **T2** | `sha256(irHash)` | 跨环境语义复用（需重校验质量断言） |
| **T3** | 条件指纹 | 按约束条件复用 |

### 3.2 核心创新点 C2：Transformer 调度智能体

**问题**：多智能体编排若只靠 LLM 逐轮对话，成本高、不可复现、无法预算。

**方案**：自研三个轻量 Transformer 模块，先以**影子模式**运行（只记录不决策），
积累数据后逐步接管：

| 模块 | 规模 | 职责 |
|---|---|---|
| **Scheduler** | ~12M | 图编码器 + Actor-Critic，决定"下一步该调哪个 Agent" |
| **Consistency Embedder** | 256 维 | 把角色/场景/风格编码为可跨镜比对的一致性向量 |
| **Light Verifier** | ~5M（ViT-Tiny） | 轻量判定"这张图合格吗"，替代部分 VLM 调用 |

**降级预案（重要）**：若训练数据不足或时间不够，**不硬撑**。改为：

> "本文提出并验证了 **Agent 决策接口协议**，并用**规则基线**实现了参考实现；
> 自研模型的训练留作后续工作，本文给出数据构造方案与可行性验证。"

这样仍是原创贡献（协议设计与验证本身即贡献），且无编造风险。

### 3.3 核心创新点 C3：确定性验收门禁

**问题**：出图的模型自己判定合格，等于自我签收。

**方案**：三层把关，**生成方与审核方物理隔离**：

| 层 | 机制 | 性质 |
|---|---|---|
| L1 | **确定性断言算子** | 客观、可复现、零成本（如 `identity_similarity` 阈值判定） |
| L2 | **一致性嵌入** | 连续可度量，可追踪跨镜漂移趋势 |
| L3 | **跨模型族盲读** | 生成方与审核方**必须不同模型族** |

**硬性约束**（代码强制，非文档约定）：

- 加权总分**由服务端权威计算**，不信任模型自报（模型在评分任务上有系统性乐观偏差）
- 偏差 > 5 分则报告作废重审
- `review` 包**不做生成**，`runtime` 包**不做判定** —— 从结构上杜绝既当运动员又当裁判

### 3.4 多智能体协作机制

**18 个职位，按真实剧组建制组织。**

Agent 不是抽象编号，而是**剧组的真实职业** —— 这不是命名偏好，而是一条设计决策：

> 真实剧组里"谁管什么"已经过几百年打磨。照搬这套分工，
> **比自创更不容易出现职责重叠或真空**；而且产出物名可直接对应
> （摄影指导交镜头、剪辑师交成片、场记交场记单），不必另发明一套产物分类。

#### 3.4.1 剧组建制表

| 部门 | 职位 | 交付 |
|---|---|---|
| **导演组** | 导演 | 编排计划、最终创作决策 |
| **编剧组** | 编剧、剧本顾问、文学策划 | 剧本草稿/定稿、剧评意见、风格把关 |
| **美术组** | 美术指导、角色设计师、场记 | 场景库与美术 bible、角色锚点图集、连贯性报告 |
| **摄影组** | 分镜师、摄影指导、灯光师、摄影师 | 镜头表、逐镜图像、光照方案、运动镜头 |
| **录音组** | 对白剪辑、作曲 | 对白音轨、配乐 |
| **剪辑组** | 剪辑师、合成剪辑 | 节奏方案、成片母版与交付证据链 |
| **制片组** | 制片主任、版权与合规 | 排期与预算、合规报告 |
| **审片组** | 审片 | 品控裁定 |

**执行方式分布**（决定成本与调度）：

| 执行方式 | 人数 | 说明 |
|---|---|---|
| 文本推理 | 8 | 编剧、剧评、分镜、排期等 |
| 视觉判定 | 2 | 场记、审片（**跨模型族盲读**） |
| 图像生成 | 3 | 美术指导、角色设计师、摄影指导 |
| 视频生成 | 1 | 摄影师 |
| 音频生成 | 2 | 对白剪辑、作曲 |
| **纯确定性组装** | 2 | 合成剪辑、版权与合规（**不调模型**） |

> **确定性职责不是 Agent，是工具。**
> 技术质检（查分辨率/时长/帧率/编码）与合规核对（查归属标注是否注入）
> 本质是**规则判定**，不需要模型决策。做成 Agent 的后果是每次质检都花钱、
> 引入不确定性，且**永远不如一条断言可靠**。它们的位置是 L3 执行工具
> （`qc.tech_check` / `license.audit`）。

#### 3.4.2 协作机制的四层结构

| 层 | 机制 | 解决什么 |
|---|---|---|
| 1 | **剧组分工**（上表） | 职责隔离 |
| 2 | **审查循环**：编剧出稿 → **并行双维审查**（剧本顾问 ‖ 文学策划）→ 导演合并 → 返工 | 单一视角会自证 |
| 3 | **QC-5 五维品控**：完整性 25 / **一致性 40** / 品质感 25 / 可执行性 / 合规性，**权重按阶段调整** | 度量可审计 |
| 4 | **结构化消息**：职位之间**不传自由文本**，只传带 schema 的消息 | 可追溯、可量化、可复现 |

**第 4 条是分水岭。** 若职位之间传自由文本，"协作"退化为"多轮对话"——
无法审计、无法量化、无法复现。

#### 3.4.3 三条不可绕过的硬规则（代码强制）

**① 服务端权威算分** —— 不信任模型自报

模型在评分任务上有**系统性乐观偏差**：自报分与其给出的维度明细常常不自洽。

```
实测情形：模型自报 90 分
          但维度明细为 一致性45 / 完整性80 / 品质感70 / 可执行85 / 合规95
          加权权威总分 = 64.5        ← 权威值由维度算出
          偏差 25.5 > 容差 5.0       → 整个报告作废，判定 ESCALATE
```

不可信时**整个报告作废重审** —— 不是因为自报分错了，而是因为
"自报分与自身维度明细不自洽"说明该职位的判定过程不可靠。

**② 跨模型族盲读** —— 生成方与审核方必须不同族

```python
"qwen3-vl-max" 审核 "deepseek-v4" 的产出  →  ✅ 跨族，结论有效
"qwen3-vl-max" 审核 "qwen3-max"  的产出  →  ❌ 同族，判定 ESCALATE
```

**③ 不自我签收** —— 按**产出归属**判定，而非按"是否具备审核能力"

> ⚠️ 这条规则本项目的校验器**曾经写错过**：早期判据是"生成了内容又声明审核能力"，
> 于是把**剧本顾问**与**文学策划**判为违规 —— 而那两位**只**审别人的稿，
> 审核正是它们唯一的职责。错在把"有审核能力"当成了"自我签收"。
>
> 正确判据是**产出归属**：某职位交付的产物，不得由它自己审核。

#### 3.4.4 结构化消息示例

```jsonc
{ "kind": "review_feedback",
  "msgId": "msg_a9cf3c2e...",  "replyTo": "msg_...",   // 审查链可追溯
  "from": "dramaturge",  "to": "screenwriter",
  "verdict": "REVISE",              // PASS | REVISE | REJECT | ESCALATE
  "score": {
    "dimensions": { "consistency": 45, "completeness": 80,
                    "quality": 70, "feasibility": 85, "compliance": 95 },
    "claimedScore": 90,             // 模型自报（仅用于偏差检测）
    "total": 64.5,                  // 权威算分
    "weakest": { "dimension": "consistency", "score": 45 }
  },
  "issues": [
    { "severity": "major", "dimension": "consistency",
      "location": { "scene": "SC-E001-003", "line": 42 },   // 必须结构化定位
      "problem": "角色服装与第 2 场不一致",
      "suggestion": "改为米色风衣" }
  ],
  "repairHints": [
    { "graphId": "G-ep001-sh005", "op": "insert_shot",
      "args": { "after": "SH-E001-003-007", "durationSec": 3.0 },
      "fromIssue": "issue_001" }
  ],
  "reviewerModel": "qwen3-vl-max", "generatorModel": "deepseek-v4" }
```

**三条强制的可执行性要求**：

| # | 要求 | 为什么 |
|---|---|---|
| 1 | `issues[].location` **必须结构化**（场/镜/行/资产） | 散文式定位**无法驱动自动返工** |
| 2 | `BLOCKER` 级问题**必须给 `suggestion`** | 否则编排器产生不出可执行的返工指令（构造时即拒绝） |
| 3 | `repairHints[].op` 走**白名单**，且必须带 `graphId` | **这是协作闭环的落点** —— 每条返工指令都能映射成 IR 变更 |

**第 3 条是关键**：`repairHints` 里的"在某镜后插入镜头"就是**图结构变更**，
可直接翻译为 IR 补丁 → 重编译 → 再审。**审查到执行之间没有人工翻译环节。**

### 3.5 不依赖编排框架的三层调用协议

**明确决策：不使用 LangGraph 等图编排框架。**

**理由**：它用**同一抽象（图）**同时表达两个**正交**的轴：

```
轴 A · 组织分层  —— 决策层 / 协作层 / 执行层   （本质是树）
轴 B · 推理循环  —— 有界状态机，步数上限必须可校验
```

压扁成同一种表示后，**层边界不可强制**、**推理轮数上限不可校验**，
且使真正需要图的 IR 执行 DAG 失去立足点。

**替代方案：三原语**

| 原语 | 职责 |
|---|---|
| **CapabilityRegistry** | 能力发现：谁能做什么 |
| **CallEnvelope** | 三层同一信封：调用链由 span 天然构成，可观测性零额外埋点 |
| **Blackboard** | 共享黑板：乐观并发 + 失效传播 |

**四条层边界硬规则**（代码强制，违反即测试失败）：

| 规则 | 内容 |
|---|---|
| **R1** | 单向依赖：L3 不得回调上层 |
| **R2** | 禁止跳层：L1 不得直调 L3 |
| **R3** | 预算只减不增（子调用预算 ≤ 父剩余预算） |
| **R4** | 深度硬上限（6 层） |

**有界推理循环**：步数上限是**构造参数**而非图上的跳转条件 —— **Agent 无法绕过**。

### 3.6 模型双通道（本地 / API 统一抽象）

**需求**：用户可选择用**本地模型**（零成本、慢）或**云端 API**（快、按量计费）。

**方案：把"模型"与"通道"拆成两个正交维度。**

```
模型（干什么、擅长什么）              通道（在哪跑、怎么调）
  TaskKind        任务域                COMFYUI   本地节点图执行
  Capability      能力画像              HTTP      直连 HTTP
  ResourceProfile 资源画像              PROCESS   本地进程内（预留）
  CostProfile     成本画像
```

**关键判断：本地服务与云端 API 不是两种通道，是同一种通道的两个 endpoint。**

`D:\AI\local-gen` 暴露的是与云端等价的 OpenAI 兼容 HTTP 接口，
因此它与 DeepSeek / 通义走**同一段代码**，只是 endpoint 不同。
**只有 ComfyUI 因为需要"编译成节点图"才是真正不同的通道。**

| 形态 | 示例 | 说明 |
|---|---|---|
| 真·双通道 | `minimax-h3` | 本地 ComfyUI 节点 **或** 云端 HTTP API |
| 两个本地后端 | `z-image-turbo` | ComfyUI 节点图 **或** `local-gen` HTTP 服务 |
| 仅 HTTP | `deepseek-v4` | 无本地权重 |

**通道契约的四条硬要求**：

| # | 条款 | 为什么 |
|---|---|---|
| **R1** | 提交幂等 | 本地重跑浪费数分钟 GPU；**云端重跑重复计费** |
| **R2** | 可中断 | 取消后不得再有产物落地 |
| **R3** | 可对账 | 崩溃重启回收已完成任务，**绝不重复提交** —— 4 小时长跑续跑的基础 |
| **R4** | 进度可观测 | 细粒度进度供前端与超时判定 |

**模型路由**（`compiler/router.py`）：六步求解，**淘汰理由可解释**：

```
task → 通道形态 → 授权门禁 → 能力必满足 → 成本上限 → 软偏好排序
```

"为什么没选它"和"为什么选它"同样重要 —— 否则用户无法理解平台的决策。

### 3.7 模型授权门禁（合规硬约束）

**把模型权重授权变成代码强制的硬约束**，三条强制行为：

| 行为 | 说明 |
|---|---|
| **A. 未核实即拒绝** | 授权目录中无记录、或标记未核实 → `NEEDS_REVIEW`，**不放行** |
| **B. 降级链每跳重过授权** | 因能力降级换模型时，必须重新过门禁 —— 不能"换个能用的"绕过合规 |
| **C. 归属标注自动注入** | 要求标注的模型，其标注文本自动进入交付物元数据 |

**已逐一核验的授权事实**（19 个模型，`LICENSE_CATALOG`）包含几个
"名字几乎一样、后果完全不同"的陷阱：

- **FLUX.2 Klein `4B` = Apache-2.0 可商用 / `9B` = 禁商用**
- **MiniMax H3 排除 US/EU/UK/KR**，中国大陆在范围内；营收 2000 万美元门槛；须界面标注
- **Wan 开源线到 2.2 为止** —— 网上流传的"2.7 开源"是假消息
- **Lens 是 repackage**，原始厂商与授权待查

**API 服务类模型单列一类**：其授权是**合同问题**（服务条款）而非**版权问题**（许可证），
后果也不同（前者可能被停服，后者是版权风险）。因此这类条目一律
`verified=False + NEEDS_REVIEW`，**部署方须逐条核实后再启用**。

### 3.8 3D 白模：以几何约束换取空间与机位一致性

**问题定位**：本项目的 P1（长程一致性崩塌）有两个正交的子问题，而纯 2D 参考图
只能解决其中一个：

| 子问题 | 2D 参考图能解决吗 |
|---|---|
| **外观一致性**（角色脸型、服装） | ✅ 能（`identity.reference`） |
| **空间一致性**（站位、轴线、纵深、机位） | ❌ **不能** |

一张参考图无法约束"角色在这一镜朝左、下一镜朝右"（跳轴），也无法保证
"第 3 镜与第 17 镜是同一机位"。**3D 白模补的正是这一块。**

#### 3.8.1 核心设计决策：白模是「确定性渲染步骤」，不是「IR 里的一棵 3D 树」

这是本节最重要的架构决策，它决定了整个方案的代价。

```
❌ IR 中加一棵 scene3d 树（顶点 / 相机矩阵 / 骨骼）
   → schema 大改 · 浮点哈希失稳 · 协议破坏性变更 · 全部测试复查

✅ IR 声明**语义镜头意图**，白模是一步**确定性渲染**
   → IR 几乎不动 · 白模可哈希可缓存 · 与现有抽象同构
```

**为什么后者正确**：本平台的核心抽象是「**声明式输入 → 确定性编译 → 可哈希产物**」。
白模恰好符合该模式 —— **同一套 `(镜头规格 + 角色参数 + 模板 id)`
必然产出同一段白模序列**，因而天然可哈希、可缓存、可复现。

这与 `ir` 的六步规范化、三级缓存键是同一套机制，**不是新增机制**。

#### 3.8.2 数据流

```
IR（语义层，改动极小）
  shot: { character, pose, path, camera, shot_size, lighting, duration }
        │
        │ ① 预演师 Agent（LLM 只做**选择**，不产生坐标）
        ▼
  预演意图（结构化消息，复用 agent/messages.py）
        │
        │ ② 几何层（确定性代码，**无任何模型参与**）
        ▼
  白模场景（参数化代理 + 模板驱动关键帧）
        │
        │ ③ Blender headless（Workbench 引擎，**CPU**）
        ▼
  控制序列（Gray 灰度 / Depth 深度 / Normal 法线）
        │
        │ ④ H3 ControlNet
        ▼
  视频
```

#### 3.8.3 三个关键设计点

**① LLM 只选模板，不产生坐标**

LLM 的数值空间推理不可靠 —— 让它输出相机矩阵会得到"看似合理但穿墙"的结果。
正确分工是：

| 角色 | 职责 |
|---|---|
| **LLM（预演师）** | 从模板库**选择**：`{pose: "回头", camera: "过肩推进", shot_size: "medium_close"}` |
| **确定性代码** | 模板 id + 参数 → **坐标与关键帧** |

坐标计算、碰撞检测、轴线校验全部确定性 —— **可验证、可复现、可缓存**。

**② 几何用参数化代理，不用文生 3D 模型**

| 方案 | 判断 |
|---|---|
| 文生 3D 模型（Hunyuan3D 等） | ❌ 输出带纹理的精细资产，**且一致性是弱项**（同一角色生成两次得到两个人） |
| 单图重建 3D | ❌ 需要额外模型，本机内存紧张，质量不稳 |
| **参数化代理** | ✅ **参数相同 ⇒ 几何必然相同**，一致性完美；毫秒级生成；与哈希体系天然契合 |

白模只需要几何，不需要纹理 —— 因此"低模胶囊体"不是妥协，而是**恰好够用**。

**③ Blender 用 Workbench（CPU），不碰 GPU**

本机 8 GB 显存同时只能加载一个模型。若白模渲染用 EEVEE（GPU），
会与 ComfyUI **争夺显存导致来回卸载重载**。

Workbench 渲染的深度图/灰度图**不需要光追**，CPU 完全够用，
且让预演师成为**纯 CPU 职位**，与 GPU 调度彻底解耦。

#### 3.8.4 可行性依据（官方样片实证）

阿里 PAI 为 H3 发布的 `Fun-ControlNet-Union-2.0` 支持 **8 种控制条件**，
且官方仓库附带**控制输入与生成结果的对比样片**：

| 控制条件 | 对白模的意义 |
|---|---|
| **Gray（灰度）** | ✅ **白模渲染出来本就是灰度图 —— 可直接作为控制输入** |
| **Depth（深度）** | ✅ 更精确的空间约束 |
| **Layout（布局框）** | 站位控制，最省事（彩色框即可，无需 3D） |
| Canny / HED / MLSD | 边缘类，轮廓控制 |
| Pose | 骨架，动作控制 |

**关键实证结论**（取自官方样片逐帧比对）：

- **Depth 控制**：狗的位置、朝向、**大小变化**严格跟随深度序列；
  背景透视一致；生成画面质量**未因控制而退化**
- 但**外观每帧不同** —— 深度管的是「**东西在哪、多大、怎么动**」，
  **不管「长什么样」**。因此：

> **3D 白模与 2D 参考图是互补关系，不是替代关系。**
> **参考图锁「长相」，白模锁「空间」。二者叠加才是完整的一致性方案。**

**`control_context_scale` 可调**（1.0 最强 / 0.0 完全关闭）——
这使"白模影响多大"成为一个**可调参数**而非硬约束。

#### 3.8.5 接入方式：一个新工具，不是一套新架构

| 组件 | 设计 | 改动量 |
|---|---|---|
| **通道** | `runtime/channels/blender.py`，子进程调用 | 小（双通道抽象已预留 `PROCESS`） |
| **工具** | 注册 L3 工具 `blender.render` | 小 |
| **职位** | 名册新增「预演师 / Previs Artist」，`ExecutionKind.PROCESS`（纯 CPU） | 一条声明（18→19） |
| **IR** | 新增 1~2 个 kind + `bindings` 加代理参数 + 相机**语义**字段 | **中**（远小于"加一棵 3D 树"） |
| **编译规则** | 加 2~3 条映射到 `blender.render` | 小 |
| **前端** | **参数表单 + 服务端渲染回图**，**不做 3D 编辑器** | 小 |
| **模板库** | 复用[鲲鹏导演台](https://github.com/pengfeiqiao/kunpeng-director)的动作/运镜模板（**MIT 许可，可合法复用**） | 数据工作 |

**⚠️ GPL 隔离**：Blender 是 GPL 软件，其官方许可明确要求"发布的 addon 必须 GPL"。
因此本平台**只以子进程方式调用 Blender，不写 addon、不链接、不分发其二进制** ——
子进程边界使平台保持 Apache-2.0。

#### 3.8.6 网页接入：分两阶段

**阶段 1（推荐先做）：参数表单 + 服务端渲染**

```
浏览器                        平台后端
  ├─ 选角色 / 动作模板 ────────►│
  ├─ 选运镜 / 调时长 ──────────►│ Blender 渲染（CPU）
  │◄─── 白模预览图 / 预览视频 ───┤
  ├─ 满意 → 提交生成 ──────────►│ H3 ControlNet → 视频
  │◄─── 成片 ───────────────────┤
```

前端**零 3D 代码**。用户看到的是渲染出的图片，不是网页里的 3D 场景。
延迟约 3~10 秒（Workbench 单帧 0.5~2 秒），**可接受**。

**阶段 2（可选，将来）**：若确实需要拖拽编辑，再引入 Three.js
（但要**手写深度/法线 GLSL**，且分布需与 ControlNet 训练分布对齐）
或直接集成鲲鹏导演台作为编辑前端。

> **为什么阶段 1 优先**：Three.js 的深度纹理是**为阴影贴图优化**的
> （非线性、视图空间），而 ControlNet 是在 Blender 式 Z-pass 上训练的。
> 用 Three.js 产出可用控制图**不是配置问题，是重写渲染通道**。

#### 3.8.7 实测结果（P1 已完成）

**2026-10-11 实测**：参数化几何 → Workbench 双通道渲染的本地链路**已跑通**。

环境：Blender **4.5.14 LTS**（内置 Python 3.11.15）· Workbench 引擎（纯 CPU）

| 环节 | 实测结果 |
|---|---|
| **参数化几何** | `168cm / slim / 7.6 头身` → 全身人形（头 / 躯干 / 双臂 / 双手 / 双腿），比例自洽 |
| **几何自洽性** | 头 0.2211 + 颈 0.0884 + 躯干 0.5085 + 腿 0.8621 = **1.6801 m** ✅（腿占身高 51%，符合成人比例） |
| **单帧耗时** | **0.055 秒** @832×480（Workbench） |
| **显存占用** | **+88 MB** —— 与 Workbench 的空闲基线对比 |
| **对照：EEVEE** | 3.0 秒/帧、**+1155 MB** —— 因此**不选 EEVEE** |
| **双通道输出** | Gray 灰度（标准差 25.7 / 144 灰阶）+ Depth 深度（标准差 56.2），**同一镜头、同一几何** |
| **帧数对齐** | **124 帧 = 17×7+5** ✅ 精确落在 H3 的 VAE 网格上 |
| **输出帧率** | **固定 24 fps** ✅ |
| **248 帧（两遍，静态）** | **13.7 秒** |
| **248 帧（两遍，逐帧重建姿态）** | **约 35 秒** |
| **人体测量比例** | 大腿半径/身高 **0.0455**（成人 0.049）· 小腿 0.0360（0.039）· 上臂 0.0285（0.030）· 颈 0.0335（0.034） |
| **动作模板** | **8 个**（`stand` / `walk` / `run` / `look_back` / `point_forward` / `sit_down` / `wave` / `recoil`），姿态峰值帧与站姿差异最大 **14,279 像素** |

**一个对成本模型有实质影响的推论**：

| 场景 | 白模预演耗时 | 对比 H3 生成 |
|---|---|---|
| 单镜（5 秒 / 124 帧） | **7 秒** | H3 需 **442~518 秒** |
| 一集（60 镜） | **约 7 分钟** | 数小时 |

> **白模预演比视频生成快 60 倍以上，成本几乎可忽略。**
> 这意味着**可以先出全套白模给导演审、改完再渲染** ——
> 白模序列可无限次重出，不构成成本约束。

**关键工程决策（由实测数据支撑）**：

> **Workbench 也能输出深度图。** `ViewLayer.use_pass_z` 是**与渲染引擎无关**的
> 渲染通道，配合合成器的 `Map Range` 归一化即可得到灰度深度图。
> 因此**不需要为了深度图而付出 EEVEE 的 55 倍时间与 13 倍显存**。

##### 与现有白模产出的对应关系

白模已实现**双通道渲染**（§3.8.4）：

| 白模通道 | 对应用途 |
|---|---|

##### ⚠️ 必须记录的坑：DiffSynth 补丁（**保留备查** —— 最终走 ComfyUI 通道，未用到）

本机（Windows + torch 2.9.1 + safetensors）下，`safe_open(...).get_tensor()`
对**大于约 4 GB** 的 safetensors **必然失败**：

| device | 表现 |
|---|---|
| `"cpu"` | **进程段错误退出（0xC0000005）** |
| `"cuda"` | `RuntimeError: invalid python storage` |

而 P3 的两个文件都超限：**ControlNet 6.25 GB、transformer 22.93 GB**。

**补丁**：`D:\AI\local-gen\app\diffsynth_patch.py`
（把 `DiskMap` 的句柄换成纯 Python 的 seek/read 读取器，不用 mmap）。

> **必须在 `import diffsynth` 之前打补丁** —— 否则只会看到一个光秃秃的段错误，
> 极难定位（本次已踩）。

**补丁自身的代价**：它用 `bytearray(raw)` 复制一份张量数据，
所以 6.25 GB 的文件在 15.8 GB 内存下就 `MemoryError`。
**内存充裕的机器上无此问题**，但这一点必须知道。

##### 附带修复：白模 Depth 通道退化成剪影（真实缺陷）

**症状**：Depth 通道几乎是纯色剪影，没有深度梯度。

| 通道 | 主体灰度跨度 | 标准差 |
|---|---|---|
| **Depth（修复前）** | **5 ~ 22 级** | **0.9 ~ 3.0** |
| Gray（对照） | 132 ~ 138 级 | 16 ~ 22 |

**根因**（不是 bug，是归一化区间选错）：旧做法取
`[d0 − 1.2h, d0 + 1.5h]`，对 1.68 m 的人是 **5.46 m 跨度**；
而角色自身景深仅约 0.5 m —— **只占 9%**，理论灰度跨度就是约 23 级，**与实测吻合**。

**这类缺陷不报错，只是静默地把控制信号变弱** —— 而 depth 条件恰恰靠梯度工作。

**修法**：改为按主体包围盒实测景深（`auto_depth_range`），两端留 12% 余量。
**效果：主体灰度跨度 10.2 → 45.8 级（4.5 倍）。**

修复过程还踩了两个陷阱，都已写入代码注释：

| # | 陷阱 | 后果 |
|---|---|---|
| **1** | `matrix_world` **不随 `location` 立即更新**，须先 `view_layer.update()` | 读到单位矩阵 → 转相机空间等于没转 → 算出**负距离** → 被夹成 0.246 m 荒谬区间 → **像素全截断成纯黑纯白** |
| **2** | 几何是**逐帧重建**的，默认站姿的包围盒不代表整镜 | 走路时手臂摆动改变景深 → 改为**跨动作时刻采样取并集** |

> （5.9 GB）+ 分块卸载**。**同一个模型，装载方式决定了可行性。**

**这正是本项目"双通道正交"设计的价值兑现**：换通道不改流水线。

##### ⚠️ 三个必须记住的调优结论（都靠看图得出，非指标算出）

**① `scheduler` 必须是 `simple`，`karras` 会产出崩坏的画面**

最隐蔽的一条。同样的图、同样的种子、同样的提示词，**只换调度器**：

| scheduler | 结果 |
|---|---|
| `karras` | ❌ **大片暗块 + 荧光错色 + 人物数量错乱**；模糊节点还会渲染成一个亮绿球 |
| `simple` | ✅ 完全干净 |

`shot_to_ir` 原先的默认值就是 `karras` —— **所以这是默认值错误，不是参数偏好**。
`simple` 也是 Z-Image-Turbo 官方示例用的调度器。

**② 控制信号要**模糊**，不要用实心剪影**

白模的实心剪影**带内部明暗**，模型会去**描摹骨架的内部细节**（手臂、腿的精确位置），
人物因此被驯化成骨架形 —— 用户的原话是"完全不像人"。

加一道高斯模糊（`ImageBlur`，半径 18 @832×480）抹掉内部结构，只留
"**这一团是中景偏左的一个人，这么大**"：**定位信息保住，外观自由度还给模型**。

做成**图节点**而非平台侧预处理：`blur_radius` 会自动进入 IR 哈希，
改半径必然重渲。平台侧处理则要额外维护一份参数哈希 ——
漏了就是"改了参数却命中旧缓存"，那类失效**无法察觉**。

**③ 强度 0.5，不是 1.0**

实测三档强度（1.0 / 0.6 / 0.35）的**构图、人物大小、位置完全一致**，
只有**姿态自由度**不同 —— 所以**降强度不损失定位**，只让人更自然。

**④ 提示词必须写全场景**（最容易误判成"模型坏了"）

只写"一位少女"时产出**大片暗块 + 荧光错色**，看起来像模型链路出了问题。
补上地点与光线后立刻干净。**遇到"画面崩坏"先查提示词，再怀疑模型。**

## 四、系统架构

### 4.1 双轴分层模型

**两个正交的分层轴，不可互相替代**：

```
轴 A · 代码分层（静态结构）        轴 B · 运行时分层（动态行为）
  [0] version  ir                     L1 决策层  —— Agent 决策
  [1] governance                      L2 协作层  —— 协议、黑板、预算
  [2] models  capability              L3 执行层  —— 编译、提交、回收
  [3] compiler  agent
  [4] runtime  review
  [5] api  cli
```

**轴 A 的一条代码可以参与轴 B 的多个层**（如 `compiler` 既被 L1 调用做规划，
也被 L3 调用做编译），但**依赖方向只由轴 A 约束**。

### 4.2 依赖铁律（机器强制）

| 规则 | 说明 |
|---|---|
| 高层可依赖低层 | `compiler` 可用 `capability` |
| **低层不得依赖高层** | `ir` **绝不能** import `compiler` |
| 同层依赖需白名单 | 目前只有 `(compiler, capability)`、`(compiler, models)` |
| 叶子层零内部依赖 | `ir` 与 `governance` |

**由 `tests/test_architecture.py` 强制**，违反直接测试失败。

> **为什么需要架构守卫**：违反依赖方向**通常不影响功能**。
> 功能测试永远发现不了架构退化 —— 等发现时，解耦成本已经很高。

### 4.3 零第三方依赖（核心层）

`ir` / `governance` / `models` / `capability` / `compiler` / `agent`
**运行期与测试期均不引入第三方库**。

| 需求 | 用的标准库 |
|---|---|
| TOML 配置 | `tomllib`（Python 3.11+） |
| HTTP 客户端 | `urllib.request` |
| WebSocket | `socket` + 手写 RFC 6455 子集 |
| 数据校验 | `dataclasses` + 自研断言 |

**收益**：核心层可独立测试、可独立发布、不受依赖冲突影响；
任何人 clone 下来即可跑通全部测试。

## 五·五、成本可控的实测证据（缓存在渲染链上的效果）

**这是"改一句只重跑受影响的镜头"从设计意图变成可验证事实的地方。**
数据由 `src/little_crew/runtime/cache_measure.py` 采集，可复现。

**环境**：Z-Image-Turbo（local-gen HTTP 通道）· 3 镜 · 8 步 · 832×480

| 运行 | 场景 | 实算 | 命中 | 命中率 | 耗时 | 节省 |
|---|---|---|---|---|---|---|
| **R1** | 首跑（建立缓存） | 3 | 0 | 0% | **75.7 s** | — |
| **R2** | 什么都不改，重跑 | **0** | 3 | **100%** | **0.0 s** | **75.5 s** |
| **R3** | **只改第 2 镜**，重跑 | **1** | 2 | 66.7% | **13.3 s** | **57.5 s** |

> **R2：重跑一集从 75.7 秒降到 0.0 秒（1889×）。**
> **R3：改一个镜头只需 13.3 秒，而不是 75.7 秒（5.31×）。**

**核心命题成立：改一个镜头，只有它被重跑。**

### 它是怎么做到的（不需要增量分析）

缓存键 = `sha256(irHash ‖ catalogHash ‖ ruleVersion)`，而 `irHash` 是
**内容哈希**，只随语义变化。于是：

```
改第 2 镜的服装  →  第 2 镜 irHash 变  →  只有它未命中
                    其余镜 irHash 不变 →  全部命中，零 GPU
```

**内容寻址本身就是增量的** —— 不需要"依赖图推导"或"影响分析"。
这也是为什么 C1（统一 IR + 内容哈希）与 P4（成本失控）是同一个设计的两面。

### 度量方法学（三条必须遵守的）

| 要求 | 违反的后果 |
|---|---|
| **跨运行测量** | 同一会话内重跑会被 `RenderSession` 自身的 R1 幂等掩盖 —— **测的是空气** |
| **分清算谁的缓存** | 我们的三级缓存（零 GPU）与 ComfyUI 节点级缓存（仍要提交）**来源不同**，混记会让指标虚高 |
| **对照组要真的不写缓存** | 若对照组也在写缓存，后面的"开缓存"自然命中不了 —— 实验组与对照组就变成了同一组 |

## 五·六、断点续跑的实测证据（长跑可作性）

一集按实测是**分钟到小时级**。在这个时长上，崩溃、重启、误关窗口
**不是异常，是必然**。而"从头再来"的代价不只是时间 ——
**云端按次计费，重跑就是重复付费**。

**所以续跑不是便利功能，是长跑可作性的前提。**

### 真机实测（Z-Image-Turbo · 5 镜）

```
第一次运行：跑到第 3 镜后硬中断  →  完成 3 镜（101.7 s）
   ↓ 模拟崩溃（进程退出，检查点账本已落盘：{succeeded: 3}）
重启：加载账本 → 计划 = 已完成 3 / 需对账 0 / 待重跑 0 / 全新 2
   ↓
第二次运行：只跑缺的 2 镜（25.9 s），其余 3 镜直接命中
最终账本：{succeeded: 5}
```

> **若不续跑、从头再来需重跑 5 镜；实际只跑了 2 镜，省下约 75.8 秒。**

### 两阶段提交：为什么"提交前"就要落盘

```
① 写意图（PENDING，含幂等键与请求指纹）   ← 崩在提交之前 → 无副作用
② 提交，拿到 channel_id 立刻落盘            ← 崩在提交之后 → 必须能找回
③ 完成后记产物引用（SUCCEEDED）
```

**关键是①必须在②之前落盘。** 若只在拿到 channel_id 之后才写，
在"提交成功、还没来得及写"这一瞬间崩溃，重启后就**不知道有个任务在跑** ——
只能重新提交，而服务端其实已经在跑。结果：**双份 GPU**。

（严格说这一瞬间仍无法完全消除；但把窗口从"整个提交往返（可能几十秒）"
压到"一次本地写（毫秒级）"，风险降低几个数量级。）

### 状态机刻意区分两种"未完成"

| 状态 | 含义 | 能否直接重提 |
|---|---|---|
| `PENDING` | 记了意图但没提交成功 | ✅ 安全 |
| **`SUBMITTED`** | **已提交**（服务端可能已经在跑） | ❌ **必须先对账** |

**把这两者混为一谈，就是重复烧 GPU 的根源。**

### 与内容缓存的分工

| | 内容缓存（§5.5） | 检查点（本节） |
|---|---|---|
| 记什么 | **结果**（跑出来的产物） | **过程中的状态**（谁在跑、跑到哪） |
| 键 | 内容哈希 | job_id（幂等键） |
| 解决 | **改一句只重跑受影响的** | **跑到一半崩了不用从头跑** |

**两者互补，不替代。**

### 为什么这一步重要

**它是唯一把"项目产物"变成"可观赏作品"的一步。**

在此之前，一集的交付物是 `episode.master.json` —— 能被审片、能被验收、

现在 `python -m little_crew.runtime.episode_demo` 一路跑到 MP4。

### ⭐ 顺带完成的一次语义闭环

IR 的 `camera_movement`（5 种）此前**只是写给模型看的提示词**。
视频合成把它**真的变成了画面运动**：

| IR 语义 | 画面运动 | 实测首尾帧差异 |
|---|---|---|
| `static` | 固定机位 | 0.07（应为静止 ✅） |
| `dolly_in` | 推进，缩放 1.00 → 1.14 | 27.67 ✅ |
| `dolly_out` | 拉远，1.14 → 1.00 | 20.99 ✅ |
| `truck_left` / `truck_right` | 横向平移，方向相反 | 23.17 ✅ |

**这是"语义 → 执行"的一次真实闭环**：IR 里写 `dolly_in`，
画面上真的在推进 —— 而不是一句无人执行的提示词。

**自检里锁住了这个耦合**：IR 声明的每一种运镜都必须在映射表里，
否则会**静默退化成静止画面**（看起来"能出片"，只是不动）。

### 失败分类（与平台其它层一致的思路）

每种失败都带**可执行的恢复动作**，而不是一个裸报错：

| 分类 | hint |
|---|---|
| `TOOL_MISSING` | 设置 `FFMPEG_BIN` 指向 ffmpeg.exe |
| `INPUT_MISSING` | 检查成片清单里的产物路径 |
| `COMMAND_FAILED` | 看 stderr 的实际报错 |
| `TIMEOUT` | 提高超时，或降分辨率/帧率 |
| `BAD_OUTPUT` | 重跑；反复出现则查磁盘空间 |
| `UNSUPPORTED` | 换用 libx264；或换完整版 ffmpeg |

### ⚠️ 两个必须记录的坑（都极难定位）

**坑 1：ffmpeg 会永久阻塞 —— 缺 `stdin=DEVNULL`。**
ffmpeg 在非交互环境下会读标准输入；若 stdin 被继承而永不 EOF
（**后台作业、CI、被管道包住的进程**都会这样），它**永久阻塞且不产生任何输出**。
看起来就是"卡住了"。

**坑 2：测试夹具不是合法 PNG → ffmpeg 烧满 CPU 但永不结束。**
夹具曾用「PNG 魔数 + 零字节」冒充图片。ffmpeg 拿到它之后，
`scale` / `zoompan` 在退化输入上陷入**病态计算**：

```
PID 53788  已运行 187s  CPU 225.7s     ← 正常只需 3.5 秒
```

**表现是"测试卡住"，真相是"夹具不是合法输入"。**
修法是新增零依赖的 `make_test_png()` 作为公共工具。

### 已知限制

- **视频是「静图 + 运镜」，不是真动态** —— 人物不会走、不会做表情
- **无音轨** —— 需要 TTS，是另一条链
- **无转场特效** —— 镜头间是淡入淡出
- **帧率固定 24** —— 未从 `config/project.toml` 读取

### 5.8.1 先厘清一个概念：角色资产是「两层」，不是一件事

规划文档 §410 的 `bindings` 里，一个角色要装**三样**东西：

```jsonc
"CHAR-0007": {
  "anchorSet": "assets://char/CHAR-0007/anchors/v3",   // 锚点图集（图片）
  "loraFile": "linwan_v3.safetensors",                 // LoRA 权重（文件）
  "embeddingId": "emb_8f21..."                          // 嵌入（向量）
}
```

**这三样都是「图像侧资产」。** 而"角色设计"这个环节应当产出**两层**：

| 层 | 内容 | 谁产 | 本机可行性 |
|---|---|---|---|
| **文字层** | 角色的**可复现外观描述**（发型/发色/服装/体型/标志特征） | 角色设计师（LLM） | ✅ **可以** |
| **图像层** | **锚点图集**（1~3 张） | 图像生成 | ❌ **本机不行**（见 5.8.3） |

**顺序固定**：图像层需要文字层作为输入 —— 否则生成的每张锚点图之间就不一致，**锚点本身失去意义**。

> **常见误解**："我有角色资产设计" ≠ "我有锚点图"。
> 前者是**装载结构**（已有），后者是**结构里的内容**（没有）。

#### ⚠️ 曾以为找到了"第四条路"，实测**否证**（2026-10-12）

`local-gen` 的 Z-Image 支持 **img2img**（`input_image_path` + `denoising_strength`）。
设想是：用一张已生成的图当参考，低强度重绘 —— 若能产出**同一角色的不同姿态**，
就能**自举出训练集**，不需要任何外部资源。

**实测结果：锁得住角色，但产不出多样性。**

| 项 | 实测 |
|---|---|
| 机制是否可用 | ✅ 服务端确实切到 `zimage-dif` 引擎走 img2img |
| 单张耗时 | **240 / 267 / 398 秒**（`denoising_strength=0.35`） |
| 角色是否锁住 | ✅ 三张的发色/瞳色/服装/脸型一致 |
| **姿态是否变了** | ❌ **几乎没变** —— 同姿势、同构图、同表情，只有背景细节与微光不同 |
| L2 相似度 | **0.990 ~ 0.9999**（对照：真机同集不同镜均值 0.888） |

**结论**：`denoising_strength=0.35` **太保守** —— 它把构图与姿势一起锁死了。
而训练集需要的是"**同一角色的 20~30 张不同姿态**"，不是 20~30 张几乎一样的图。

#### 2026-10-16 补测：**高强度同样无效，这条路彻底否证**

上面曾留了一句"下一步把强度提到 0.55~0.75"。**那一句已被证伪，不要再去试。**
依据是 `local-gen` 自己的实测记录（`HARDWARE.md` 与 local-gen 技能文档，
比"提强度"这个设想更早、更全）：

| `denoising_strength` | 提示词要求 | 实测结果 |
|---|---|---|
| **0.40** | "坐在咖啡馆窗边、暖色光" | ❌ **构图与背景原封不动**，场景要求被完全忽略 |
| **0.70** | "全身、走在秋天街道、**侧面视角**、回头" | ⚠️ 背景变成了街道 ✓，**但仍是正面特写** —— 没有全身、没有侧面 |

**根本原因**（这才是要记的东西）：

> **img2img 锁的是「这张照片」，不是「这个角色」。**
> 构图、机位、景别、脸被绑成一个**不可拆的整体**。

它从**同一张图的潜变量**起步，所以**空间布局在结构上就被锚住了** ——
提高强度只是"重绘得更狠"，**改不了潜变量里已经固定的空间布局**。
所以强度不是杠杆，**调它没有出路**。

**零成本旁证**（项目内既有的输入/输出对，denoise 0.5，2026-10-06）：

```
i2i_input.png -> i2i_output.png
  肉眼：脸一致；衣服 纯白 -> 红白碎花；项链 银 -> 金
        但姿势、构图、机位**完全没动**
  L2 量化：similarity 0.9939 · layout 0.9996 · palette 0.9969
```

`layout 0.9996` 是决定性的 —— 对照 **构图水平移 15% 只有 0.7940**。
**构图一动没动。**

**所以：**

| | |
|---|---|
| ✅ img2img **能做** | **同机位、同景别的连续镜头**（对话正反打、同场景多句台词）；换服装 / 表情 / 背景 / 光线 |
| ❌ img2img **做不到** | 近景→全景、正面→侧面、站→走 |

**跨机位角色一致性要 i2L / IP-Adapter / LoRA**，而本机**三者都没有可用实现**
（Z-Image 无官方 IP-Adapter 权重；LoRA 训练需 22.93 GB fp32 底模 > 本机 15.8 GB 内存）。

> **真正的解法在项目里本来就有，只是分工不同** —— 见 §5.8.4 开头那句：
> **参考图锁「长相」，白模锁「空间」，二者叠加才是完整方案。**
> img2img 的错误在于**让"参考图"去兼顾"空间"**，所以两边都不彻底。
> 空间归 **ControlNet + 白模**（已跑通），长相归参考图 —— **互补，不是替代**。

> 顺带一个副产品发现：**L2 描述子对"三张几乎是同一张图"给出 0.99+**。
> 这是它该有的行为（它测的是整体一致性），但也再次说明
> **它不能替代身份度量** —— 三张连姿势都没变的图，它无法指出这一点。
> （本次 `layout 0.9996` 倒是说明：**分维比总分有用** —— 总分 0.9939 看着"很像"，
> 而 layout 维单独看才知道"构图没动"。）

## 五·九、验收门禁的实测（M5）

### 结果

```
合格产物 6 个：正确放行 6，误杀 0    -> 误杀率 0.0%
注入缺陷 8 个：拦下 8，漏放 0       -> 拦截率 100.0%
精确率 100.0%
```

样本取自**真实产物**（`outputs/episode_E100/` 的生成图，832×480）；
缺陷由 8 类真实故障注入构造。证据见 `research/review-evidence/`。

### 三层把关的落点

| 层 | 机制 | 状态 |
|---|---|---|
| **L1** | **确定性断言算子** | ✅ 10 个算子，`review/ops.py` |
| **L2** | 一致性嵌入（看跨镜漂移趋势） | ⬜ 未实现 |
| **L3** | 跨模型族盲读（生成方 ≠ 审核方） | ⚠️ 机制在 `agent/orchestrator.py`，**仍未接进门禁报告** |

### 两条反自我签收的守卫

**这是 C3 的核心，也是本项目与"模型自评"路线的根本差别。**

#### ① 缺观测 ≠ 通过

注入的 8 类缺陷里，有一条是"**观测值缺失（未测）**"，门禁判 `RETRY`。

若把"没测"当成"通过"，就等于**放行了从未被检查的约束** ——
这是自我签收的变体，而且更隐蔽：报告上看起来一切正常。

#### ② 判定不可信 ≠ 产物不合格

门禁是**三态**的，不是二态：

| 结论 | 含义 | 处置 |
|---|---|---|
| `KEEP` | 全部硬门禁通过 | 交付 |
| `RETRY` | **产物**不合格 | 带返工指令回去重做 |
| `ESCALATE` | **判定本身不可信** | 升级人工 —— **不给返工指令** |

实测：约束引用未知算子 -> `ESCALATE`（而非 `RETRY`）。

合并后两者的后果：判定不可信时也去返工 -> 白烧算力且下次依然不可信；
产物不合格时去叫人 -> 人被迫做机器能做的事。

**`ESCALATE` 优先于 `RETRY`** —— 连结论都不该信时，更不该拿它驱动返工。

### ⚠️ 实现过程中犯的一个错（记录，因为它正是 C3 要消灭的模式）

第一版里，约束引用未知算子时 `evaluate_one` 返回 `None`，
于是该约束**从报告里彻底消失** —— 一份"4 条约束"的报告只列出 3 条，
而缺的那条恰是**没被检查**的那条。

> **C3 要消灭的模式，出现在了 C3 自己的实现里。**

已修：无法判定的约束**仍产出断言记录**，标注 `evaluated: False` 与原因。
自检里加了 `E6/E7` 两条断言锁住它。

### 一次夹具错误（记录以免重犯）

第一版测量报出 **50% 误杀率**。**那是夹具的错，不是门禁的错。**

我把分辨率不同的对照拼图（1050×230 等）也当成"合格产物"，
再喂给一条要求 832×480 的约束 —— **门禁拦它完全正确**。

> **门禁的职责是「按声明的规格判定」，它不该猜哪张图算合格。**
> 基准由调用方给，给错了是调用方的错。

### 已接进流水线（2026-10-12 补充）

门禁从"独立可调用的判定层"变成**流水线的一环**：渲染后、合成前判定，
结论进交付证据链，且 **`ok` 会因门禁而变 `False`**。

**真机实测（ComfyUI + 白模控制，3 镜）**：

```
门禁计数: {'shots': 3, 'kept': 3, 'retry': 0, 'escalate': 0, 'skipped': 3}
具备的观测能力: ['bytes', 'characterCount', 'height', 'name',
                'plannedDurationSec', 'width']

逐镜裁定:
  SH-E100-001-001  KEEP  [v] cr_res_…   resolution_matches  {width:832, height:480}
                         [v] cr_cast_…  count_at_most        {characterCount:2, max:3}
```

**分辨率是真的量出来的** —— 从 `{文件名: bytes}` 里的**内存字节**解析 PNG 头，
而不是读产物引用上的字段（那些字段实测为空）。

#### 为什么"接进去"比看起来难：一个反复出现的静默失效

接入过程中，**同一个失效模式现身了两次**：

| 次 | 原因 | 症状 |
|---|---|---|
| 1 | 观测提取只按 `ArtifactRef` 对象读 | 引用上的 `width`/`bytes` 为空 → 分辨率类约束**全部被跳过** |
| 2 | `_run_gate` 用 `list(o.artifacts)` 只取了**键** | `CacheOutcome.artifacts` 是 `{名字: bytes}`，取键就丢了字节 → 同样的症状 |

**共同点：没有任何一处报错。** 门禁看起来接了、报告看起来正常、`ok=True` ——
但它实际上**一条约束都没检查**。

唯一能抓到它的是"断言它**确实执行了**"的测试（`G3` / `G14`）。
这也是本项目反复出现的那个模式的又一例：
**凡是"本地看不出、跑起来也不报错"的缺陷，只能靠"断言机制真的生效"来抓。**

#### 约束的强制级别：算子实现了，就该升 hard

| 约束 | 级别 | 理由 |
|---|---|---|
| 分辨率 / 时长 / 角色数 | **hard** | 确定性能判，且不满足确实不该出片 |
| 身份相似度 | **soft** | 本机没有人脸/嵌入模型，**算不出来**；标 hard 会让每镜都升级人工 |

早期把所有约束标 `soft`，理由是"断言算子未实现" —— 现在算子已实现（10 个），
**继续标 soft 就是自己放弃了门禁的阻断能力**。

### 5.9.3 L2 一致性嵌入：能做与不能做

**结论先写**：它是一个**粗粒度一致性描述子**，不是身份度量。
正因如此，它的强制级别是 **`audit`**（如实记录，不阻断）——
这个决定有实测依据，不是保守。

#### 之前的状态

`ops.py` 里有 `identity_similarity` 与 `pairwise_similarity` 两条算子，
它们只负责**比阈值**，文档写明"相似度由谁算是调用方的事"。

**而那个"调用方"此前不存在。** 于是本机实测里这两条约束
**永远被判"缺观测 similarity"而跳过** —— 跨镜角色一致性**没有任何度量手段**。

#### 四维正交分解

| 维度 | 负责 | 返工方向 |
|---|---|---|
| `palette` | 色相分布（色彩的"身份"） | 改风格/提示词配色 |
| `layout` | 8×8 网格亮度布局（构图） | 改机位/构图 |
| `lighting` | 明度分布（曝光） | 改打光参数 |
| `richness` | 饱和度分布（色彩浓度） | 改饱和度/风格强度 |

**为什么要拆四维**：门禁要回答"**是哪一维不一致**"，那直接决定返工方向。
答错方向等于白跑一轮返工。

**受控退化实验（12 项）归因 12/12 正确**：

| 退化 | 最弱维 | 退化 | 最弱维 |
|---|---|---|---|
| 色相 +10/25/60° | `palette` | 去饱和 0.5 / 0.9 | `richness` |
| 亮度 ×1.15 / ×1.40 | `lighting` | 构图移 5% / 15% | `layout` |
| 局部崩坏 10% / 30% | `palette` | 基准 | 全为 1.000 |

#### ⚠️ 它**不能**判身份 —— 这是硬的边界

| 数据集 | 观测区间 |
|---|---|
| **同一集、同一管线**（9 张真实产出） | **0.80 ~ 1.00**（均值 0.888） |
| 跨批次混比（34 张） | 0.66 ~ 1.00（均值 0.833） |

**关键事实**：同一角色在**不同构图**下就落到 0.66，
而**完全不同的场景**也在同一区间。两者**重叠** ——
所以**没有任何阈值**能把"角色漂移"与"换了景别"分开。

**中心裁剪试过了，没用**：

| 取区 | 均值 | 最低 |
|---|---|---|
| 整帧 | 0.6165 | 0.3592 |
| 中心 60% | 0.6003 | 0.3917 |
| 中心 40% | 0.5848 | 0.4005 |

裁剪几乎不动 —— 说明**不是背景淹没**，而是"整图统计量"
这个度量本身答不了"是不是同一个角色"。

**所以它测的是「整体像不像同一场戏」。**

#### 为什么标 `audit` 而不是 `hard`

| 阶段 | 级别 | 理由 |
|---|---|---|
| L2 之前 | `soft` | 算子未实现，标什么级别都无代价 |
| L2 之后（第一版） | `soft` | 能算了，但不该阻断 |
| **定稿** | **`audit`** | 能算，**但测的不是身份** —— "不合格"这个结论不成立 |

**明确不做的事**：不把它改标 `hard` 来"显得门禁更严"。
那样做的后果是**每一镜都被判不合格**，而真正的问题是**度量能力不足**——
**把能力缺失伪装成"发现了缺陷"，比不做度量更糟。**

阈值取 **0.70**：同集同管线的真实分布最低是 **0.801**，
所以正常变化不会误报；灾难性退化（局部崩坏 30% → 0.78）会告警。
**它是告警线，不是通过线。**

#### 一次真实的方法学修正

最初用**直方图交集**，它在受控退化下暴露了严重缺陷：

| 画面 | 饱和度直方图 | 交集 |
|---|---|---|
| 原图 | `[0,0,0,1,0]`（全在桶 3） | — |
| 轻度去饱和 | `[0,0,0,1,0]` 或 `[0,0,1,0,0]` | 0 或 1 |
| 重度去饱和 | `[1,0,0,0,0]`（全在桶 0） | **0.00** |

**两幅"中等程度不同"的图被判成 0 相似度**，而"完全一样"的是 1 ——
中间没有过渡。因为真实图像的统计量高度集中，微小数值平移就跨过桶边界。

改用 **EMD（推土机距离）** 后，分布**平移**只产生小的距离，
只有分布**形状真的变了**才会拉开 —— 12 项归因才全部成立。

> **教训**：直方图比较里"交集"是常见做法，但它隐含假设
> 「桶是独立类别」。对**有序**统计量（色相/明度/饱和度都有序），
> 那个假设是错的 —— 该用知道"相邻桶很近"的距离度量。

#### 仍未做的部分

| 项 | 现状 |
|---|---|
| **阈值未在缺陷集上验证** | ⚠️ 0.70 来自"正常分布的下界"，**不是**"缺陷分布的上界" |
| **不参与返工闭环** | ⚠️ `audit` 级不阻断，也就不触发返工 |
| **只支持 PNG** | ⚠️ 其它格式走 `consistencyUnavailable` |
| **判身份** | ⚠️ 需人脸/身份嵌入模型，本机没有 |

### 5.9.2 返工闭环：门禁从「报告」变成「机制」

**链路**：

```
渲染 -> 门禁判 RETRY -> 有可应用的动作 -> 改 IR -> 只重跑那几镜 -> 复检
                        ^                                        |
                        +---------- 最多 max_repair_rounds 轮 ----+
```

**实测**（自检 H1）：

```
首轮：门禁判 RETRY（分辨率 32x24 != 要求 64x48）
      -> 返工动作 ir.set_params(n_latent, {width:64, height:48})
      -> **只有那一镜**重跑（提交 3 次 = 首跑 2 镜 + 重跑 1 镜）
      -> 复检 KEEP
结果：ok=True
```

> **门禁原本"知道哪里错了"但"不知道该改什么"** ——
> 它产出的是给人看的句子，机器读不懂。
> 所以缺的不是判定，而是**可执行的修正**。

#### 为什么两种表达都要

| 只有句子 | 只有动作 |
|---|---|
| 循环没法执行 | 报告读不懂，人无法判断该不该接受 |

所以每个失败断言同时产出 `repairs`（句子，进报告）与
`repair_actions`（结构化，进循环）。

#### 只有 3 类约束可自动修（如实标注）

| 可自动修 | 不可自动修（附原因） |
|---|---|
| 分辨率 `ir.set_params` | **削减角色** —— 创作决策（删谁/合镜/拆镜），不该由规则做 |
| 宽高比 `ir.set_params` | **身份相似度** —— 需锚点图或 IPAdapter 权重，本机都没有 |
| 时长 `shot.set_duration` | **文本差异** —— 需按剧本原文重写，属生成决策 |
| | **文件过小** —— 需查编码链路，不是参数问题 |

**"不可应用"必须如实标记**：假装可修会让循环白跑 N 次然后失败，
而真正的问题是**能力缺失**。

#### 三道防烧 GPU 的闸

| 闸 | 作用 |
|---|---|
| `max_repair_rounds` | 硬上限。没有它，门禁不退让就会无限重跑 |
| `repairable_shots()` | 动作**全不可应用**的镜头不重跑 —— 跑了也是同一张图 |
| **IR 哈希必须变** | 没变就是命中缓存，重跑等于空转 |

**第二道最有价值**：实测 `count_at_most(max=0)` 这种"能算但修不了"的约束，
循环**明说**"没有可应用的动作（能力缺失，不是参数问题）—— 不重跑，如实上报"，
而不是白跑三轮。

#### 三条铁律

| # | 铁律 | 理由 |
|---|---|---|
| 1 | 动作**必须改变 IR 的哈希** | 否则重跑命中缓存拿回同一张图，循环空转 |
| 2 | 修不了的**如实标记** | 假装可修 = 白烧算力，且掩盖真正的能力缺失 |
| 3 | 动作是**对 IR 的编辑**，不是对图的编辑 | 平台的可复现性建立在"IR 是唯一真相"上；改图会绕开哈希链 |

#### 仍未做的部分

| 项 | 现状 |
|---|---|
| **不可自动修时不升级人工** | ⚠️ 只如实报 RETRY；接进 `agent` 的升级流程是下一步 |
| **返工不回退到分镜层** | ⚠️ 只重跑渲染；若缺陷在分镜（如角色数超限），当前不会回退 |
| **没有"修完仍不过"的二次升级** | ⚠️ 上限用尽后停在 RETRY |
| **返工次数不成本核算** | ⚠️ 未计入 `secondsSaved` / 成本报告 |

### 已知限制

| 项 | 现状 |
|---|---|
| **相似度类算子** | ✅ **已参与测量**（alpha.27 的 L2）。但它是**粗粒度一致性描述子，不是身份度量** —— 同角色不同构图与不同场景的分数区间**重叠**，见 §5.9.3。因此只标 `audit`，不阻断 |
| 缺陷样本量 | 8 类。足以证明"能拦"，**不足以给出统计置信区间** |
| **返工闭环已闭合** | ✅ 门禁判 RETRY -> 改 IR -> **只重跑那几镜** -> 复检（见下方 §5.9.2）。**但只有 3 类约束可自动修**，其余动作如实标为不可应用 |
| **`duration_within` 在图像阶段恒被跳过** | ⚠️ 图像没有时长 —— 该约束要到视频阶段才可判定。**被显式记录**为跳过，不是静默通过 |
| **`engine_resolution` 必须与实际产出一致** | ⚠️ 不一致会让**每一镜都被判不合格**（实测：夹具产 64x48 而约束写 832x480 → 12 镜全 RETRY）。门禁没错，是约束没反映真实规格 |

> **但空间维度不需要它** —— 白模 + ControlNet 已经跑通（§5.8.4 的 P3 实测：
> 相对基线 MAE **35.6 / 37.5 / 37.8**，阈值 8）。
> **「锁长相」这一半缺，不代表「锁空间」那一半也缺。**

## 六、本机硬件约束（决定全部设计取舍）

**实测环境**：RTX 4060 Laptop **8 GB 显存** · **15.8 GB 内存**

| 约束 | 实测事实 | 对设计的影响 |
|---|---|---|
| **内存是真正瓶颈** | 15.8 GB（不是显存） | Z-Image fp32 底模需 22.93 GB → **无法训练角色 LoRA** → **一致性必须参考图优先** |
| **H3 视频硬上限 10 秒** | 12 秒必 OOM，**降分辨率无效**（瓶颈是注意力序列长度） | 分镜时长上限硬约束 |
| **同时只能加载一个模型** | 8 GB 显存 | **GPU 必须按模型分批调度** |
| **单集耗时 4–7.5 小时** | 60 镜 | **瓶颈是时间不是钱** → 缓存与断点续跑是必需品不是优化 |
| **现金成本 ≈ ¥5/集** | 本地电费 | 云端 API 的价值在**时间**而非成本 |

**这些约束不是限制，而是本项目的差异化来源** ——
在 8 GB 笔记本上跑通的方案，在强显卡上只会更快；
反之则不成立。

## 七、风险与应对

| # | 风险 | 影响 | 应对 |
|---|---|---|---|
| **R-1** | **Transformer 三模块训练数据不足** | C2 创新点无法兑现 | ① 影子模式冷启动 ② **降级叙事预案**（改为"协议设计+规则基线实现"）③ 提前评估数据构造可行性 |
| **R-2** | **18 个职位工作量过大** | 协作层不完整 | ① 先做 5 个核心职位打通最短链路 ② 其余按需补 ③ **结构化协议已先行完成**，后期成本已降低 |
| **R-3** | **单集渲染时间超预算** | 无法产出足够实验数据 | ① 三级缓存 ② 草稿档（480×704/4 步）③ 断点续跑 |
| **R-4** | **一致性效果不达门禁** | 产出不合格 | ① 降级链 + 阈值联动已是既有机制 ② 参考图 + ControlNet 多重锁定 ③ 门禁阈值可由 `TaskProfile` 按阶段调整 |
| **R-5** | **模型授权变更** | 合规风险 | 授权事实集中在 `LICENSE_CATALOG`，单点维护；门禁"未核实即拒绝" |
| **R-6** | **ComfyUI 版本升级破坏兼容** | 编译失效 | ① 能力矩阵 + 漂移检测 ② 环境快照入库，可离线回归 ③ 规则表与节点名解耦 |
| **R-7** | **8 GB 显存跑不动 H3 `int8_convrot`** | **白模驱动的生成路线在本地不成立** | ① 先验（P1 不依赖该下载，可独立推进）② 退回 2D 控制（`Depth` + `Layout`）③ 或走云端 API |
| **R-8** | **白模灰度不能作为 `Gray` 控制** | 白模只剩 `Depth` 一条路 | ① 同时输出 Gray 与 Depth，互为备份 ② 官方样片已证 `Depth` 有效 |
| **R-9** | **白模质量不足以支撑控制** | 生成结果变差 | ① 参数化代理先做最小版本，实测后再决定精细度 ② `control_context_scale` 可调，可减弱约束 |
| **R-10** | **3D 路线投入挤占核心创新点时间** | 主线交付风险 | **P1 与主线并行**（P1 只需 CPU，不占 GPU）；**P3 单独成阶段**，不与主线耦合 |

## 九、项目特色与创新性总结

| # | 特色 | 与现有工作的差异 |
|---|---|---|
| **1** | **统一 IR 与双层同构 DAG** | 现有项目只能表达语义图**或**执行图；本平台让二者共享同一份可编译、可校验、可回溯的表示。**`constraint` 边是可执行断言而非注释** |
| **2** | **多智能体协作不依赖编排框架** | 用三原语 + 四条层边界硬规则取代图编排框架；解决"两个正交轴被同一抽象压扁"的根本问题 |
| **3** | **降级链 + 显式降级通知** | 与"模板填充"式集成的分水岭：能力不足时告知"能力变弱了、阈值已放宽、建议装什么"，而非静默产错图 |
| **4** | **确定性验收门禁** | 生成方与审核方**物理隔离**（跨模型族盲读）；`review` 不做生成，`runtime` 不做判定 |
| **5** | **模型双通道正交抽象** | 本地与云端 API 统一为"同一种通道的两个 endpoint"；加模型不改通道，加通道不改模型 |
| **6** | **把合规变成代码** | 授权不是文档约定而是硬门禁；三条强制行为（未核实即拒绝 / 降级每跳重过 / 标注自动注入） |
| **7** | **机器强制的架构纪律** | 依赖方向由测试守卫；规则表契约由双校验器守卫 —— **功能测试永远发现不了架构退化** |
| **8** | **零第三方依赖的核心层** | 6 个核心包运行期与测试期零依赖，可独立测试与发布 |
| **9** | **以剧组职业组织智能体** | Agent 不是抽象编号而是**真实剧组职位**（导演/编剧/美术指导/摄影指导/场记…）。职责边界沿用真实剧组几百年打磨的分工，比自创更不易出现重叠或真空 |
| **10** | **白模作为「确定性渲染步骤」而非 IR 中的 3D 树** | 与"在 IR 里加一棵场景树"的常规做法相反：白模是**声明式输入 → 确定性渲染 → 可哈希产物**，因而可缓存、可复现，且 IR 改动极小（见 §3.8.1） |

### 9.1 与现有工作的边界（诚实标注）

本节的存在是为了**避免夸大**。以下工作已覆盖了本项目的部分方向，
本项目的差异化在于**组合方式**与**约束条件下的工程实证**：

| 现有工作 | 它做了什么 | 与本项目的关系 |
|---|---|---|
| [**StoryBlender**](https://arxiv.org/abs/2604.03315)（ECCV 2026） | 3D 分镜生成框架，**跨镜一致 + 可编辑**，多智能体分层编排 + 验证循环 | ⚠️ **方向重叠最重**。其"连续性记忆图解耦全局资产与镜头局部变量"与本平台的 `bindings` 同构。**本课题不以 3D 分镜生成为创新点** |
| [**鲲鹏导演台**](https://github.com/pengfeiqiao/kunpeng-director)（MIT） | 3D 白模预演 + **Agent 操作**（15 个 MCP 工具）+ 人工锁定 | ✅ **互补**。它产出"给人看的白模 MP4"，**不驱动扩散模型**；本平台取其模板库（MIT 合规）用于控制序列生成 |
| [**AI Renderer 2.0**](https://mickmumpitz.ai/posts/new-video-free-2-151633267) | Blender 深度/边缘通道 → 视频模型（已发布工作流） | ✅ **验证了机制可行**。本平台不重复发明该机制，而是把它**纳入可编排、可缓存、可验收的编译管线** |
| [**Vibe3DScene**](https://github.com/3DSceneAgent/Vibe3DScene) | Blender 作独立运行时（`local-client` / `headless` 两种模式） | ✅ **架构参照**。本平台的 Blender 通道采用其 `headless` 模式的思路 |
| **ComfyUI-BlenderAI-node** | ComfyUI ↔ Blender 双向集成（维护两年） | 与本平台是**不同层次**：它是节点级桥接，本平台是编译与编排层 |

**本项目真正未被覆盖的是**：

> **在 8 GB 显存 / 15.8 GB 内存的消费级设备约束下，把长视频生产跑通**
> —— 含实测的降级链、跨模型族验收门禁、以及"改一句只重跑受影响镜头"的成本证据。

StoryBlender 是云端的；AI Renderer 假设硬件充足。
**边缘约束下的工程实证是空白的**，而这恰好是本项目的实测数据能给的东西。

## 十、结论

AIGC 漫剧生产的结构性瓶颈在 **P2 编排粒度错配** ——
创意决策与扩散执行之间缺少共享表示。本项目以**统一 IR** 架起这座桥，
以**多智能体协作**在桥上完成决策、质疑与裁决，以 **ComfyUI** 作为执行底座，
以**确定性验收门禁**保证产出质量，
以 **3D 白模**补上纯 2D 方案无法覆盖的**空间与机位一致性**。

截至 `0.4.0-alpha.4`，项目已完成：

| 成果 | 证据 |
|---|---|
| **统一 IR + 六个核心层** | 22,282 行，**806 项测试通过** |
| **端到端真机验证** | 从 IR 到真实出图全链路 **18/18**（ComfyUI 0.39.0 / 970 节点） |
| **架构纪律机器化** | 依赖守卫 + 规则表双校验器 —— **功能测试发现不了架构退化** |
| **协作层成型** | 18 个剧组职位名册 + 结构化消息协议 + 服务端权威算分 |

**下一步聚焦三个价值命题**：

| # | 命题 | 阶段 |
|---|---|---|
| **1** | "只重跑受影响的镜头" —— 成本可控 | R9 |
| **2** | "证明图满足断言" —— 验收有效 | R10 / R12 |
| **0** | ~~"只重跑受影响的镜头" —— 成本可控~~ | ✅ **已达成**（§5.5 实测） |
| **3** | "机位与站位按预期跟随" —— 空间可控 | P1 → P3 |

并以 **5 个核心职位打通最短链路**，产出一集完整成片与实测数据。

**本项目的差异化不在"发明了 3D 驱动视频"**（该机制已由
[AI Renderer 2.0](https://mickmumpitz.ai/posts/new-video-free-2-151633267) 等工作验证），
**而在于把这条链路纳入可编排、可缓存、可验收的编译管线，
并在 8 GB 显存 / 15.8 GB 内存的消费级约束下给出实测证据。**
