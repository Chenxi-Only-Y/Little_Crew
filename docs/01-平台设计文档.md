## 第 1 章 选题定位与创新性论证

### 1.1 问题陈述

AIGC 漫剧（动画短剧）生产面临四个结构性困难：

| 编号 | 困难 | 本质 |
|---|---|---|
| **P1** | **长程一致性崩塌** | 一集 60–120 镜，角色脸、服装、场景、色调在各镜之间漂移；扩散模型无跨镜记忆 |
| **P2** | **编排粒度错配** | 创意决策（剧本/分镜/运镜）是**语义级**的；扩散执行是**张量级**的。两者之间没有共享表示，导致"人话"到"节点图"的翻译损耗 |
| **P3** | **验收自证** | 出图的模型自己说"这张没问题"，错误逐帧累积且无人拦截 |
| **P4** | **成本与重跑失控** | 单集数百次 GPU 生成，任一参数微调导致全量重跑；中断即从头再来 |

现有开源方案各自解决了其中 1–2 条，但没有方案同时回答四条。

### 1.3 空白点的形式化表述

设平台能力空间为三个维度的笛卡尔积：

- **V** = 可视化节点编排（Visual node orchestration）
- **A** = 智能体原生执行（Agent-native execution）
- **C** = ComfyUI 作为执行引擎（ComfyUI as execution engine）

则现有工作分布为：

```
TapCanvas, wind-comic, novella   ∈  V × A × ¬C
NiliX, kt-ai-Studio, auto-drama  ∈ ¬V × ¬A × C
Novel-Director                   ∈  V × ¬A × C   （手搭图，无 Agent 编排）
────────────────────────────────────────────────
本课题                            ∈  V × A × C   ← 空集
```

**核心创新点（C1）**：在 V × A × C 空间内，提出**双层同构 DAG + 统一 IR**，使语义图与执行图共享同一中间表示。这一构造在现有开源生态中不存在。

### 1.4 三个创新点

| 编号 | 创新点 | 解决 | 可量化指标 |
|---|---|---|---|
| **C1** | **双层同构 DAG + 统一 IR**：语义层（角色/镜头/连续性约束）与执行层（ComfyUI 节点图）编译自同一 IR，支持双向映射与约束回传 | P2 | 编译成功率、约束保留率、编译耗时 |
| **C2** | **自研 Transformer 调度智能体**：以图状态为输入的策略网络，学习"何时分支/重试/换引擎/分配预算"，替代 LLM 逐步决策 | P1, P4 | 任务成功率、重跑率、单集成本、决策延迟 |
| **C3** | **确定性验收门禁（不自我签收）**：产出模型不得自证；跨模型盲读 + 确定性算子 diff + 硬门禁阻断 | P3 | 缺陷漏检率、误杀率、人工介入率 |

**辅助机制（非创新点，但是能跑通一集的生死线）**：内容寻址缓存、渲染检查点、节点幂等与租约、产物时效清单、断点续跑。

### 2.1 七层架构

```
┌─────────────────────────────────────────────────────────────────────┐
│ L7  交互层   无限画布 · 分镜编辑器 · 导演台 · Agent 对话 · 审片工作台   │
├─────────────────────────────────────────────────────────────────────┤
│ L6  编排层   StoryGraph（语义 DAG）· 黑板 · 任务租约 · 调度器          │
│              └─ 自研 Transformer Scheduler（C2）                     │
├─────────────────────────────────────────────────────────────────────┤
│ L5  智能体层 18 个专业 Agent · AgentRegistry · 结构化消息协议          │
│              └─ Consistency Embedder / Light Verifier（C2）          │
├─────────────────────────────────────────────────────────────────────┤
│ L4  契约层   Unified IR（C1）· 跨阶段契约 · Schema 注册表 · 版本迁移   │
├─────────────────────────────────────────────────────────────────────┤
│ L3  编译层   IR → ComfyUI Prompt Graph 编译器                         │
│              能力矩阵探测 · 漂移检测 · 降级策略 · 图哈希版本管理        │
├─────────────────────────────────────────────────────────────────────┤
│ L2  执行层   ComfyUI 进程托管 · 队列/租约 · 缓存 · 检查点 · GPU 调度    │
├─────────────────────────────────────────────────────────────────────┤
│ L1  验收层   确定性门禁（C3）· 质量评分 · 返工闭环 · 交付证据链         │
└─────────────────────────────────────────────────────────────────────┘
```

### 2.2 主数据流

```
用户输入（一句话/小说/剧本）
   │
   ▼
[L6] StoryGraph 构建 ──► 语义节点：角色·场景·镜头·连续性约束
   │
   ├──► [L5] 智能体协作（黑板读写 + 审查循环）
   │        剧本Agent ⇄ 剧评Agent ⇄ 风格Agent
   │        角色设计 ⇄ 场景设计 ⇄ 道具设计 ⇄ 一致性审查
   │        分镜构建 ⇄ 节奏导演 ⇄ 连续性检查
   │
   ▼
[L4] Unified IR 序列化（唯一真相源，带内容哈希）
   │
   ▼
[L3] 编译：IR → ComfyUI Prompt Graph（按镜头粒度编译）
   │        ├─ 能力矩阵校验（/object_info）
   │        ├─ 节点缺失/端口变更 → 降级或阻断
   │        └─ 图哈希 → 缓存键
   │
   ▼
[L2] 执行：POST /prompt → WebSocket 进度 → /history 回收
   │        ├─ 条件指纹命中 → 直接复用
   │        └─ prompt_id 落盘 → 崩溃续跑
   │
   ▼
[L1] 验收门禁
   │        ├─ 硬门禁：确定性算子（token-diff / 帧数 / 时间码 / 人脸相似度）
   │        ├─ 软门禁：跨模型盲读（生成者 ≠ 审核者）
   │        └─ KEEP → 落库 ｜ RETRY → 带修复注记回 L6 ｜ 超限 → 人工升级
   │
   ▼
成片（FFmpeg 合成）+ 交付证据链 + 成本报告
   │
   └──► 回写黑板 → 更新语义图状态 → 下一镜
```

### 2.3 与现有架构的关键差异

| 维度 | TapCanvas / wind-comic | NiliX / kt-ai-Studio | **本平台** |
|---|---|---|---|
| 编排对象 | 业务阶段（固定管线） | 工作流模板（固定 JSON） | **语义 DAG + 统一 IR** |
| ComfyUI 角色 | 无 / 引擎之一 | 执行后端，参数注入 | **IR 的编译目标（图级映射）** |
| 新增能力成本 | 改代码 | 改模板节点 ID | **改 IR 节点类型 + 编译规则** |
| 节点版本漂移 | 不适用 | **直接失效** | **探测 + 降级 + 显式告警** |
| 一致性 | 提示词 + 资产库 | 指纹 + 时效清单 | **向量嵌入 + 契约校验 + 时效清单** |
| 验收 | VLM 自评 | VLM 打分（加权在外部算） | **确定性算子 + 跨模型盲读 + 硬门禁** |

## 第 3 章 统一中间表示（Unified IR）

> 本章是全文技术核心。IR 必须同时满足：① 能表达"这个镜头要保证角色 A 的服装连续性"这种**语义约束**；② 能无损编译成 ComfyUI 可执行的 prompt graph；③ 编译失败时能把**降级原因回传到语义层**。

### 3.1 设计目标（取舍声明）

| 目标 | 决策 | 理由 |
|---|---|---|
| 图灵完备性 | **不追求**。IR 是有向无环、类型化、非图灵完备的 | 可静态校验；可确定性编译；可哈希缓存 |
| 控制流 | 只允许 **条件分支**（selector 节点）与 **映射**（map 节点，表达"对每个镜头做 X"） | 覆盖漫剧全部需求；保留可分析性 |
| 副作用 | 节点声明 `sideEffect` + `idempotency`，由运行时统一裁决 | 直接借用 TapCanvas 的 execution-semantics/v2 设计 |
| 语义与执行同构 | **同构但不相同**：同一 IR 有 `semanticView` 与 `execView` 两个投影 | 语义层含循环/批处理，执行层须展开为静态图 |

### 3.2 三层映射

```
① 语义图 SemanticGraph    人/Agent 读写。节点粒度 = 剧作概念
        │  compile()
        ▼
② 统一 IR  UnifiedIR      唯一真相源。节点粒度 = 计算算子 + 语义约束挂载点
        │  lower()
        ▼
③ 执行图 ExecutionGraph   ComfyUI API 格式（dict[nodeId → {class_type, inputs}]）
        │  POST /prompt
        ▼
   ComfyUI 运行时（惰性求值 + 节点级输出缓存）
```

**回传方向**：执行图的 `outputs` → IR 的 `ArtifactRef` → 语义图的 `shot.artifact` → 黑板。同时执行期的降级事件（节点缺失、精度回退、引擎切换）以 `DegradationNotice` 挂到 IR 对应节点，**语义层可见**。

### 3.3 IR 形式定义

#### 3.3.1 图

```jsonc
{
  "irVersion": "little_crew.ir/v1",          // 协议版本，参与缓存键
  "graphId": "G-ep001-sh042",
  "scope": "shot",                      // project | episode | scene | shot
  "nodes": [ /* IRNode[] */ ],
  "edges": [ /* IREdge[] */ ],
  "constraints": [ /* Constraint[]  语义层专属，执行层忽略但校验 */ ],
  "bindings": { /* 资产引用：角色锚点/场景卡/LoRA */ },
  "provenance": {                       // 可回溯
    "parentGraphId": "G-ep001",
    "authorAgent": "storyboard.shot_composer",
    "authorAgentVersion": "1.4.2",
    "createdAt": "2026-10-11T10:20:00+08:00",
    "contentHash": "sha256:..."          // 规范化序列化后哈希
  }
}
```

#### 3.3.2 节点

```jsonc
{
  "id": "n_prompt_pos",
  "kind": "prompt.text",               // 命名空间化类型，决定编译规则
  "inputs": {                          // 静态值 或 端口引用
    "text": { "ref": "n_script_beat", "port": "line" }
  },
  "outputs": { "text": { "dtype": "STRING" } },
  "execution": {                       // 借自 execution-semantics/v2 思路
    "sideEffect": "pure",              // pure | read | write | external
    "idempotency": { "source": "runtime_node", "inputField": null },
    "resultLookup": { "mode": "none", "outputField": null },
    "recoveryMode": "replay",          // replay | reconcile | manual
    "maxAutomaticAttempts": 3,
    "backoffClass": "bounded_exponential",
    "failureStage": "media_generation"
  },
  "semantic": {                        // 语义挂载点：执行层忽略，语义层/门禁用
    "characterRef": "CHAR-0007",
    "constraintRefs": ["cr_costume_007", "cr_face_007"],
    "intent": "锁定角色A的服装与面部特征"
  },
  "meta": { "title": "正向提示词", "ui": { "x": 120, "y": 340 } }
}
```

#### 3.3.3 边（两条独立子类型）

```jsonc
// 数据边（编译为 ComfyUI 的 [nodeId, outputIndex] 连接）
{ "id": "e1", "type": "data", "from": {"node":"n_prompt_pos","port":"text"},
  "to": {"node":"n_ksampler","port":"positive"}, "dtype": "CONDITIONING" }

// 约束边（不编译，用于门禁与一致性校验）
{ "id": "e2", "type": "constraint", "from": {"node":"n_ref_img","port":"image"},
  "to": {"node":"n_ksampler","port":"latent"},
  "assertion": { "op": "identity_similarity", "threshold": 0.82,
                 "against": "CHAR-0007.anchor_set" },
  "enforcement": "hard" }              // hard=阻断 | soft=告警 | audit=仅记录
```

> **关键设计**：约束边是 IR 区别于普通工作流 JSON 的本质。它把"这个镜头必须长得像角色 7"从一个**提示词里的一句话**变成一条**可执行断言**，从而可被自动验收。

### 3.4 规范化与哈希（缓存基础）

编译前对 IR 做**确定性规范化**，保证"语义等价 ⇒ 哈希相同"：

1. 节点按 `id` 字典序排序；边按 `(from, to, port)` 三元组排序
2. 剔除 `meta.ui`（坐标）、`provenance.createdAt`、任务 ID/租约等**非语义字段**
3. 浮点数量化到声明精度（如 CFG 保留 2 位、strength 保留 3 位）
4. 默认值补全（缺省字段写入其 schema 默认值，避免"省略 vs 显式"哈希不同）
5. 递归解析端口引用链，形成**规范表达式串**
6. 排除**运行期随机源**：seed 由 `deriveSeed(projectSeed, episodeIdx, sceneIdx, shotIdx, attempt)` 确定性推导，不进哈希

```
contentHash = sha256( canonicalJson( normalizedIR ) )
```

`contentHash` 同时是缓存键、产物时效清单的指纹项、复现实验的锚点。

```jsonc
    {
      "kind": "prompt.negative",
      "target": { "classTypes": ["CLIPTextEncode"] },
      "portMap": { "text": "text", "clip": "clip" }
    },
    {
      "kind": "identity.lora",
```

**编译算法**（伪代码）：

```
function compile(ir, capabilityMatrix):
    rules = loadRules(COMPILE_RULE_VERSION)
    out   = {}                    # API 格式 prompt graph
    notices = []

    for node in topoSort(ir.nodes):
        rule = rules[node.kind]
        if rule is null: return CompileError(UNKNOWN_KIND, node.id)

        cls = selectClassType(rule, capabilityMatrix)      # 优先 preferred，按序候选
        if cls is null:
            if rule.required: return CompileError(MISSING_REQUIRED_NODE, node.kind)
            cls = selectClassType(rules[rule.degradeTo], capabilityMatrix)
            if cls is null:
                notices += DegradationNotice(node.id, SKIPPED_OPTIONAL)
                continue
            notices += DegradationNotice(node.id, DEGRADED, rule.degradeTo)

        inputs = {}
        for (irPort, cType) in rule.portMap:
            src = resolveInput(ir, node, irPort)
            inputs[cType] = (src is portRef) ? [src.node, outputIndexOf(src)]
                                             : materialize(src, rule, capabilityMatrix)
        inputs += defaultsFor(cls, capabilityMatrix)        # 缺省 widget 值补全
        out[node.id] = { class_type: cls, inputs: inputs,
                         _meta: { title: node.meta.title, irNodeId: node.id } }

    assertNoDanglingRefs(out)
    return CompileResult(graph=out, notices=notices, graphHash=sha256(canonical(out)))
```

### 3.7 反向编译（执行 → IR）

用途：① 用户手搭 ComfyUI 图后导入平台；② 从 ComfyUI history 回收产物时重建 IR 挂载。

```
ExecutionGraph ──analyze──► IR
  1. 从 outputs 反查消费链（哪个节点最终产出 IMAGE / VIDEO）
  2. 按 class_type 反查 compileRules → kind（多候选时取端口签名最匹配者）
  3. 未识别的 class_type → 生成 kind: "opaque.custom"，保留原始参数，
     标记 semantic: { opaque: true }（不参与语义校验，但参与缓存与执行）
  4. 无对应约束边的镜头自动补 constraint 桩，enforcement: "audit"
```

**局限性声明**：反向编译是**有损**的——原始语义意图（为什么这么写提示词）无法从图里恢复。因此反向编译仅用于导入与产物回收，不作为主流程。

### 3.8 IR 版本演进

| 变更类型 | 处理 |
|---|---|
| 新增可选字段 / 新增 kind | **兼容**。`irVersion` 次版本号 +1；旧图直接编译 |
| 字段语义变更 / 删除 kind | **不兼容**。主版本号 +1；提供 `migrate_ir(vN → vN+1)` 纯函数迁移器 |
| 编译规则变更 | `ruleVersion` 参与缓存键；规则升级自动使旧缓存失效 |

> **一级原则（版本化变换）**：任何**改变"输入 → 输出"映射的函数**都必须携带版本标识并参与缓存键——编译器（`ruleVersion`）、IR 规范（`irVersion`）、环境能力（`catalogHash`）、以及后续的解析器与调度策略。缺少任一维度，都会导致**规则升级后静默复用旧产物**，这是长跑产线最难排查的一类故障。本平台把这条原则贯穿到所有变换环节。
| 迁移可回溯 | 迁移前的原始 IR 永久保留（`graph_versions` 表），支持回滚 |

### 4.4 跨阶段连续性契约

每个阶段产出时自动校验，防止"翻译损耗"：

| 契约 | 校验项 | 违规级别 |
|---|---|---|
| **S1→S2** 剧本→资产 | 角色/场景/道具覆盖率 100%；风格对齐 ArtBible；服装逻辑与时代设定一致 | 缺角色 = blocker |
| **S2→S3** 资产→分镜 | 每个镜头引用的角色/服装/道具均已存在于资产库；提示词注入检查；种子连续性 | 悬空引用 = blocker |
| **S3→S4** 分镜→制作 | 提示词完整性；对白时间码合理性（Σ对白 ≤ 镜头时长）；总时长合规；IR 可编译 | 不可编译 = blocker |
| **S4→S5** 制作→验收 | 硬门禁全通过；产物时效 = current；无未处理降级通知 | 硬门禁失败 = blocker |

**违规级别语义**：`blocker` 阻断下一阶段 → `major` 需人工确认 → `minor` 自动记录。

### 5.5 三层调用协议（不依赖编排框架）

> 本节回答一个必须先定的架构问题：**Agent 的调用规范怎么定？** 它决定了后续所有代码的骨架。
> 结论是：**不使用 LangGraph 等图编排框架**，而是用三个数据结构自建协议。参考实现见 [`../src/little_crew/agent/protocol.py`](../src/little_crew/agent/protocol.py)（27 项自检全通过）。

#### 5.5.1 问题：两个正交的轴被同一个抽象压扁了

"三层结构"实际上混合了两个互不相干的轴：

```
轴 A：组织分层（谁调用谁）            轴 B：单体推理循环（Agent 内部怎么想）
  L1 决策层  Director / Scheduler      1 Observe 观察
  L2 协作层  18 个领域 Agent            2 Think   思考
  L3 执行层  确定性工具 / 算子           3 Act     行动 → 回到 1
```

**LangGraph 的核心问题在于：它用同一个抽象（图 + 节点 + 边）去表达这两个轴。** 后果有三：

| 后果 | 说明 |
|---|---|
| 轴 A 被错误地赋予了回路能力 | 调用关系本质是**树**；画成图后调度决策不再可静态分析 |
| 轴 B 的预算约束退化 | "最多 3 轮"变成隐性约定，不再可校验、可强制 |
| 真正需要图的地方失去立足点 | IR 执行 DAG 才是真图，但"图"这个抽象已被前两轴占用 |

#### 5.5.2 方案：三个原语取代一个抽象

| 原语 | 作用 | 关键性质 |
|---|---|---|
| **CapabilityRegistry** | 发现：谁能做什么 | 声明式副作用与成本，调用前即可预判 |
| **CallEnvelope** | 调用：怎么说话 | **三层使用完全相同的信封** |
| **Blackboard** | 状态：共享什么 | 乐观并发 + 依赖失效传播 |

> **关键洞察**：三层调用用的是**同一个信封**，只是 `callee_kind`（`agent` / `tool`）不同。因此"规范三层调用"不需要三套 API，也不需要图抽象——原语只有三个，词汇量不随层数增长。

**分工**：
- 轴 A → 显式调用树（`LayerRuntime`，单向、可强制、可追溯）
- 轴 B → 有界循环（`BoundedReasoningLoop`，硬上限，超出即 Escalate）
- 执行 DAG → 只在 L3 内部，由 IR 编译器产出（第 7 章）

#### 5.5.3 层边界四条硬规则（可强制，非约定）

```
L1 决策层 ──只能调──► L2 协作层 ──只能调──► L3 执行层
   ▲                                            │
   └──────────── 结果经 Blackboard 回流 ◄────────┘
              （禁止 L3 回调上层）
```

| 规则 | 内容 | 违反时 |
|---|---|---|
| **R1 单向依赖** | L1→L2、L2→L3 合法；L3→上层非法 | 抛 `LayerViolation` |
| **R2 禁止跳层** | L1 不得直接调 L3 | 抛 `LayerViolation` |
| **R3 预算只减不增** | 子调用预算 ≤ 父剩余预算 | 抛 `BudgetExceeded` |
| **R4 深度硬上限** | 递归深度上限（默认 6），超限即升级人工 | 抛 `DepthExceeded` |

> **R1 + R2 是整套体系的地基**：它们保证 L3 永远收不到"带 LLM 的判断"，因此 L3 的每个工具都是**可重放、可幂等、可缓存**的。一旦允许 L3 回调 L2，L3 就不再确定性——第 9 章的缓存、检查点、时效清单会**全部失效**。

#### 5.5.4 调用信封（三层同一结构）

```jsonc
{
  "traceId": "b9c39a1e...",          // 全链路关联
  "spanId": "a1b2c3d4e5f60718",
  "parentSpanId": "0f1e2d3c...",     // 调用树的父子关系由此构成
  "caller": "master_director",
  "callee": "shot_composer",
  "calleeKind": "agent",             // "agent" | "tool"
  "capability": "shot.plan",         // 能力标签，非具体实现（可替换）
  "depth": 1,
  "budget": { "tokens": 30000, "cny": 3.0, "wall_ms": 300000, "steps": 6 },
  "idempotencyKey": null             // external 副作用工具必填
}
```

**调用树由 `(traceId, spanId, parentSpanId)` 天然构成**——这意味着可观测性不需要任何额外埋点。一条真实运行产生的调用树：

```
[agent] master_director <- user (episode.direct, d=0)
  [agent] shot_composer <- master_director (shot.plan, d=1)
    [tool ] llm.complete <- shot_composer (llm.complete, d=2)
    [tool ] ir.build <- shot_composer (ir.build, d=2)
  [agent] image_gen <- master_director (shot.produce, d=1)
    [tool ] comfy.submit <- image_gen (comfy.submit, d=2)
    [tool ] gate.identity <- image_gen (gate.identity, d=2)
```

#### 5.5.5 轴 B：Agent 内部推理循环的规范化

与 LangGraph 循环的差别：这里没有"边"，只有 **step 计数器 + 预算**。`max_steps` 是构造参数而非图上的跳转条件，因此**不可能被 Agent 绕过**。

```python
class AgentDecision:          # Agent 每步只返回"下一步"，不返回完整轨迹
    action: str               # 工具名 或 "finish"
    action_input: Mapping     # 工具入参
    thought: str              # 推理留痕，进证据链
    final_output: Any = None

class BoundedReasoningLoop:   # 循环由运行时驱动，因此上限是强制的
    def __init__(self, *, max_steps: int, budget: Budget): ...
    def run(self, envelope, runtime, decide) -> (CallResult, list[ReasoningStep]):
        for idx in range(self.max_steps):     # ← 硬上限
            d = decide(envelope, steps)
            if d.action == "finish": return ...
            # 越权检查：action 必须是 manifest.consumes 声明的能力
            # 层校验：L1 Agent 调工具会被 R2 拒绝
        return CallResult.fail("F-REASONING-BUDGET", escalate=True)   # 超限即升级
```

**每一步都留痕**（`ReasoningStep`：thought / action / action_input / observation / spent），全部进入交付证据链——答辩时可逐帧回放 Agent 的决策过程。

#### 5.5.6 已实现的自检覆盖（27/27 通过）

| 组 | 覆盖内容 |
|---|---|
| T1 | 能力注册表静态审计；分层登记正确性 |
| T2 | 端到端 L1→L2→L3 调用；证据链生成；预算累加 |
| T3 | 调用树渲染；深度递增正确 |
| T4 | **R1 违反被拒绝**（L3 回调 L1 / L3 回调 L2 均被拦） |
| T5 | **R2 违反被拒绝**（L1 直调 L3；含 L1 在推理循环内偷调工具） |
| T6 | **R3 预算越界被拒绝**；Agent 声明上限收窄生效 |
| T7 | external 工具缺幂等键被拒绝（防重复计费） |
| T8 | **R4 深度超限被拒绝** |
| T9 | 黑板失效沿依赖链传递；源条目不误标 stale；乐观并发冲突 |
| T10 | **推理循环硬上限生效**（不无限循环，超限 escalate） |
| T11 | 信封指纹稳定（嵌套键序/冗余 null/浮点噪声无关，内容敏感） |

#### 5.5.7 收益对照

| 维度 | LangGraph 式 | 本协议 |
|---|---|---|
| 层边界 | 约定（靠自觉） | **代码强制**（抛异常） |
| 推理轮数上限 | 图上的跳转条件 | **构造参数，不可绕过** |
| 可观测性 | 需另接 tracing | **调用树天然存在** |
| 预算控制 | 无内建 | **R3 逐层收窄** |
| L3 确定性 | 不保证 | **R1+R2 保证** |
| 依赖体积 | 框架 + 其依赖树 | **零依赖（纯标准库）** |
| 与 IR 编译器的关系 | 抽象冲突 | **互补：IR 是真图，这里管调用** |

### 5.6 审查循环与人工确认点

```
编排器分配任务
      │
      ▼
创作 Agent 提交初稿
      │
      ├──► 并行审查（维度 A：剧评）  ┐
      └──► 并行审查（维度 B：风格）  ┘
                 │
                 ▼
        合并意见：去重 + 加权评分
                 │
      ┌──────────┴───────────┐
      │                      │
  总分 ≥ 80              总分 < 65
  且无 blocker           或有 blocker
      │                      │
      ▼                      ▼
  🛑 人工确认点         返回修改意见
  （通过→下一阶段）           │
                       创作 Agent 修订
                             │
                       重新审查（最多 3 轮）
                             │
                       超限 → 自动升级人工决策
```

**QC-5 五维品控模型**（权重分阶段调整）：

| 维度 | 定义 | S1 剧本 | S2 资产 | S3 分镜 | S5 成片 |
|---|---|:---:|:---:|:---:|:---:|
| 完整性 | 是否覆盖所有必需要素 | 25% | 20% | 15% | 15% |
| 一致性 | 内部元素、与上游约定是否一致 | 15% | **40%** | 30% | 30% |
| 品质感 | 创意/审美/叙事高度 | **35%** | 25% | 25% | 20% |
| 可执行性 | 下游能否直接使用 | 15% | 10% | **25%** | 25% |
| 合规性 | 时长/预算/风格约束 | 10% | 5% | 5% | 10% |

**判分规则**：总分 ≥ 80 且无 blocker → 自动通过；65–79 → 人工快审；< 65 → 必须修订；最多 3 轮。

> ⚠️ **关键实现细节**：所有加权总分**由服务端权威计算**，不信任模型自报分数。模型的 `dimensions` 只是原始输入，若模型自报 `score` 与服务端计算值偏差 > 5，判定为"评分不可靠"，该报告作废并重新审查。

> **为什么必须这样做**：LLM 在评分任务上存在系统性乐观偏差与自我一致性偏好，且自报分数与其自身给出的维度明细常常不自洽。把"算分"这件事从生成模型手里拿走、交给确定性代码，是让 QC-5 成为**可审计的度量**而非**模型的自我评价**的前提。这是验收层的第一条设计纪律。

### 5.7 编排：Multi-Agent 与 Pipeline 的分界

| 阶段 | 范式 | 理由 |
|---|---|---|
| S1 剧本创作 | **Multi-Agent 审查循环** | 创意需多角度审视，允许非确定性 |
| S2 资产设计 | **Multi-Agent 并行 + 集中审查** | 三类设计可并行，一致性需集中裁决 |
| S3 分镜设计 | **Multi-Agent 审查循环** | 节奏与连续性需专门视角 |
| S4 制作合成 | **Pipeline 确定性执行** | 已确定的任务必须可复现、可缓存、可断点续跑 |
| S5 验收 | **门禁（Gate）** | 不是生成任务，是判定任务 |

**设计原则**：**创意阶段用 Agent，生产阶段用 Pipeline**。在需要创造力的地方引入非确定性；在需要稳定交付的地方消灭非确定性。

## 第 6 章 自研 Transformer 智能体

> 本章回答"自研 Transformer 架构的 Agent"如何**不沦为噱头**。

### 6.1 定位声明（先说清不做什么）

**不做**：
- ❌ 自训 LLM 写剧本 —— 打不过 DeepSeek/Qwen，且无数据优势
- ❌ 自训扩散模型 —— 与平台定位无关
- ❌ 用 Transformer 替代已有成熟能力

**做**（三块有数据、有指标、有基线可打的方向）：

| 编号 | 模块 | 替代什么 | 为什么值得自研 |
|---|---|---|---|
| **A** | **Scheduler**：图状态 → 调度策略 | LLM 逐步决策"下一步做什么" | 决策频率极高（每镜多次），LLM 调用延迟/成本不可接受；且决策可离线学习 |
| **B** | **Consistency Embedder**：角色/场景 → 一致性向量 | 纯提示词描述 | 提示词是离散、易漂移的；向量可检索、可度量、可约束 |
| **C** | **Light Verifier**：产物 → 合格概率 | 昂贵 VLM 逐镜审片 | VLM 审一镜数秒+额度；轻量模型可先筛，只把可疑样本送 VLM |

### 6.2 模块 A：Transformer Scheduler

**问题形式化**：把漫剧生产建模为**部分可观测马尔可夫决策过程（POMDP）**：

- **状态** $s_t$：StoryGraph 的当前快照 $\rightarrow$ 图编码
- **动作** $a_t \in \mathcal{A}$：
  - `GENERATE(shot_id, engine, params)` — 生成某镜
  - `RETRY(shot_id, repair_hint)` — 带修复注记重跑
  - `ESCALATE(shot_id, reason)` — 升级人工
  - `ADVANCE(scene_id)` — 推进下一场
  - `FANOUT(shot_ids)` — 并行展开
  - `SWITCH_ENGINE(engine)` — 换引擎
  - `STOP(episode_id)` — 预算终止
- **奖励** $r_t$：
  $$r_t = \underbrace{\mathbb{1}[\text{验收通过}]}_{\text{成功}} - \lambda_1 \underbrace{\text{cost}_t}_{\text{GPU/API 成本}} - \lambda_2 \underbrace{\text{latency}_t}_{\text{时延}} - \lambda_3 \underbrace{\mathbb{1}[\text{人工介入}]}_{\text{人工}}$$

**图编码器**（异构 GNN + Transformer）：

```
输入：IR 图（节点特征 + 边类型 + 约束）+ 全局状态（预算/已用时/队列深度）
  │
  ├─ 节点特征嵌入：kind(one-hot) ‖ dtype ‖ 参数向量 ‖ 执行语义(sideEffect/idempotency)
  ├─ 4 层异构图注意力（按边类型分离注意力头：data / constraint / control）
  ├─ 全局 readout token（[CLS] 式）
  └─ 时间维：最近 K 次尝试的轨迹 → 1D 卷积 → 拼接到全局 token
  │
输出：图嵌入 h ∈ R^512
  │
  ├─ Actor 头：动作分布 π(a|s)（动作空间用 pointer network 指向具体节点）
  └─ Critic 头：V(s)（用于 PPO 优势估计）
```

**规格**：~12M 参数，4 层，8 头，hidden 512。**单次决策 < 10ms（GPU）/ < 40ms（CPU）**——比 LLM 决策快 2–3 个数量级。

**训练**：

| 阶段 | 方法 | 数据来源 | 目标 |
|---|---|---|---|
| **冷启动** | 启发式策略 | 人工规则（如"硬门禁失败 → 提升 LoRA 权重重跑"） | 保证系统可用 |
| **阶段 1：模仿学习** | 从人工/LLM 编排轨迹做行为克隆 | 录制 200–500 集生产日志 | 达到基线水平 |
| **阶段 2：离线 RL** | CQL / IQL（避免在线探索烧 GPU） | 同上 + 反事实评估 | 超过启发式 |
| **阶段 3：在线微调** | PPO（限制探索幅度，安全约束） | 线上交互 | 持续优化 |

**⚙️ 冷启动的务实做法**：系统第一天就用启发式策略跑通，Scheduler 与启发式**并行决策做影子对比**（shadow mode），积累数据后再切换。这样**不等模型训好就能出片**——这对"两者兼顾"的定位至关重要。

### 6.3 模块 B：Consistency Embedder

**要解决的问题**：角色 A 在第 3 镜是米色风衣、第 27 镜变深灰——提示词描述无法可靠约束跨镜一致性。

**方案**：为每个角色/场景学习一个**一致性嵌入向量** $e \in \mathbb{R}^{256}$。

```
训练目标（多任务对比学习）：
  正样本对：同一角色、不同镜头、人工判定"一致"的图对
  负样本对：同一角色、人工判定"漂移"的图对 + 不同角色的图对

  L = L_contrastive(e_img, e_char) + L_triplet(anchor, pos, neg) + L_reg
```

**用途**：

| 用途 | 实现 |
|---|---|
| **一致性度量** | 新镜头图与角色锚点集的嵌入相似度 → 直接作为 `cr_face_*` 断言的观测量 |
| **检索复用** | 相似镜头嵌入 → 命中缓存条件指纹，避免重复生成 |
| **漂移预警** | 嵌入在时间轴上的轨迹突变 → 提前告警（不等出片就发现问题） |
| **提示词校正** | 嵌入差异 → 反查差异最大的属性维度 → 生成定向修复提示词 |

**数据来源**：平台自身生产日志（每集天然产出数百张同角色跨镜图）+ 人工一致性标注（可众包/自标）。

**为什么这是平台独占优势**：竞品把生产日志当天丢弃；本平台把它变成**训练数据飞轮**。

### 6.4 模块 C：Light Verifier

**问题**：VLM 审片（如 GLM-4.6V）每镜 3–8 秒 + 额度消耗；一集 100 镜，纯 VLM 审查成本与耗时不可接受。

**方案**：轻量分类器先筛，只把"可疑样本"送 VLM。

```
产物（缩略图 + 帧差统计 + 关键属性）
   │
   ▼
[Light Verifier]  ~5M 参数 ViT-Tiny + MLP 头
   ├─ 输出 8 维质量概率（对齐 VLM 审片维度）
   ├─ 不确定性估计（MC Dropout / 深度集成）
   └─ 决策：
        p(合格) > 0.92 且 不确定性低  → 直接 KEEP（跳过 VLM）
        p(合格) < 0.35               → 直接 RETRY（跳过 VLM）
        其余                          → 送 VLM 精审
```

**收益预期**（需实验验证）：VLM 调用量下降 70–85%，端到端审片耗时下降 60%+。

**训练**：以 VLM 的历史判定为软标签（知识蒸馏），加确定性算子结果作硬标签。

### 6.5 三模块的协同

```
                    ┌─────────────────────────────┐
                    │      Scheduler (A)          │
                    │  "下一步做什么？"            │
                    └───────┬─────────────────────┘
                            │ 读状态
        ┌───────────────────┼───────────────────┐
        ▼                   ▼                   ▼
┌───────────────┐  ┌───────────────┐  ┌───────────────┐
│ Embedder (B)  │  │  ComfyUI 执行 │  │ Verifier (C)  │
│ "像不像？"     │  │  (GPU)        │  │ "过不过？"     │
└───────┬───────┘  └───────┬───────┘  └───────┬───────┘
        │  嵌入距离         │  产物             │  合格概率
        └───────────────────┴───────────────────┘
                            │
                    奖励信号 → 训练 Scheduler
```

**闭环**：B 和 C 提供密集的中间奖励信号，使 Scheduler 的 RL 训练**不必等到成片才有奖励**——这是三模块协力才成立的训练可行性。

### 6.6 与"用 LLM 当 Agent"的对比实验设计

| 配置 | 说明 |
|---|---|
| Baseline-1 | 纯固定流水线（无 Agent 决策） |
| Baseline-2 | LLM Agent 编排（DeepSeek-V3.2 / Qwen-Max，逐步决策） |
| Baseline-3 | 启发式规则调度 |
| **Ours** | Transformer Scheduler |
| Ablation | 去掉 B / 去掉 C / 去掉 B+C |

**主指标**：单集总成本（¥）、单集墙钟时间、一次通过率、人工介入率。
**预期结论**：Ours 在成本与时延上显著优于 Baseline-2，在质量上持平或更优。

## 第 7 章 ComfyUI 编译层

### 7.1 编译契约

| 项 | 定义 |
|---|---|
| 输入 | `UnifiedIR`（单镜头或单场景粒度）+ `CapabilityMatrix` + `COMPILE_RULE_VERSION` |
| 输出 | `CompileResult { graph, notices[], graphHash, compileMs }` |
| 目标格式 | ComfyUI **API 格式**（`{nodeId: {class_type, inputs}}`），非前端保存的含 `nodes/links` 的 UI 格式 |
| 纯度 | 编译是**纯函数**：同一 (IR, Matrix, RuleVersion) 必得同一 (graph, hash) |
| 失败语义 | `UNKNOWN_KIND` / `MISSING_REQUIRED_NODE` / `DANGLING_REF` / `PORT_MISMATCH` 四类，均返回结构化错误 |

### 7.2 能力矩阵探测

启动时与每次 ComfyUI 重连后，调用 **`GET /object_info`** 抓取当前环境的完整节点目录，构建：

```jsonc
{
  "probedAt": "2026-10-11T10:15:00+08:00",
  "comfyVersion": "0.3.xx",
  "frontendVersion": "1.x.x",
  "nodes": {
    "KSampler": {
      "input": { "required": {
        "model": ["MODEL"], "positive": ["CONDITIONING"], "negative": ["CONDITIONING"],
        "latent_image": ["LATENT"], "seed": ["INT",{"default":0,"min":0,"max":18446744073709551615}],
        "steps": ["INT",{"default":20,"min":1,"max":10000}],
        "cfg": ["FLOAT",{"default":8.0,"min":0.0,"max":100.0}],
        "sampler_name": [["euler","euler_ancestral","dpmpp_2m","..."],{}],
        "scheduler": [["normal","karras","exponential","..."],{}],
        "denoise": ["FLOAT",{"default":1.0,"min":0.0,"max":1.0}]
      }},
      "output": ["LATENT"], "category": "sampling", "output_node": false

  },

  "customNodePacks": ["ComfyUI-GGUF", "ComfyUI_IPAdapter_plus", "..."]

```

**为什么 `nodeCatalogHash` 是关键**：它把"环境"变成一个可哈希的实体。缓存键包含它，环境一变，所有依赖该环境的缓存自动失效——**根治"换了节点版本后旧产物静默错误"**。

### 7.3 漂移检测（三态）

| 漂移类型 | 检测方式 | 处理 |
|---|---|---|
| **节点缺失** | `object_info` 中无该 `class_type` | 走 `degradeTo` 链；无降级路径且 `required` → **阻断编译**并给出安装建议 |
| **端口变更** | 声明端口不在 `object_info.input.required/optional` | 尝试**同名别名映射**（维护别名表）；失败则走降级链 |
| **枚举值缩减** | 声明的 sampler/scheduler/lora_name 不在候选列表 | 自动回退到语义最近的候选（维护序关系表，如 `dpmpp_2m → dpmpp_2m_sde → euler`）+ 产生通知 |

**模型/LoRA 存在性校验**：对 `lora_name`、`ckpt_name` 等文件型输入，通过 `object_info` 的候选列表校验文件是否真的在目标环境（**这是 kt-ai-Studio 式模板填充的经典故障点**）。

### 7.5 图哈希与版本管理

```
graphHash    = sha256( canonical(executionGraph) )        # 编译产物哈希
irHash       = sha256( canonical(normalizedIR) )           # 语义哈希
catalogHash  = sha256( nodeCatalog )                       # 环境哈希
ruleVersion  = "little_crew.compile/v1"                                # 规则版本

# 三级缓存键
conditionFingerprint = md5( prompt ‖ characterRefs ‖ sceneRef ‖ width ‖ height ‖ frames ‖ fps )
cacheKeyTier1 = md5( irHash ‖ catalogHash ‖ ruleVersion )               # 同环境同语义
cacheKeyTier2 = md5( irHash )                                          # 跨环境语义（需校验产物兼容性）
cacheKeyTier3 = md5( conditionFingerprint ‖ resolutionTier )            # 镜头级条件缓存
```

三级缓存的意义：**Tier1 环境内精确命中**（最快）；**Tier2 跨环境/跨机器复用**（需重新校验质量断言）；**Tier3 条件级复用**（不同 IR 但实际条件相同的镜头共享编码结果，大幅省 GPU）。

**实现过程中发现并修正的五个真实缺陷**（均已在测试中固化）：

| # | 缺陷 | 后果 | 修正 |
|---|---|---|---|
| 1 | `class_types` 备选被当作并列需求 | "任一备选缺失"即误判阻断，**降级链完全失效** | 按 kind 分组，预演选型后只对实际选中的 class_type 声明需求 |
| 2 | `param_map` 的**键**（IR 参数名）被当作端口需求 | 产生 "节点上不存在输入端口 sampler" 之类**假漂移** | 需求声明统一使用 `param_map` 的**值**（ComfyUI 输入名） |
| 3 | 降级补偿表/阈值放宽量取自**目标规则** | 两者在目标规则上为空 → 补偿与阈值联动**静默失效** | 同时返回源规则与目标规则：端口映射用目标、补偿与阈值用源 |
| 4 | `PortRequirement.files` 的键语义混乱（端口名 vs class_type） | 文件校验静默跳过 → **"底模/LoRA 不在目标环境"这一最致命故障漏检** | 统一为端口名，并新增"文件型输入不存在"的显式 blocker |
| 5 | 阈值放宽可被多个节点重复累加 | 约束被过度放宽，**失去把关作用** | 同一约束只放宽一次（按约束注册表判重） |

> 第 3 与第 5 条尤其值得记录：它们都属于"不会报错、只是悄悄不生效"的缺陷。若没有把降级行为写成可断言的测试，这类问题会在生产环境里表现为"一致性莫名变差但查不出原因"。这也是 E2 消融实验要回答的问题。

### 7.8 ComfyUI 接口契约知识（源码级核实）

设计编译层时，我对 ComfyUI 的内部机制做了**源码级核实**（一手来源见
`research/comfyui-internals/`，含 `execution.py` / `caching.py` 快照）。
核实结果**修正了三处此前的判断**——其中一处是我自己先前的过度判断。

#### 7.8.1 更正：种子变化**不需要**强制重算

**此前判断**：种子可能不在 ComfyUI 的缓存键里，需靠 `IS_CHANGED` 强制重算。

**源码事实**（`caching.py:117-128`）：

```python
signature = [class_type, await self.is_changed_cache.get(node_id)]
...
for key in sorted(inputs.keys()):
    if is_link(inputs[key]):
        signature.append((key, ("ANCESTOR", ancestor_index, ancestor_socket)))
    else:
        signature.append((key, inputs[key]))      # ← widget 值（含 seed）全在签名里
```

节点签名 = `[class_type, is_changed]` + **全部 inputs** + 递归祖先签名。
**`seed` 是 inputs 的一部分**，因此换了种子自动重算。

而本平台的种子是**确定性派生**的（`derive_seed(projectSeed, ep, sc, sh, attempt)`）
并写入 `n_ks.inputs.seed` —— 所以：

> **本平台的种子设计与 ComfyUI 的缓存语义天然契合，不需要任何额外处理。**
> 上一轮我判断"必须新增 `IS_CHANGED` 处理以保证重跑真的重跑"，是**过度的**。

#### 7.8.2 真实风险：缓存键**不完整**的节点

真正的风险不在种子，而在**读外部状态却未声明钩子**的节点。而钩子无法探测：

| 钩子 | 适用 | 形态 |
|---|---|---|
| `IS_CHANGED` | v1 节点 | `@classmethod`，返回值进 `is_changed` |
| `fingerprint_inputs` | v3 节点 | 同上 |

二者都是**类方法**，**不会出现在 `GET /object_info` 的 schema 里**。

已从官方源码逐条确认的钩子（`research/comfyui-internals/` 有行号依据）：

| class_type | 钩子 | 计算内容 |
|---|---|---|
| `LoadImage` | `IS_CHANGED` | 图片文件的 **sha256 内容** |
| `LoadImageMask` | `IS_CHANGED` | 同上（经 `super()` 复用） |
| `LoadImageOutput` | `IS_CHANGED` | 同上（继承 `LoadImage`） |
| `LoadAudio` | `IS_CHANGED` | 音频文件内容 |
| `LoadVideo` | `fingerprint_inputs` | 视频文件的 **mtime**（刻意不哈希大文件以省时） |

**处置**：新增 `little_crew.capability.comfy_interfaces` 作为**接口契约知识的唯一位置**，
采用三级来源补全——① 显式声明（自定义节点走这条）② 已知表（上面 5 条）
③ 都没有 → `DeterminismClass.UNKNOWN`，编译器产出 `CACHE_KEY_INCOMPLETE` 通知。

> **关键设计选择**：`UNKNOWN` **不默认当作 `PURE`**。
> "不知道"必须显式化为存疑并告知用户，否则会静默复用可能失效的缓存。
> 三态（`True`/`False`/`None`）严格区分："显式确认无钩子"不得回退到已知表。

#### 7.8.3 发现并修复的第六个缺陷：**把文件路径喂给 IMAGE 端口**

核实 `LoadImage` 时暴露了一个更严重的既有缺陷：

```
编译器产出： "image": "char/CHAR-0007/anchor_front_v3.png"   ← 字符串
端口要求：   image  dtype=IMAGE                              ← 张量
```

`IPAdapterAdvanced.image` 的端口类型是 **IMAGE（张量）**，而 IR 的 `bindings`
存的是路径字符串。**必须先经 `LoadImage` 转换。** 早期版本直接塞字符串——
编译"成功"，但提交到真实 ComfyUI 必然报类型错误。

| 环节 | 问题 | 修正 |
|---|---|---|
| 规则表 | 缺 `image.file` kind（`LoadImage`） | 新增规则，`output_ports=("IMAGE","MASK")` |
| 输入解析 | widget 字符串值未做端口类型强制 | 新增 `_coerce_for_port`：值落在 `IMAGELIKE_INPUT_DTYPES` 端口且为路径字符串时**自动注入 `LoadImage`** |
| 节点 id | 自增计数器会破坏编译纯度 | 由**路径 sha256 派生**（`n_loadimg_<10位>`），保证同 IR 同图同哈希 |
| 需求声明 | 编译前无法预知需要 LoadImage | 新增 `required_loaders`，把"缺 LoadImage"提前到漂移检测阶段发现 |

**附带收益**：`LoadImage` 自带 `IS_CHANGED`（对文件内容做 sha256），
因此**锚点图换版时 ComfyUI 会自动重算下游**——与本平台第 9.3 节的产物时效清单天然互补：
时效清单负责跨 ComfyUI 实例的失效传播，`IS_CHANGED` 负责实例内的。

#### 7.8.4 环境哈希纳入钩子存在性

`IS_CHANGED` 的有无**直接改变缓存键的计算方式**，因此属于 **ABI 变化**。
`catalog_hash()` 的每节点签名新增两个字段：

```python
"fh":  spec.fingerprint_hook,   # 钩子种类（如 "IS_CHANGED" / None）
"det": spec.determinism,        # PURE / HOOKED / UNKNOWN
```

同时新增漂移类型：`FINGERPRINT_HOOK_CHANGED`（警告级，提示复核时效清单）、
`DETERMINISM_CHANGED`（信息级，多因已知表更新）。

> 注意：钩子的**来源**（known_table / declared / prefix_match）**不纳入哈希**——
> 同一事实的不同来源不应改变环境身份。但 `determinism` 必须纳入，
> 因为 `UNKNOWN` 与 `HOOKED` 意味着不同的缓存行为保证。

#### 7.8.5 缓存分层：我们**不重复实现** ComfyUI 的节点级缓存

源码核实的另一个重要结论：**ComfyUI 已提供跨 prompt 的节点级增量计算。**

| 事实 | 依据 |
|---|---|
| 签名不含 `prompt_id` → **跨 prompt 命中** | `caching.py:102-128` |
| 签名默认不含 `node_id` → 图结构相同即命中 | `caching.py:89-90` |
| **跨 prompt 持久**：`CacheSet` 在 `PromptExecutor.__init__` 创建，`reset()` 仅构造时调用一次 | `execution.py:665-677` |
| 命中结果**广播** `execution_cached`（带命中节点列表） | `execution.py:766-774` |
| 缓存策略四选一：`CLASSIC` / `LRU` / `NONE` / `RAM_PRESSURE` | `execution.py:114-154` |

因此两层缓存**作用域完全不同，是组合而非重叠**：

```
本平台三级缓存 = 语义级（跨 ComfyUI 实例）
    T1  irHash × catalogHash × ruleVersion
    T2  irHash
    T3  条件指纹
         ↓ 未命中才提交
ComfyUI 节点级缓存 = 执行级（实例内，按输入签名）
```

**一个必须遵守的工程结论**（写入 `runtime` 的接口契约）：

> 当 IR 变了但底层图大部分未变时，**仍应提交给 ComfyUI**，
> 让它的节点级缓存吃掉未变的祖先链。仅靠 T1/T2 会白跑一趟。
>
> 并且 **`execution_cached` 的命中必须与平台命中分开统计** ——
> 否则会把 ComfyUI 的功劳算成平台的，E7 缓存收益实验的量化指标会失真。

#### 7.8.6 修正后的缺陷清单

| # | 缺陷 | 类别 |
|---|---|---|
| 1–5 | 见 §7.7（降级链失效、假漂移、补偿失效、文件漏检、阈值过度放宽） | 静默失效 |
| **6** | **把文件路径字符串喂给 IMAGE 端口** | **类型错误（编译过、执行必错）** |
| **7** | 确定性存疑节点**逐节点告警**，一个普通镜头图产出 9 条同义通知 | **告警疲劳** |

> **第 6 条**值得单独强调：它的**守卫其实早就存在**（能力矩阵记录了端口类型），
> 但因为"widget 值的类型校验"这一环缺失而没有被触发。
> 通用教训：**守卫存在 ≠ 守卫生效** —— 必须为守卫本身写测试。

> **第 7 条**是修正过程中由"演示输出"暴露的，值得单独说明。
> 初次实现把每个确定性未核实的节点都产出告警，实测一个最普通的镜头图
> （KSampler / CLIPTextEncode / VAEDecode / 各种 Loader）产出 **9 条**通知。
> 后果不是更安全，而是**告警疲劳**：开发者会学会忽略这个通知，
> 真正需要关注的第三方节点存疑反而被淹没。
>
> **修正为三件事**：
> 1. 建立**官方确定性节点白名单**（严格收录：官方核心 + 无外部状态 + 无钩子），
>    区分"未收录"与"确实未知"
> 2. 告警**按 `class_type` 去重**，每类一条并声明影响范围（"涉及 N 个节点"）
> 3. 建立**第三方节点在册表**（`THIRD_PARTY_NODES_IN_USE`），
>    记录我们主动选用的第三方依赖及其核实状态，附具体核实方法
>
> 修正后同一图只有 **1 条**告警，且是真实的（`IPAdapterAdvanced` 钩子未核实）。
> 这类"降噪"设计在监控系统里是常识，但在生成管线的编译层容易被忽略 ——
> **告警的可信度取决于它的信噪比，而非数量。**

> **未验证项如实标注**：`/object_info` 是否支持 `?properties=` 查询参数、
> 是否提供节点 `displayName` 字段，均**不在已取源码快照范围内，未验证**，
> 因此**不写入实现**。记录此条的目的是把"未验证"显式化 ——
> 凭印象把未验证的假设写进实现，比留一个显式的 TODO 危险得多。

## 第 8 章 一致性保障体系

漫剧一致性的五个层次，逐层有独立机制：

### 8.1 身份一致性（角色脸/体）

| 机制 | 说明 |
|---|---|
| **锚点集 AnchorSet** | 每个角色维护正/侧/背/表情锚点图，版本化（v1/v2/v3），形象指纹 `sha256` 跨项目复用零渲染 |
| **LoRA 锁定** | 有训练好的角色 LoRA 则优先；权重由约束阈值反推 |
| **参考注入** | IP-Adapter / ReferenceLatent / ControlNet 按环境能力选择 |
| **嵌入校验** | Consistency Embedder 比对，作为 `cr_face_*` 断言观测量 |
| **双形态契约** | 角色的变身/真身形态独立锚点，避免混淆 |

### 8.2 风格一致性

| 机制 | 说明 |
|---|---|
| **ArtBible（风格圣经）** | 项目级风格定义：色板、光影逻辑、材质倾向、镜头语言，作为独立 IR 节点参与编译 |
| **提示词纪律注入** | 风格词由 `StyleGuardAgent` 统一注入，位置固定（段落前部高服从位） |
| **负向约束** | 项目级负向词 + 镜头级负向词分层合并 |
| **风格向量** | Embedder 的场景/风格嵌入，用于跨镜风格距离监控 |

### 8.3 场景与道具持续性

- **场景卡**：客观描述空间结构/材质/光影，禁止主观形容词（"温馨的房间" ❌ → "浅木地板、右侧落地窗、暖白顶灯 3000K" ✅）
- **道具卡**：关键道具独立资产，引用即锁定
- **陈设快照**：同场景多镜头共享 `sceneLayoutHash`，布局变更触发相关镜头时效失效

### 8.4 时间连续性

| 机制 | 说明 |
|---|---|
| **种子体系** | `projectSeed → episodeSeed → sceneSeed → shotSeed → attemptSeed`，确定性推导，全链可复现 |
| **首尾帧承接** | 链式生成：上段末帧接续下段首帧，防止跳变 |
| **运动上下文门控** | 固定运镜镜头不加载运动上下文模块，避免运动描述与静态构图指令相互干扰导致运镜指令失效 |
| **轴线与视线** | `ContinuityCheckAgent` 校验 180° 轴线、视线匹配、动作衔接 |
| **节奏模型** | 5s ≈ 3–4 拍 / 10s ≈ 5–7 拍 / 15s ≈ 6–9 拍，峰值刹车；情感戏强制近景特写 |

### 8.5 音画一致性

- 对白带**说话人 ID**（`(S1)/(S2)` 或 `角色名:` 前缀），音色按角色绑定
- 时长计算器：`frames = ceil(audioDuration × fps) + bufferFrames`
- 字幕卡点：毫秒级对齐；`chars_per_sec` 可配，超限自动补偿 clamp
- 口型：viseme 轨 → 对齐评分 → 漂移自动校正 → 引擎渲染 → 回写时间线

### 8.6 一致性检查的三种执行者

| 执行者 | 何时用 | 特点 |
|---|---|---|
| **确定性算子** | token 包含、帧数、时长、哈希、人脸相似度阈值 | 快、免费、可复现、**可作为硬门禁** |
| **Light Verifier** | 大部分镜头的初筛 | 快、便宜、有不确定性估计 |
| **VLM 跨模型盲读** | 可疑样本 + 关键镜头 | 慢、贵，但能发现语义级问题 |

## 第 9 章 工程落地机制

> 本章机制**不是优化项，是能不能跑通一集的生死线**。

### 9.1 内容寻址缓存（三级）

见 7.5。实现要点：

- 缓存存储实际文件（图/视频/潜在编码），键为 `cacheKey`
- **草稿/定稿分辨率各自独立缓存**（草稿 416P 预审 → 定稿 1088P，避免定稿时草稿缓存全部失效）
- 命中率、节省 GPU 秒数纳入可观测指标

### 9.2 渲染检查点与崩溃恢复

```
提交前：  NodeExecution(prompt_id, inputs_hash, status='submitted') 落盘
执行中：  WebSocket 事件更新 status
完成后：  /history 回收 outputs，写 Artifact，status='done'

崩溃重启：
  1. 读取所有 status='submitted' 的记录
  2. 批量查询 ComfyUI /history
  3. 已有结果 → 直接回收（绝不重复烧 GPU）
  4. 队列中 → 重新 watch
  5. 已丢失 → 按 recoveryMode 决定 replay / reconcile / manual
```

**幂等保证**：每个节点的 `idempotency` 声明决定重放语义。`pure` 节点可任意重放；`external`（如调用付费 API）节点必须有 `idempotencyKey` 或 `providerReceipt` 才能重试。

### 9.3 产物时效清单（Freshness Manifest）

每个产物记录**全部输入指纹**：

```jsonc
{
  "artifactId": "A00091",
  "shotId": "SH-E001-S003-005",
  "freshness": "stale",
  "inputs": {
    "irContentHash": "sha256:aaa...",
    "characterAnchors": { "CHAR-0007": "sha256:bbb...", "mtime": "2026-10-11T09:00:00+08:00" },
    "anchorGeneration": { "CHAR-0007": 3 },        // 视图代数
    "artBibleHash": "sha256:ccc...",
    "comfyCatalogHash": "sha256:ddd...",
    "ruleVersion": "little_crew.compile/v1",
    "seedDerivation": "sha256:eee...",
    "engineVersion": "h3-ref2va-int8-v2"
  },
  "reason": "characterAnchors.CHAR-0007 变更（代数 2→3）"
}
```

**四态**：`current` / `stale` / `missing` / `orphan`。
**自动行为**：`stale` → 排入重渲队列（含其条件缓存失效）；`missing` → 断点续跑时补齐。

> 这是"改一张定妆照，全剧 40 个相关镜头自动重跑且只重跑这 40 个"的实现基础。

### 9.4 队列、租约与幂等

| 机制 | 说明 |
|---|---|
| **任务队列** | 优先级：用户交互 > 关键镜头 > 批量；支持暂停/插队 |
| **租约** | Worker 领取任务需获租约（`leaseOwner` + `leaseExpiresAt`），超时自动回收，防僵尸任务 |
| **幂等键** | `idempotencyKey = md5(runId ‖ irNodeId ‖ attemptOrdinal)`，重复提交返回既有结果 |
| **重试策略** | `maxAutomaticAttempts` + `bounded_exponential` 退避；区分**可重试失败**（超时/429）与**不可重试失败**（参数非法） |
| **对账** | 定期 `reconcile`：本地状态 vs ComfyUI 队列/历史，修复不一致 |

### 9.5 GPU 调度

| 策略 | 说明 |
|---|---|
| **模型常驻** | 统计模型使用频率，热模型保持常驻，避免反复加载（加载常是最大开销） |
| **显存感知排队** | 任务声明显存需求，调度器按当前显存水位决定并发度 |
| **分辨率分档** | 草稿 416P / 标准 768P / 高清 1088P，草稿预审半分辨率 → 定稿全分辨率零返工 |
| **批处理** | 同条件镜头合并批次（条件缓存命中时直接跳过编码） |
| **加速开关** | SageAttention / TurboLoRA 按步数阈值自动启用（步数 ≤ 8 启用 TurboLoRA ≈ 2.9× 提速） |
| **保养窗口** | 每日定时清理 ComfyUI 共享 input/output，防盘满 |

### 9.6 可观测性与交付证据链

```jsonc
{
  "runId": "run_20261011_ep001",
  "episodeId": "EP-001",
  "phases": [
    { "phase": "S1_script", "status": "done", "ms": 184000, "costCny": 1.42,
      "agentCalls": 7, "reviewRounds": 2 },
    { "phase": "S4_production", "status": "running", "shots": { "done": 62, "running": 3, "pending": 41 },
      "gpuMs": 1840000, "cacheHits": 23, "cacheMisses": 83 }
  ],
  "evidence": [
    { "artifactId": "A00091", "assertions": [ /* 全部断言结果 */ ],
      "reviews": [ /* 全部审片报告 */ ], "degradations": [ /* 全部降级通知 */ ] }
  ],
  "costReport": { "llmCny": 3.21, "gpuCny": 0.00, "cloudApiCny": 0.00, "totalCny": 3.21 }
}
```

**交付证据链的价值**：任一成片镜头都可追溯到"哪次尝试、哪个 IR 哈希、哪些断言通过、谁审的、有没有降级"。这是**答辩演示与真实生产共用的能力**。

### 9.7 失败码体系

```
F-SUBMIT-API     提交失败（接口错误）
F-SUBMIT-VALID   图校验失败
F-MISSING-NODE   必需节点缺失
```

每个失败码对应**自动处置策略**与**UI 修复引导**。失败码统计是持续改进的主要输入。

#### 11.3.3 无授权项目的处理纪律（重要）

调研发现 **5 个高相关项目未提供 LICENSE 文件**，其中 NiliX 的工程机制（条件缓存、产物时效清单、渲染检查点）质量极高、极易被"顺手照搬"。本平台对此采取明确纪律：

1. **机制可以独立推导，文本不可复制**。本平台第 9 章的缓存/检查点/时效清单机制，其**需求来源**是明确的工程约束（P4：成本与重跑失控），设计与字段定义均为独立推导；文档中不复制任何无授权项目的命名（如不使用 `script_parse_ver`、`agent_state.json`、`manju_*` 等标识符）。
2. **文档措辞审计**。设计文档中凡涉及无授权项目的段落，仅做**事实性描述**（"它做了什么"），不使用"借鉴/照搬/参考其实现"等可能被解读为派生关系的表述。
3. **代码来源审计**。提交前对代码库执行依赖与片段扫描，确认无来自二级项目的代码片段。
4. **答辩与论文的引用规范**。在"相关工作"章节以学术引用形式列出（附仓库 URL 与核验日期），并明确标注"未提供开源许可，故本文仅作现状描述，不构成对其实现的复用"。

> **为什么这条纪律值得写进设计文档**：漫剧平台很可能被产业化使用，"某个核心机制来自一个没有许可证的仓库"会成为实质性法律风险，且追溯成本极高。把纪律前置到设计阶段，是零成本的。

### 11.4 模型授权门禁（已实现）

§11.3 处理的是**代码依赖**的合规。还有一类风险容易被忽略：**模型权重与产出的授权**。

**「权重能下载」≠「产出能商用」**。调研中逐一核验模型授权后，发现四类真实风险：

| 风险类型 | 实例 | 若靠人工记忆会怎样 |
|---|---|---|
| **同名模型授权相反** | FLUX.2 Klein **4B** = Apache-2.0（可商用）；**9B** = FLUX Non-Commercial（禁商用） | 名字几乎一样，随手选了 9B，产品里嵌了禁商用产出 |
| **地区排除** | MiniMax H3 排除 US/EU/UK/KR（中国大陆**在范围内**）；HunyuanVideo 1.5 排除欧盟/英国/韩国 | 部署到欧美后才被发现，返工成本极高 |
| **营收门槛** | LTX Community < 1000 万美元；Stable Audio 3 < 100 万美元 | 规模化后突然越线，需追溯授权 |
| **信源冲突** | MiniMax Music 3：一说 CC-BY-NC-4.0，一说 Community License | 随手挑一个说法，可能选错 |

**实现**：`../src/little_crew/governance/license.py`（33 项测试全通过）。核心是三条**强制行为**——不是文档里的一句话，而是代码里的 `DENY`：

| # | 强制行为 | 理由 |
|---|---|---|
| **A** | **未核实 = 拒绝**。`verified: false` 的模型不得进入自动路由 | 授权信源冲突时，"我不知道"的正确处理是拒绝，不是随便挑一个。该规则**优先于**授权本身的宽松性（即便写 Apache-2.0，未核实也不放行） |
| **B** | **降级链的每一跳都要重新过授权** | 防止"为避免 OOM 降级 → 落到禁商用模型 → 静默产出禁商用内容" |
| **C** | **归属标注自动注入** | MiniMax H3 要求界面显著标注；靠人记得必然会漏 |

**路由集成**：被拒模型**根本不进入打分环节**——

```python
allowed, verdicts = gate.filter_allowed(candidates, ctx)   # 硬约束前置
# 之后才轮到 TaskProfile 的 prefer 加权排序
```

**审计报告可直接用于答辩与商用尽调**。本机情形（中国大陆 / 非商用）实测输出：

```
ALLOW=17  DENY=0  NEEDS_REVIEW=2
[OK ] minimax-h3            MiniMax-Community     允许使用
[OK ] qwen-image-2512       Apache-2.0            允许使用
[OK ] wan2.2-14b            Apache-2.0            允许使用
[OK ] flux2-klein-4b        Apache-2.0            允许使用
[OK ] flux2-klein-9b        FLUX-Non-Commercial   允许使用  [NC]   ← 明确标记禁商用
[OK ] yue2-3b               CC-BY-NC-4.0          允许使用  [NC]
[?? ] lens                  UNVERIFIED            授权未核实，拒绝自动启用
[?? ] minimax-music-3       UNVERIFIED            授权信源冲突，必须人工核实
```

> ⚠️ **报告呈现的一个细节**：非商用授权在**非商用情形**下判定为 `ALLOW`（技术上正确），
> 但若不加标记，读者会误读为"可以商用"。因此审计输出对这类模型单独打 `[NC]` 标记。
> **这是我在测试中发现的呈现缺陷并修正的**——合规报告的误导性比缺失更危险。

**切换场景的实测差异**（同一批候选模型）：

| 部署情形 | 被拒模型 | 触发规则 |
|---|---|---|
| 中国大陆 / 商用 / 50 万美元 | flux2-klein-9b、yue2-3b、lens、minimax-music-3 | `NONCOMMERCIAL_IN_COMMERCIAL_CTX` 等 |
| **美国** / 商用 / 50 万美元 | 上述 + **minimax-h3** | `REGION_EXCLUDED` |
| 中国大陆 / 商用 / 3000 万美元 | 上述 + **ltx-video-2b** | `REVENUE_THRESHOLD_EXCEEDED` |

> 这张表就是"为什么授权必须是代码强制"的最好证明：**同一个模型清单，在不同部署情形下的合法子集完全不同**。人工维护三个版本的模型白名单，必然出错。

**本机场景的实际影响**：中国大陆在 MiniMax H3 授权范围内，年营收 < 2000 万美元即可商用，个人与小团队的实际限制几乎为零。因此**本机的首选视频模型 H3 是合规的**。但门禁仍须实现——因为一旦部署地区或商业化规模变化，约束立即生效。

### 12.2 与 ComfyBench / GenAgent 的差异（答辩必答）

| 维度 | ComfyBench (CVPR'25) | GenAgent | 本平台 |
|---|---|---|---|

**答辩话术**：
> "ComfyBench 证明了 LLM Agent 可以设计 ComfyUI 工作流，但它评的是**单次工作流设计的正确性**。我的工作解决的是**跨 100 个镜头的长程一致性与成本可控**问题，为此我提出统一 IR 让语义约束可编译、可校验、可回传，并用自研轻量 Transformer 替代 LLM 承担高频调度决策。两者问题设定不重叠，我的工作可视为 ComfyBench 结论在**内容生产场景**下向**长程与成本维度**的延伸。"

### 12.3 不可替代性来源（护城河）

1. **统一 IR + 编译规则表**：新增模型/节点类型只需加规则，不改平台代码
2. **约束一等公民**：一致性从"提示词里的一句话"变成"可执行断言"
3. **生产日志 → 训练数据飞轮**：竞品丢弃日志，本平台把它变成 Embedder/Scheduler 的训练集，**用越久越准**
4. **降级透明**：环境能力不足时明确告知影响，而非静默产出错图

### 13.3 实验矩阵

| 实验 | 变量 | 对照 | 预期结论 |
|---|---|---|---|

### 13.4 统计要求

- 每配置 ≥ 20 集（或 ≥ 2000 镜），报告均值 ± 标准差

- 所有实验固定种子，**IR 哈希与产物哈希随论文/毕设材料一并归档**（可复现性）

1. 用平台产出一集漫剧（任务完成率、耗时、SUS 量表）
2. 对比现有工具（kt-ai-Studio / 手动 ComfyUI）的主观评分
3. 半结构化访谈，提炼可用性问题

## 第 16 章 答辩预案

### 16.1 预期问答

**Q1：ComfyBench 已经做了 LLM Agent 在 ComfyUI 中的工作，你的创新在哪里？**
> 见 12.2。核心差异：他们评单工作流设计正确性；我解决长程一致性 + 成本可控。且我提出统一 IR 把语义约束变成可编译、可校验、可回传的一等公民，这是他们没有的。

**Q2：为什么不用 LangGraph / Dify 这类现成编排框架？**
> 它们面向 LLM 状态机（节点 = LLM 调用），无法表达扩散执行图（节点 = 张量算子 + 显存约束）。而且我需要**语义图与执行图同构**，这要求自己控制 IR 的规范化、哈希、编译与降级语义。用现成框架会在最核心的地方失去控制权。

**Q3：你的 Transformer Agent 参数量这么小，凭什么比 LLM 好？**
> 不是"比 LLM 好"，而是**任务不同**。LLM 擅长开放式语义理解，我保留它们做剧本和分镜；但**每镜多次的调度决策**是高频、结构化、可离线学习的——用 12M 参数的策略网络把延迟从秒级降到毫秒级、把成本降到零，这本身就是收益。E3 实验会给出成本/时延/质量的完整对比曲线。

**Q4：一致性怎么客观度量？会不会是自己说了算？**
> 三层证据：① 确定性算子（token-diff、帧数、时间码、人脸相似度）——完全客观可复现；② 一致性嵌入距离——连续、可统计；③ 跨模型盲读 + 人工盲评——报告 Cohen's κ。而且**生成者与审核者强制不同模型族**，杜绝自证。

**Q5：为什么不用现成的 ComfyUI 工作流直接跑，非要搞 IR？**
> E2 消融实验直接回答：模板填充范式在节点漂移时**直接失效且静默产错图**（其工作机制要求在目标环境保持固定节点 ID 与端口签名，而这些会随自定义节点版本变化）。IR 的价值有三：① 语义约束可校验；② 节点变化时可降级并显式告警；③ 缓存键可精确到语义级，改一个镜头只重跑一个镜头。这三点在 60–120 镜的长程生产里是数量级的差异。

**Q6：单集成本多少？跟商业方案比呢？**
> 报告分项：LLM 成本、GPU 电费/折旧、云 API 成本。全本地路径的边际成本接近零（除电费），这是相对云端方案的实质优势。实验会给出草稿档/高清档/混合档三套成本曲线。

**Q7：工作量这么大，你完成了吗？没完成的部分怎么办？**
> 用 M0–M8 里程碑表回答进度。关键路径 M1→M2→M5 已完成的部分作为核心演示（IR 编译 + 崩溃恢复 + 一集成片）。M6 自研 Agent 以影子模式呈现，展示"已完成训练管线与离线评测结论"，并明确说明在线切换是下一步。

**Q8：为什么选择 Apache-2.0 而不是 MIT 或 GPL？**
> Apache-2.0 含明确专利授权，商业友好，适合毕设后继续演进或被企业采用；MIT 缺专利条款；GPL 会阻碍落地。同时把 IR 规范用 CC-BY-4.0 独立发布，鼓励第三方实现编译器形成生态。

**Q9：如果 ComfyUI 未来改架构 / 出官方 SDK 抽象层，你的工作还有价值吗？**
> 有价值，而且更容易落地。官方 SDK 抽的是**执行层**（如何提交图），我抽的是**语义层**（如何把创作意图变成约束可校验的图）。两者是叠加关系：官方 SDK 成熟后，我的编译层可以少写通信代码，把精力集中在语义映射与门禁上。IR 与契约规范可以适配任何执行后端。

**Q10：这个平台和"一键成片"工具有什么本质不同？**
> 一键成片工具给你一个不透明结果；本平台给你**可解释、可干预、可复现、可验收**的产线。具体体现：每条约束都有断言证据；每次降级都有通知；每个产物都有输入指纹；每个镜头都能追溯到 IR 哈希。这决定了它能不能用于**真正的批量生产**——而不是演示。

### A. 术语表

| 术语 | 含义 |
|---|---|
| **IR** | Intermediate Representation，统一中间表示 |
| **双层同构 DAG** | 语义图与执行图编译自同一 IR，结构同构但粒度不同 |
| **条件指纹** | 镜头生成的输入条件哈希，决定缓存命中 |
| **产物时效清单** | 记录产物全部输入指纹的元数据，用于判定 current/stale |
| **能力矩阵** | 目标 ComfyUI 环境的节点目录快照（来自 `/object_info`） |
| **降级通知** | 编译期因环境能力不足而回退时产生的显式告警 |
| **硬门禁** | 确定性算子判定，失败则阻断后续阶段 |
| **跨模型盲读** | 审核模型族 ≠ 生成模型族，且不告知审核者生成参数 |
| **影子模式** | 新调度策略与线上策略并行决策但不生效，仅用于收集数据 |
| **Sketch-Lock** | 先出黑白构图草图并锁定，再生成正片 |
