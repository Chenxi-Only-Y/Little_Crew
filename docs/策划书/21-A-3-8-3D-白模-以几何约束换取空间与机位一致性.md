## 附录 A · 3.8 3D 白模：以几何约束换取空间与机位一致性

> 旧白模设计（模板库选帧 / 纯 CPU 职位），实际实现是另一套，见 §5.10.17~20


**问题定位**：本项目的 P1（长程一致性崩塌）有两个正交的子问题，而纯 2D 参考图
只能解决其中一个：

| 子问题 | 2D 参考图能解决吗 |
|---|---|
| **外观一致性**（角色脸型、服装） | ✅ 能（`identity.reference`） |
| **空间一致性**（站位、轴线、纵深、机位） | ❌ **不能** |

一张参考图无法约束"角色在这一镜朝左、下一镜朝右"（跳轴），也无法保证
"第 3 镜与第 17 镜是同一机位"。**3D 白模补的正是这一块。**

#### 3.8.1 核心设计决策：白模是「确定性渲染步骤」，不是「IR 里的一棵 3D 树」

这是本节最重要的架构决策，它决定了整个方案的代价。

```
❌ IR 中加一棵 scene3d 树（顶点 / 相机矩阵 / 骨骼）
   → schema 大改 · 浮点哈希失稳 · 协议破坏性变更 · 全部测试复查

✅ IR 声明**语义镜头意图**，白模是一步**确定性渲染**
   → IR 几乎不动 · 白模可哈希可缓存 · 与现有抽象同构
```

**为什么后者正确**：本平台的核心抽象是「**声明式输入 → 确定性编译 → 可哈希产物**」。
白模恰好符合该模式 —— **同一套 `(镜头规格 + 角色参数 + 模板 id)`
必然产出同一段白模序列**，因而天然可哈希、可缓存、可复现。

这与 `ir` 的六步规范化、三级缓存键是同一套机制，**不是新增机制**。

#### 3.8.2 数据流

```
IR（语义层，改动极小）
  shot: { character, pose, path, camera, shot_size, lighting, duration }
        │
        │ ① 预演师 Agent（LLM 只做**选择**，不产生坐标）
        ▼
  预演意图（结构化消息，复用 agent/messages.py）
        │
        │ ② 几何层（确定性代码，**无任何模型参与**）
        ▼
  白模场景（参数化代理 + 模板驱动关键帧）
        │
        │ ③ Blender headless（Workbench 引擎，**CPU**）
        ▼
  控制序列（Gray 灰度 / Depth 深度 / Normal 法线）
        │
        │ ④ H3 ControlNet
        ▼
  视频
```

#### 3.8.3 三个关键设计点

**① LLM 只选模板，不产生坐标**

LLM 的数值空间推理不可靠 —— 让它输出相机矩阵会得到"看似合理但穿墙"的结果。
正确分工是：

| 角色 | 职责 |
|---|---|
| **LLM（预演师）** | 从模板库**选择**：`{pose: "回头", camera: "过肩推进", shot_size: "medium_close"}` |
| **确定性代码** | 模板 id + 参数 → **坐标与关键帧** |

坐标计算、碰撞检测、轴线校验全部确定性 —— **可验证、可复现、可缓存**。

**② 几何用参数化代理，不用文生 3D 模型**

| 方案 | 判断 |
|---|---|
| 文生 3D 模型（Hunyuan3D 等） | ❌ 输出带纹理的精细资产，**且一致性是弱项**（同一角色生成两次得到两个人） |
| 单图重建 3D | ❌ 需要额外模型，本机内存紧张，质量不稳 |
| **参数化代理** | ✅ **参数相同 ⇒ 几何必然相同**，一致性完美；毫秒级生成；与哈希体系天然契合 |

白模只需要几何，不需要纹理 —— 因此"低模胶囊体"不是妥协，而是**恰好够用**。

**③ Blender 用 Workbench（CPU），不碰 GPU**

本机 8 GB 显存同时只能加载一个模型。若白模渲染用 EEVEE（GPU），
会与 ComfyUI **争夺显存导致来回卸载重载**。

Workbench 渲染的深度图/灰度图**不需要光追**，CPU 完全够用，
且让预演师成为**纯 CPU 职位**，与 GPU 调度彻底解耦。

#### 3.8.4 可行性依据（官方样片实证）

阿里 PAI 为 H3 发布的 `Fun-ControlNet-Union-2.0` 支持 **8 种控制条件**，
且官方仓库附带**控制输入与生成结果的对比样片**：

| 控制条件 | 对白模的意义 |
|---|---|
| **Gray（灰度）** | ✅ **白模渲染出来本就是灰度图 —— 可直接作为控制输入** |
| **Depth（深度）** | ✅ 更精确的空间约束 |
| **Layout（布局框）** | 站位控制，最省事（彩色框即可，无需 3D） |
| Canny / HED / MLSD | 边缘类，轮廓控制 |
| Pose | 骨架，动作控制 |

**关键实证结论**（取自官方样片逐帧比对）：

- **Depth 控制**：狗的位置、朝向、**大小变化**严格跟随深度序列；
  背景透视一致；生成画面质量**未因控制而退化**
- 但**外观每帧不同** —— 深度管的是「**东西在哪、多大、怎么动**」，
  **不管「长什么样」**。因此：

> **3D 白模与 2D 参考图是互补关系，不是替代关系。**
> **参考图锁「长相」，白模锁「空间」。二者叠加才是完整的一致性方案。**

**`control_context_scale` 可调**（1.0 最强 / 0.0 完全关闭）——
这使"白模影响多大"成为一个**可调参数**而非硬约束。

#### 3.8.5 接入方式：一个新工具，不是一套新架构

| 组件 | 设计 | 改动量 |
|---|---|---|
| **通道** | `runtime/channels/blender.py`，子进程调用 | 小（双通道抽象已预留 `PROCESS`） |
| **工具** | 注册 L3 工具 `blender.render` | 小 |
| **职位** | 名册新增「预演师 / Previs Artist」，`ExecutionKind.PROCESS`（纯 CPU） | 一条声明（18→19） |
| **IR** | 新增 1~2 个 kind + `bindings` 加代理参数 + 相机**语义**字段 | **中**（远小于"加一棵 3D 树"） |
| **编译规则** | 加 2~3 条映射到 `blender.render` | 小 |
| **前端** | **参数表单 + 服务端渲染回图**，**不做 3D 编辑器** | 小 |
| **模板库** | 复用[鲲鹏导演台](https://github.com/pengfeiqiao/kunpeng-director)的动作/运镜模板（**MIT 许可，可合法复用**） | 数据工作 |

**⚠️ GPL 隔离**：Blender 是 GPL 软件，其官方许可明确要求"发布的 addon 必须 GPL"。
因此本平台**只以子进程方式调用 Blender，不写 addon、不链接、不分发其二进制** ——
子进程边界使平台保持 Apache-2.0。

#### 3.8.6 网页接入：分两阶段

**阶段 1（推荐先做）：参数表单 + 服务端渲染**

```
浏览器                        平台后端
  ├─ 选角色 / 动作模板 ────────►│
  ├─ 选运镜 / 调时长 ──────────►│ Blender 渲染（CPU）
  │◄─── 白模预览图 / 预览视频 ───┤
  ├─ 满意 → 提交生成 ──────────►│ H3 ControlNet → 视频
  │◄─── 成片 ───────────────────┤
```

前端**零 3D 代码**。用户看到的是渲染出的图片，不是网页里的 3D 场景。
延迟约 3~10 秒（Workbench 单帧 0.5~2 秒），**可接受**。

**阶段 2（可选，将来）**：若确实需要拖拽编辑，再引入 Three.js
（但要**手写深度/法线 GLSL**，且分布需与 ControlNet 训练分布对齐）
或直接集成鲲鹏导演台作为编辑前端。

> **为什么阶段 1 优先**：Three.js 的深度纹理是**为阴影贴图优化**的
> （非线性、视图空间），而 ControlNet 是在 Blender 式 Z-pass 上训练的。
> 用 Three.js 产出可用控制图**不是配置问题，是重写渲染通道**。

> **白模预演比视频生成快 60 倍以上，成本几乎可忽略。**

##### 为什么本机不行：三道门槛，逐一定位

```
① 未打 DiffSynth 补丁  →  段错误 0xC0000005
② 打上补丁            →  MemoryError
③ 改用 lite 版     →  1.92 GB，✅ **实测跑通，12~16 s/张**
```

**根因是内存，不是显存**：

| 资源 | 本机 | P3 需要 |
|---|---|---|
| **系统内存** | **15.8 GB** | ControlNet 6.25 + transformer 22.93 + 文本编码器 7.49 GB |
| 显存 | 8 GB（实可用约 6.9 GB） | 低显存 offload 策略下勉强，但被内存拖累 |
| 磁盘 | 72.7 GB 可用 | ✅ 够 |

##### ⚠️ 必须记录的坑：DiffSynth 补丁（**保留备查** —— 最终走 ComfyUI 通道，未用到）

本机（Windows + torch 2.9.1 + safetensors）下，`safe_open(...).get_tensor()`
对**大于约 4 GB** 的 safetensors **必然失败**：

| device | 表现 |
|---|---|
| `"cpu"` | **进程段错误退出（0xC0000005）** |
| `"cuda"` | `RuntimeError: invalid python storage` |

而 P3 的两个文件都超限：**ControlNet 6.25 GB、transformer 22.93 GB**。

**补丁**：`D:\AI\local-gen\app\diffsynth_patch.py`
（把 `DiskMap` 的句柄换成纯 Python 的 seek/read 读取器，不用 mmap）。

> **必须在 `import diffsynth` 之前打补丁** —— 否则只会看到一个光秃秃的段错误，
> 极难定位（本次已踩）。

**补丁自身的代价**：它用 `bytearray(raw)` 复制一份张量数据，
所以 6.25 GB 的文件在 15.8 GB 内存下就 `MemoryError`。
**内存充裕的机器上无此问题**，但这一点必须知道。

##### ⚠️ 第二个坑：`ModelConfig` 没有 `cache_dir`（**同上，备查**）

它按 `local_model_path / model_id / origin_file_pattern` 定位文件
（见 `ModelConfig.download`）。**必须在装载管线前设置**：

```powershell
$env:DIFFSYNTH_MODEL_BASE_PATH = "D:\AI\local-gen\models"
```

不设的后果：DiffSynth 到当前目录的 `./models` 找，**找不到就静默重新下载几十 GB**。

**本次还踩了一个相关坑**：用 `snapshot_download(cache_dir=...)` 下载会把文件放进
**ModelScope 的嵌套缓存布局**（`models\models\PAI--xxx\snapshots\master\`），
**与 DiffSynth 期望的路径不一致**，必须手动移到 `models\PAI\<id>\`。

##### 附带修复：白模 Depth 通道退化成剪影（真实缺陷）

**症状**：Depth 通道几乎是纯色剪影，没有深度梯度。

| 通道 | 主体灰度跨度 | 标准差 |
|---|---|---|
| **Depth（修复前）** | **5 ~ 22 级** | **0.9 ~ 3.0** |
| Gray（对照） | 132 ~ 138 级 | 16 ~ 22 |

**根因**（不是 bug，是归一化区间选错）：旧做法取
`[d0 − 1.2h, d0 + 1.5h]`，对 1.68 m 的人是 **5.46 m 跨度**；
而角色自身景深仅约 0.5 m —— **只占 9%**，理论灰度跨度就是约 23 级，**与实测吻合**。

**这类缺陷不报错，只是静默地把控制信号变弱** —— 而 depth 条件恰恰靠梯度工作。

**修法**：改为按主体包围盒实测景深（`auto_depth_range`），两端留 12% 余量。
**效果：主体灰度跨度 10.2 → 45.8 级（4.5 倍）。**

修复过程还踩了两个陷阱，都已写入代码注释：

| # | 陷阱 | 后果 |
|---|---|---|
| **1** | `matrix_world` **不随 `location` 立即更新**，须先 `view_layer.update()` | 读到单位矩阵 → 转相机空间等于没转 → 算出**负距离** → 被夹成 0.246 m 荒谬区间 → **像素全截断成纯黑纯白** |
| **2** | 几何是**逐帧重建**的，默认站姿的包围盒不代表整镜 | 走路时手臂摆动改变景深 → 改为**跨动作时刻采样取并集** |

上面"内存装不下"的判断**已被推翻**。走 **ComfyUI 通道**（而非 DiffSynth 脚本）后，
lite 版在本机 8 GB 显存 / 15.8 GB 内存上**稳定跑通**：

| 项 | 结果 |
|---|---|
| 每张耗时 | **12~16 s**（比不加 ControlNet 的 6~8 s 慢约 2 倍） |
| 显存 | 无 OOM |
| 内存 | 无 OOM |

> **为什么换通道就通了**：DiffSynth 脚本要在**同一个 Python 进程**里同时持有
> 22.93 GB 的 fp32 底模与 ControlNet，而 ComfyUI 用的是 **int8 量化底模
> （5.9 GB）+ 分块卸载**。**同一个模型，装载方式决定了可行性。**

**这正是本项目"双通道正交"设计的价值兑现**：换通道不改流水线。

##### ⚠️ 三个必须记住的调优结论（都靠看图得出，非指标算出）

**① `scheduler` 必须是 `simple`，`karras` 会产出崩坏的画面**

最隐蔽的一条。同样的图、同样的种子、同样的提示词，**只换调度器**：

| scheduler | 结果 |
|---|---|
| `karras` | ❌ **大片暗块 + 荧光错色 + 人物数量错乱**；模糊节点还会渲染成一个亮绿球 |
| `simple` | ✅ 完全干净 |

`shot_to_ir` 原先的默认值就是 `karras` —— **所以这是默认值错误，不是参数偏好**。
`simple` 也是 Z-Image-Turbo 官方示例用的调度器。

**② 控制信号要**模糊**，不要用实心剪影**

白模的实心剪影**带内部明暗**，模型会去**描摹骨架的内部细节**（手臂、腿的精确位置），
人物因此被驯化成骨架形 —— 用户的原话是"完全不像人"。

加一道高斯模糊（`ImageBlur`，半径 18 @832×480）抹掉内部结构，只留
"**这一团是中景偏左的一个人，这么大**"：**定位信息保住，外观自由度还给模型**。

做成**图节点**而非平台侧预处理：`blur_radius` 会自动进入 IR 哈希，
改半径必然重渲。平台侧处理则要额外维护一份参数哈希 ——
漏了就是"改了参数却命中旧缓存"，那类失效**无法察觉**。

**③ 强度 0.5，不是 1.0**

实测三档强度（1.0 / 0.6 / 0.35）的**构图、人物大小、位置完全一致**，
只有**姿态自由度**不同 —— 所以**降强度不损失定位**，只让人更自然。

**④ 提示词必须写全场景**（最容易误判成"模型坏了"）

只写"一位少女"时产出**大片暗块 + 荧光错色**，看起来像模型链路出了问题。
补上地点与光线后立刻干净。**遇到"画面崩坏"先查提示词，再怀疑模型。**
