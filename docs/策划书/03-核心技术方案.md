## 三、核心技术方案

### 3.1 核心创新点 C1：双层同构 DAG 与统一 IR

**问题**：语义图与执行图是两种完全不同的图，但现有工具只能表达其中一种。

**方案**：定义**统一 IR**，同时承载两种信息：

```jsonc
{
  "irVersion": "little_crew.ir/v1",
  "graphId": "G-ep001-sh005",
  "scope": "shot",
  "bindings": {                      // 资产绑定：语义层引用，编译期解析为具体文件
    "CHAR-0007": {
      "anchorSet": { "front": "char/CHAR-0007/anchor_front_v3.png" },
      "anchorGeneration": 3,
      "loraFile": "linwan_v3.safetensors"
    }
  },
  "nodes": [
    { "id": "n_prompt", "kind": "prompt.text",
      "params": { "text": "雨夜天台, 米色风衣, 回头, 近景, 缓推" },
      "semantic": { "characterRef": "CHAR-0007",
                    "constraintRefs": ["cr_costume_007"] } }
  ],
  "edges": [ /* 两种边，见下 */ ],
  "constraints": [ /* 可执行断言 */ ]
}
```

**关键设计：IR 有两种独立子类型的边。**

| 边类型 | 编译结果 | 作用 |
|---|---|---|
| `data` | 编译为 ComfyUI 的节点连接 | 决定"怎么算" |
| **`constraint`** | **不编译**，生成**可执行断言** | 决定"算出来的必须满足什么" |

**constraint 边是 IR 区别于普通工作流 JSON 的本质**。它让
"这个镜头必须长得像角色 7"从提示词里的一句话，变成一条可判定、可回滚的约束：

```jsonc
{ "type": "constraint",
  "target": "n_save",
  "assertion": { "op": "identity_similarity",
                 "threshold": 0.82,
                 "against": "CHAR-0007.anchor_set" },
  "enforcement": "hard",          // hard | soft | audit
  "onFailure": { "action": "retry_with", "maxAttempts": 3 } }
```

**配套机制：六步规范化 + 内容哈希**（`ir/canonical.py`）

保证"语义等价 ⇒ 哈希相同"，这是三级缓存与产物时效清单的地基。
三级缓存键：

| 级别 | 键 | 语义 |
|---|---|---|
| **T1** | `md5(irHash ‖ catalogHash ‖ ruleVersion)` | 精确复用：同 IR + 同环境 + 同规则 |
| **T2** | `sha256(irHash)` | 跨环境语义复用（需重校验质量断言） |
| **T3** | 条件指纹 | 按约束条件复用 |

### 3.2 核心创新点 C2：Transformer 调度智能体

**问题**：多智能体编排若只靠 LLM 逐轮对话，成本高、不可复现、无法预算。

**定位（2026-10-19 决策）**：本文方向是**多智能体协作**，
所以 C2 在本项目里的身份是「**调度机制的一种可选实现方式**」—— 它是**手段**，不是研究对象。

**方案**：设计 **Agent 决策接口协议**（三原语：能力注册表 / 调用信封 / 黑板），
使调度、一致性编码、轻量判定三处**可替换**；当前以**规则基线**实现该协议。
自研 Transformer 作为该协议上的**可选实现**，其设计如下：

| 模块 | 规模 | 职责 |
|---|---|---|
| **Scheduler** | ~12M | 图编码器 + Actor-Critic，决定"下一步该调哪个 Agent" |
| **Consistency Embedder** | 256 维 | 把角色/场景/风格编码为可跨镜比对的一致性向量 |
| **Light Verifier** | ~5M（ViT-Tiny） | 轻量判定"这张图合格吗"，替代部分 VLM 调用 |

**为什么本文不训练它 —— 有数据支撑，不是「没时间」**

C2 要解决的是「只靠 LLM 逐轮对话，成本高、不可复现、无法预算」。
**本文用规则基线实现同一协议，并对其中两项做了量化验证**（`research/agent-ab/`）：

| C2 声称的痛点 | 规则基线的实测 |
|---|---|
| **无法预算** | 预算偏差 **恒 0**（17 对配对） |
| **不可复现** | 每集镜头数波动 **3.7× → 1.1×** |

**结论**：该问题的瓶颈**不在调度决策质量，而在信息传递与产出可控性** ——
这也解释了本文为何优先实现确定性门禁（C3）而非学习式调度（C2）。

训练 12M 策略模型需要**大量编排轨迹**，而本项目可用的完整编排轨迹仅十余条，
样本量不足以支撑训练（「规则产生的数据学出来还是规则」，零增量收益）。
设计与数据构造方案见 §5.10.2。

### 3.3 核心创新点 C3：确定性验收门禁

**问题**：出图的模型自己判定合格，等于自我签收。

**方案**：三层把关，**生成方与审核方物理隔离**：

| 层 | 机制 | 性质 |
|---|---|---|
| L1 | **确定性断言算子** | 客观、可复现、零成本（如 `identity_similarity` 阈值判定） |
| L2 | **一致性嵌入** | 连续可度量，可追踪跨镜漂移趋势 |
| L3 | **跨模型族盲读** | 生成方与审核方**必须不同模型族** |

**硬性约束**（代码强制，非文档约定）：

- 加权总分**由服务端权威计算**，不信任模型自报（模型在评分任务上有系统性乐观偏差）
- 偏差 > 5 分则报告作废重审
- `review` 包**不做生成**，`runtime` 包**不做判定** —— 从结构上杜绝既当运动员又当裁判

### 3.4 多智能体协作机制

**19 个职位，按真实剧组建制组织。**

Agent 不是抽象编号，而是**剧组的真实职业** —— 这不是命名偏好，而是一条设计决策：

> 真实剧组里"谁管什么"已经过几百年打磨。照搬这套分工，
> **比自创更不容易出现职责重叠或真空**；而且产出物名可直接对应
> （摄影指导交镜头、剪辑师交成片、场记交场记单），不必另发明一套产物分类。

#### 3.4.0 什么算「协作」—— **四条协调机制**（本章立论）

**先说一个必须自己说破的问题**：19 个职位排成一列往下走，
**那叫流水线，不叫协作**。评审一定会问「你这算协作还是流水线」。

所以本文**不拿职位数量当规模**，而是指着下面**四条真正的协调机制**说话 ——
每一条都要求**下游受上游约束**、或**同一产物被多方共同决定**：

| # | 协调机制 | 为什么是「协调」而不是「传递」 | **实测证据** |
|---|---|---|---|
| **①** | **上游意图约束下游自由**：导演定每场镜头预算，分镜在预算内分配 | 分镜**不能自由决定**切几个，受上游意图约束 | 真机 5 场剧本：预算 `S01=4 S02=4 S03=3 S04=5 S05=4`，实际产出**逐场完全一致，零偏差** |
| **②** | **两个职位共同决定同一产物**：灯光的影调进入分镜提示词 | 同一份分镜由灯光与分镜**共同**决定 | A/B 同 seed：亮度 **−37.08**、色温 **−10.96**；人眼复核对应「夜/窗在左后方/只剩信纸被照亮」**逐项兑现** |
| **③** | **负反馈闭环**：门禁判 RETRY 时带**返工指令**回退上游 | 有反馈回路，不是单向流 | 三态裁定（KEEP/RETRY/ESCALATE）已实现；返工指令进证据链 |
| **④** | **同一产物被多视角并行审**：双维审查 + 3 个顾问批评家 | 一次产出被多个**独立视角**同时检查 | 音轨门禁 **21/21**；无声片段**被拒**（`-an` 造样本验证） |

**判据**：一条机制要算「协作」，必须满足 —— **去掉它，下游产出会不同**。
上面四条都满足，且都做了 A/B 或真机验证。

#### 3.4.2 协作机制的四层结构

| 层 | 机制 | 解决什么 |
|---|---|---|
| 1 | **剧组分工**（上表） | 职责隔离 |
| 2 | **审查循环**：编剧出稿 → **并行双维审查**（剧本顾问 ‖ 文学策划）→ 导演合并 → 返工 | 单一视角会自证 |
| 3 | **QC-5 五维品控**：完整性 25 / **一致性 40** / 品质感 25 / 可执行性 / 合规性，**权重按阶段调整** | 度量可审计 |
| 4 | **结构化消息**：职位之间**不传自由文本**，只传带 schema 的消息 | 可追溯、可量化、可复现 |

**第 4 条是分水岭。** 若职位之间传自由文本，"协作"退化为"多轮对话"——
无法审计、无法量化、无法复现。

#### 3.4.3 三条不可绕过的硬规则（代码强制）

**① 服务端权威算分** —— 不信任模型自报

模型在评分任务上有**系统性乐观偏差**：自报分与其给出的维度明细常常不自洽。

```
实测情形：模型自报 90 分
          但维度明细为 一致性45 / 完整性80 / 品质感70 / 可执行85 / 合规95
          加权权威总分 = 64.5        ← 权威值由维度算出
          偏差 25.5 > 容差 5.0       → 整个报告作废，判定 ESCALATE
```

不可信时**整个报告作废重审** —— 不是因为自报分错了，而是因为
"自报分与自身维度明细不自洽"说明该职位的判定过程不可靠。

**② 跨模型族盲读** —— 生成方与审核方必须不同族

```python
"qwen3-vl-max" 审核 "deepseek-flash" 的产出  →  ✅ 跨族，结论有效
"qwen3-vl-max" 审核 "qwen3-max"  的产出  →  ❌ 同族，判定 ESCALATE
```

**③ 不自我签收** —— 按**产出归属**判定，而非按"是否具备审核能力"

> ⚠️ 这条规则本项目的校验器**曾经写错过**：早期判据是"生成了内容又声明审核能力"，
> 于是把**剧本顾问**与**文学策划**判为违规 —— 而那两位**只**审别人的稿，
> 审核正是它们唯一的职责。错在把"有审核能力"当成了"自我签收"。
>
> 正确判据是**产出归属**：某职位交付的产物，不得由它自己审核。

#### 3.4.4 结构化消息示例

```jsonc
{ "kind": "review_feedback",
  "msgId": "msg_a9cf3c2e...",  "replyTo": "msg_...",   // 审查链可追溯
  "from": "dramaturge",  "to": "screenwriter",
  "verdict": "REVISE",              // PASS | REVISE | REJECT | ESCALATE
  "score": {
    "dimensions": { "consistency": 45, "completeness": 80,
                    "quality": 70, "feasibility": 85, "compliance": 95 },
    "claimedScore": 90,             // 模型自报（仅用于偏差检测）
    "total": 64.5,                  // 权威算分
    "weakest": { "dimension": "consistency", "score": 45 }
  },
  "issues": [
    { "severity": "major", "dimension": "consistency",
      "location": { "scene": "SC-E001-003", "line": 42 },   // 必须结构化定位
      "problem": "角色服装与第 2 场不一致",
      "suggestion": "改为米色风衣" }
  ],
  "repairHints": [
    { "graphId": "G-ep001-sh005", "op": "insert_shot",
      "args": { "after": "SH-E001-003-007", "durationSec": 3.0 },
      "fromIssue": "issue_001" }
  ],
  "reviewerModel": "qwen3-vl-max", "generatorModel": "deepseek-flash" }
```

**三条强制的可执行性要求**：

| # | 要求 | 为什么 |
|---|---|---|
| 1 | `issues[].location` **必须结构化**（场/镜/行/资产） | 散文式定位**无法驱动自动返工** |
| 2 | `BLOCKER` 级问题**必须给 `suggestion`** | 否则编排器产生不出可执行的返工指令（构造时即拒绝） |
| 3 | `repairHints[].op` 走**白名单**，且必须带 `graphId` | **这是协作闭环的落点** —— 每条返工指令都能映射成 IR 变更 |

**第 3 条是关键**：`repairHints` 里的"在某镜后插入镜头"就是**图结构变更**，
可直接翻译为 IR 补丁 → 重编译 → 再审。**审查到执行之间没有人工翻译环节。**

### 3.5 不依赖编排框架的三层调用协议

**明确决策：不使用 LangGraph 等图编排框架。**

**理由**：它用**同一抽象（图）**同时表达两个**正交**的轴：

```
轴 A · 组织分层  —— 决策层 / 协作层 / 执行层   （本质是树）
轴 B · 推理循环  —— 有界状态机，步数上限必须可校验
```

压扁成同一种表示后，**层边界不可强制**、**推理轮数上限不可校验**，
且使真正需要图的 IR 执行 DAG 失去立足点。

**替代方案：三原语**

| 原语 | 职责 |
|---|---|
| **CapabilityRegistry** | 能力发现：谁能做什么 |
| **CallEnvelope** | 三层同一信封：调用链由 span 天然构成，可观测性零额外埋点 |
| **Blackboard** | 共享黑板：乐观并发 + 失效传播 |

**四条层边界硬规则**（代码强制，违反即测试失败）：

| 规则 | 内容 |
|---|---|
| **R1** | 单向依赖：L3 不得回调上层 |
| **R2** | 禁止跳层：L1 不得直调 L3 |
| **R3** | 预算只减不增（子调用预算 ≤ 父剩余预算） |
| **R4** | 深度硬上限（6 层） |

**有界推理循环**：步数上限是**构造参数**而非图上的跳转条件 —— **Agent 无法绕过**。

### 3.6 模型双通道（本地 / API 统一抽象）

**需求**：用户可选择用**本地模型**（零成本、慢）或**云端 API**（快、按量计费）。

**方案：把"模型"与"通道"拆成两个正交维度。**

```
模型（干什么、擅长什么）              通道（在哪跑、怎么调）
  TaskKind        任务域                COMFYUI   本地节点图执行
  Capability      能力画像              HTTP      直连 HTTP
  ResourceProfile 资源画像              PROCESS   本地进程内（预留）
  CostProfile     成本画像
```

**关键判断：本地服务与云端 API 不是两种通道，是同一种通道的两个 endpoint。**

`D:\AI\local-gen` 暴露的是与云端等价的 OpenAI 兼容 HTTP 接口，
因此它与 DeepSeek / 通义走**同一段代码**，只是 endpoint 不同。
**只有 ComfyUI 因为需要"编译成节点图"才是真正不同的通道。**

| 形态 | 示例 | 说明 |
|---|---|---|
| 真·双通道 | `minimax-h3` | 本地 ComfyUI 节点 **或** 云端 HTTP API |
| 两个本地后端 | `z-image-turbo` | ComfyUI 节点图 **或** `local-gen` HTTP 服务 |
| 仅 HTTP | `deepseek-flash` | 无本地权重 |

**通道契约的四条硬要求**：

| # | 条款 | 为什么 |
|---|---|---|
| **R1** | 提交幂等 | 本地重跑浪费数分钟 GPU；**云端重跑重复计费** |
| **R2** | 可中断 | 取消后不得再有产物落地 |
| **R3** | 可对账 | 崩溃重启回收已完成任务，**绝不重复提交** —— 4 小时长跑续跑的基础 |
| **R4** | 进度可观测 | 细粒度进度供前端与超时判定 |

**模型路由**（`compiler/router.py`）：六步求解，**淘汰理由可解释**：

```
task → 通道形态 → 授权门禁 → 能力必满足 → 成本上限 → 软偏好排序
```

"为什么没选它"和"为什么选它"同样重要 —— 否则用户无法理解平台的决策。

### 3.7 模型授权门禁（合规硬约束）

**把模型权重授权变成代码强制的硬约束**，三条强制行为：

| 行为 | 说明 |
|---|---|
| **A. 未核实即拒绝** | 授权目录中无记录、或标记未核实 → `NEEDS_REVIEW`，**不放行** |
| **B. 降级链每跳重过授权** | 因能力降级换模型时，必须重新过门禁 —— 不能"换个能用的"绕过合规 |
| **C. 归属标注自动注入** | 要求标注的模型，其标注文本自动进入交付物元数据 |

**已逐一核验的授权事实**（19 个模型，`LICENSE_CATALOG`）包含几个
"名字几乎一样、后果完全不同"的陷阱：

- **FLUX.2 Klein `4B` = Apache-2.0 可商用 / `9B` = 禁商用**
- **MiniMax H3 排除 US/EU/UK/KR**，中国大陆在范围内；营收 2000 万美元门槛；须界面标注
- **Wan 开源线到 2.2 为止** —— 网上流传的"2.7 开源"是假消息
- **Lens 是 repackage**，原始厂商与授权待查

**API 服务类模型单列一类**：其授权是**合同问题**（服务条款）而非**版权问题**（许可证），
后果也不同（前者可能被停服，后者是版权风险）。因此这类条目一律
`verified=False + NEEDS_REVIEW`，**部署方须逐条核实后再启用**。

#### 一个措辞建议

**「平台」这个词慎用** —— 它通常意味着多用户/部署/计费/权限，我们都没有。

答辩时不会引出"支持多少用户"这类答不上来的追问。
