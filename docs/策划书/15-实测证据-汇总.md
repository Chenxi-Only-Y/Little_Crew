### E6 + E7 · 白模能不能约束画面，强度取多少

> 这两条是**同一个问题的两段**（有没有用 → 用多少），合起来读才完整。

**问题**：白模（几何预演）能不能约束生成画面？控制强度该取多少？

**方法**：**同一份 IR 渲两次** —— 提示词逐字相同、同 seed、640×384、8 步，
唯一差别是 `apply_control` 调不调用。

> **为什么不用"跑两集对比"**：两集之间提示词会变，差异无法归因。

**数字**

| 组 | 像素变化 | 地平线行 | 盲判（花田是否主体 1-5） |
|---|---|---|---|
| A 无控制 | — | **38** | 3 |
| B `1.0` | 98.05% | 50 | **1** |
| B `0.5`（默认） | 84.68% | 25 | **4** |
| B `0.35` | 80.10% | **38** | 3 |

**结论**
1. **控制图确实生效** —— 98% 像素变化，方向与白模几何一致，不是噪声。
2. **强度是主变量** —— `0.5` 在盲判下**高于无控制基线**（4 vs 3）；
   `1.0` 会把"地平线在上方"放大成主体；`0.35` 与基线打平（等于没控制）。
3. 🔴 **三镜复测的结论作废 —— 因为判据在看不懂的镜头上失效了。**

   三镜盲判：镜1 **5=5**、镜2 **1=1**、镜3 **1=1**。
   一开始以为"全打平"说明控制图没有影响，**但这个解释是错的**：

   > **镜 2 的提示词是「岩石的阴影边上躺着一个人……」—— 它根本不拍花田。**
   > 盲判问的是「薰衣草花田是否画面主体」，对这类镜头**恒为 1**，
   > 于是 A/B 必然打平。**打平是判据不适用，不是控制无效。**

   所以：**E7 此前的"0.5 更优（单镜 4 vs 3）"既没有复现，也不能靠这次否定** ——
   两次都用了"只对花田镜头有效"的判据。

3b. **换 v2 判据重判同一批图（与镜头内容无关），结论：控制图既没变好也没变坏。**

   | 镜 | A 无控制 | B 强度0.5 | 谁好 |
   |---|---|---|---|
   | 镜1 | 5 / 5 = **10** | 5 / 4 = 9 | A 略好 |
   | 镜2 | 3 / 3 = 6 | 3 / 3 = 6 | 平 |
   | 镜3 | 4 / 4 = 8 | 4 / 4 = 8 | 平 |
   | **合计** | **24** | **23** | **差 1 分** |

   **能说的**：加控制图（0.5）**没有让画面变好，也没有明显变坏**。
   **不能说的**：不能说"A 更好" —— 差 1 分（满分 30）、单评者、n=3，落在噪声范围。

   > 与前面的结构观察一致：控制图主要**移动地平线/人物位置**，
   > 对"画面成立度"与"空间合理性"这两个**质量维度**几乎没有作用。
   > 换句话说：**它改构图，不改画质** —— 这恰好符合它的设计意图。

4. **教训（已进 §八）**：这是第三个"在不适用的地方当通用量尺"的指标 ——
   前两个是「紫色占比」和「地平线行」。**判据必须与镜头内容无关**，
   否则会在某些镜头上恒为常数，让人把"测不到"误读成"没差别"。

**局限**
- **n = 5、单镜、单人盲判** → 只能看方向
- 通用像素统计**不能**当"构图听话度"指标（两个指标实测失效）

**证据**：`research/p0-2-control-ab/` · `research/previs-ab/step3~4`

### E8 · 白模什么时候坏事（🔴 **待重做**）

**问题**：什么情况下白模会把画面弄坏？

**已有观察**
- `strength=1.0` 时，金黄山坡**占画面 2/3**，花田被压成底部窄条
- 给场景**加两个道具**（花垄 + 岩石）后画面**几乎不变**（12.99% vs 13.27%）

**已有结论（**暂定**）**
- 损害主要来自**强度过大**，不是"白模里有什么"
- 「空平地被模型自由发挥」这个假设**被否定**

**为什么标"待重做"**
- 只有**一镜、一个提示词**；换一镜结论可能翻转
- 该镜提示词本身把场景写成"山坡"（与"花田"意图冲突）→ **混杂变量**

**重做需要**：3~5 个不同场景的镜头 × 三档强度；并先排除"提示词场景冲突"这个混杂因素。

**证据**：`research/previs-ab/step5_props_test.py` · `hard_metrics.json`

#### E8 收口 · v2 判据三镜实测（2026-11-01）

**问题**：`strength=1.0` 到底会不会把画面弄坏？早先只有一镜、且判据不适用。

**方法**：三镜 × (A 无控制) vs (C `strength=1.0`)，**同一份 IR**，
用 **v2 判据**（画面是否成立 / 空间关系是否合理 —— 与镜头内容无关），6 张打乱盲判。

**数字**

| 镜 | A 无控制 | C `strength=1.0` | 结果 |
|---|---|---|---|
| 镜 1 | 5 / 5 = **10** | 5 / 4 = 9 | A 略好 |
| 镜 2 | 4 / 4 = **8** | **1 / 1 = 2** | **A 碾压** |
| 镜 3 | 4 / 5 = **9** | **1 / 1 = 2** | **A 碾压** |
| **合计** | **27** | **13** | **差 14 分（满分 30）** |

**结论**

1. **`strength=1.0` 会毁掉画面** —— 三镜里 **2 镜崩到 1/1**（严重崩坏 + 空间关系完全不合理）。

### 6.10 缓存在渲染链上的效果（原 §五·五）


**这是"改一句只重跑受影响的镜头"从设计意图变成可验证事实的地方。**
数据由 `src/little_crew/runtime/cache_measure.py` 采集，可复现。

**环境**：Z-Image-Turbo（local-gen HTTP 通道）· 3 镜 · 8 步 · 832×480

| 运行 | 场景 | 实算 | 命中 | 命中率 | 耗时 | 节省 |
|---|---|---|---|---|---|---|
| **R1** | 首跑（建立缓存） | 3 | 0 | 0% | **75.7 s** | — |
| **R2** | 什么都不改，重跑 | **0** | 3 | **100%** | **0.0 s** | **75.5 s** |
| **R3** | **只改第 2 镜**，重跑 | **1** | 2 | 66.7% | **13.3 s** | **57.5 s** |

> **R2：重跑一集从 75.7 秒降到 0.0 秒（1889×）。**
> **R3：改一个镜头只需 13.3 秒，而不是 75.7 秒（5.31×）。**

**核心命题成立：改一个镜头，只有它被重跑。**

### 它是怎么做到的（不需要增量分析）

缓存键 = `sha256(irHash ‖ catalogHash ‖ ruleVersion)`，而 `irHash` 是
**内容哈希**，只随语义变化。于是：

```
改第 2 镜的服装  →  第 2 镜 irHash 变  →  只有它未命中
                    其余镜 irHash 不变 →  全部命中，零 GPU
```

**内容寻址本身就是增量的** —— 不需要"依赖图推导"或"影响分析"。
这也是为什么 C1（统一 IR + 内容哈希）与 P4（成本失控）是同一个设计的两面。

### 度量方法学（三条必须遵守的）

| 要求 | 违反的后果 |
|---|---|
| **跨运行测量** | 同一会话内重跑会被 `RenderSession` 自身的 R1 幂等掩盖 —— **测的是空气** |
| **分清算谁的缓存** | 我们的三级缓存（零 GPU）与 ComfyUI 节点级缓存（仍要提交）**来源不同**，混记会让指标虚高 |
| **对照组要真的不写缓存** | 若对照组也在写缓存，后面的"开缓存"自然命中不了 —— 实验组与对照组就变成了同一组 |

### 6.11 断点续跑的实测（原 §五·六）


一集按实测是**分钟到小时级**。在这个时长上，崩溃、重启、误关窗口
**不是异常，是必然**。而"从头再来"的代价不只是时间 ——
**云端按次计费，重跑就是重复付费**。

**所以续跑不是便利功能，是长跑可作性的前提。**

### 真机实测（Z-Image-Turbo · 5 镜）

```
第一次运行：跑到第 3 镜后硬中断  →  完成 3 镜（101.7 s）
   ↓ 模拟崩溃（进程退出，检查点账本已落盘：{succeeded: 3}）
重启：加载账本 → 计划 = 已完成 3 / 需对账 0 / 待重跑 0 / 全新 2
   ↓
第二次运行：只跑缺的 2 镜（25.9 s），其余 3 镜直接命中
最终账本：{succeeded: 5}
```

> **若不续跑、从头再来需重跑 5 镜；实际只跑了 2 镜，省下约 75.8 秒。**

### 两阶段提交：为什么"提交前"就要落盘

```
① 写意图（PENDING，含幂等键与请求指纹）   ← 崩在提交之前 → 无副作用
② 提交，拿到 channel_id 立刻落盘            ← 崩在提交之后 → 必须能找回
③ 完成后记产物引用（SUCCEEDED）
```

**关键是①必须在②之前落盘。** 若只在拿到 channel_id 之后才写，
在"提交成功、还没来得及写"这一瞬间崩溃，重启后就**不知道有个任务在跑** ——
只能重新提交，而服务端其实已经在跑。结果：**双份 GPU**。

（严格说这一瞬间仍无法完全消除；但把窗口从"整个提交往返（可能几十秒）"
压到"一次本地写（毫秒级）"，风险降低几个数量级。）

### 状态机刻意区分两种"未完成"

| 状态 | 含义 | 能否直接重提 |
|---|---|---|
| `PENDING` | 记了意图但没提交成功 | ✅ 安全 |
| **`SUBMITTED`** | **已提交**（服务端可能已经在跑） | ❌ **必须先对账** |

**把这两者混为一谈，就是重复烧 GPU 的根源。**

### 与内容缓存的分工

| | 内容缓存（§5.5） | 检查点（本节） |
|---|---|---|
| 记什么 | **结果**（跑出来的产物） | **过程中的状态**（谁在跑、跑到哪） |
| 键 | 内容哈希 | job_id（幂等键） |
| 解决 | **改一句只重跑受影响的** | **跑到一半崩了不用从头跑** |

**两者互补，不替代。**

### 成片清单为什么也算交付

视频阶段依赖 H3 的 10 秒硬上限与 39 GB 权重，是**另一条独立的链**。
而"这一集由哪些镜、多长、按什么顺序、产物在哪个文件"是
**图像阶段就已完整可用**的交付物 —— 它能被审片、能被验收、能被追溯。

清单**显式标明缺口**（`stage="image"`、`pendingStages=["video","audio"]`），
而不是让人以为已完成。**把缺口写在交付物里，比不写更专业。**

### 五条硬规则（都真的会拦）

| 规则 | 拦什么 |
|---|---|
| `allShotsHaveArtifacts` | 有镜头没产物 → 不算跑通一集 |
| `allShotsWithinDurationLimit` | 镜头超 10 秒硬上限 |
| `artifactsUnique` | 产物文件名重复 → **会静默互相覆盖** |
| `hasContentHashChain` | 缺内容哈希 → 无法追溯"改了什么" |
| `manifestNonEmpty` | 空清单 |

### 6.13 视频合成：从清单到能播放的一集（原 §五·七·二）


§5.7 跑通了 20 镜、产出了成片清单 —— 但**清单不能被播放**。
本节补上最后一环。

### 实测结果

| 项 | 值 |
|---|---|
| 镜头 | 20 / 20 全部合成 |
| **成片时长** | **120.0 秒** |
| 帧数 | **2880 帧 @24fps** |
| 分辨率 / 编码 | 832×480 / h264 |
| 文件 | 2.56 MB |
| **合成耗时** | **3.5 秒** |

> **合成 120 秒成片只要 3.5 秒** —— 因为逐镜编码后拼接用 **concat 流拷贝**，
> 不重编码。这一步的成本几乎可以忽略。

### 为什么这一步重要

**它是唯一把"项目产物"变成"可观赏作品"的一步。**

在此之前，一集的交付物是 `episode.master.json` —— 能被审片、能被验收、
能被追溯，但**不能被播放**。而"一集"最朴素的含义就是"能连着看的一段"。

现在 `python -m little_crew.runtime.episode_demo` 一路跑到 MP4。

### ⭐ 顺带完成的一次语义闭环

IR 的 `camera_movement`（5 种）此前**只是写给模型看的提示词**。
视频合成把它**真的变成了画面运动**：

| IR 语义 | 画面运动 | 实测首尾帧差异 |
|---|---|---|
| `static` | 固定机位 | 0.07（应为静止 ✅） |
| `dolly_in` | 推进，缩放 1.00 → 1.14 | 27.67 ✅ |
| `dolly_out` | 拉远，1.14 → 1.00 | 20.99 ✅ |
| `truck_left` / `truck_right` | 横向平移，方向相反 | 23.17 ✅ |

**这是"语义 → 执行"的一次真实闭环**：IR 里写 `dolly_in`，
画面上真的在推进 —— 而不是一句无人执行的提示词。

**自检里锁住了这个耦合**：IR 声明的每一种运镜都必须在映射表里，
否则会**静默退化成静止画面**（看起来"能出片"，只是不动）。

### 失败分类（与平台其它层一致的思路）

每种失败都带**可执行的恢复动作**，而不是一个裸报错：

| 分类 | hint |
|---|---|
| `TOOL_MISSING` | 设置 `FFMPEG_BIN` 指向 ffmpeg.exe |
| `INPUT_MISSING` | 检查成片清单里的产物路径 |
| `COMMAND_FAILED` | 看 stderr 的实际报错 |
| `TIMEOUT` | 提高超时，或降分辨率/帧率 |
| `BAD_OUTPUT` | 重跑；反复出现则查磁盘空间 |
| `UNSUPPORTED` | 换用 libx264；或换完整版 ffmpeg |

### ⚠️ 两个必须记录的坑（都极难定位）

**坑 1：ffmpeg 会永久阻塞 —— 缺 `stdin=DEVNULL`。**
ffmpeg 在非交互环境下会读标准输入；若 stdin 被继承而永不 EOF
（**后台作业、CI、被管道包住的进程**都会这样），它**永久阻塞且不产生任何输出**。
看起来就是"卡住了"。

**坑 2：测试夹具不是合法 PNG → ffmpeg 烧满 CPU 但永不结束。**
夹具曾用「PNG 魔数 + 零字节」冒充图片。ffmpeg 拿到它之后，
`scale` / `zoompan` 在退化输入上陷入**病态计算**：

```
PID 53788  已运行 187s  CPU 225.7s     ← 正常只需 3.5 秒
```

**表现是"测试卡住"，真相是"夹具不是合法输入"。**
修法是新增零依赖的 `make_test_png()` 作为公共工具。

### 已知限制

- **视频是「静图 + 运镜」，不是真动态** —— 人物不会走、不会做表情
- **无音轨** —— 需要 TTS，是另一条链
- **无转场特效** —— 镜头间是淡入淡出
- **帧率固定 24** —— 未从 `config/project.toml` 读取
