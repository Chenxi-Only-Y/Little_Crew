#### 三、三条**设计发现**（这是这一段的真正产出）

**① 白模需要两种表示，用错一边两头受损**

| 用途 | 该用什么 | 为什么 |
|---|---|---|
| 给人看（位置参考） | 圆柱 | 不假装是人，读位置最清楚 |
| 给模型（ControlNet） | 简化人形 | 圆柱的轮廓会被模型照抄，人体塌陷 |

> **这不是「某方案不行」，而是「两种用途需要不同表示，并实现了分流」。**

**② 「刚好过线」在「没有下限」的模型上会退化成 200px**

对 MiniMax / Wan Animate（对参考视频**无像素下限**）算出 `354×200` ——
数学合规，**但那个尺寸下动作读不出来**。补了一条**我们自己的**实用下限（短边 480）。

> **平台契约与自己的判断要分开写** —— 否则以后分不清「这是平台要求的」还是「我们觉得该这样」。

**③ 规则没错，错在没限定它对谁成立**

`too-tall-in-frame` 一开始对所有景别生效 → `close` 变成无解（要求人占高 ≤100%，
而特写本来就是人比画面高）→ 模型每次把 z 往远推来躲这条错规则。
修法：只对**全身类景别**生效。同类错误另有「门是平面不是体积」。

### 5.10.17 白模（P2 预演师）的**范围收缩**（2026-10-19 用户决定）

> **用户原话**：「白模现在只用于**位置和镜头运动**为参考，不需要动作姿态、纹理之类的
> 这种细节。所以不用做太细了。人物场景用**简单几何体**，不用描绘纹理细节了」

#### 这意味着什么

原来的白模目标（§3.8.8 / §5.10.4）里有一堆做不动的项，**现在全部划出范围**：

| 原目标 | 现状 | **新范围** |
|---|---|---|
| 动作姿态（`look_back` 能转向） | ⚠️ 从背面机位看不出转向 | ❌ **不需要** |
| 纹理 / 材质 / 灰度层次 | ⚠️ 灰度 vs 深度实测结论相反、原因未查明 | ❌ **不需要** |
| 人物精细度曲线（U3） | ⚠️ 无答案 | ❌ **不需要** |
| 3D 白模 vs 2D 深度估计净增益（U4） | ⬜ 未验证 | ❌ **不需要** |
| 人物尺度控制（不偏大） | ✅ **已修**（`alpha.90`，`sensor_fit` 一行） | ✅ 仍需要（位置参考的前提） |
| **位置 / 站位** | — | ✅ **核心** |
| **镜头运动 / 机位** | — | ✅ **核心** |

#### 新定义（一句话）

> **白模 = 用简单几何体表达的"谁在哪、机位在哪、怎么动"的示意图。**
> 它不承诺任何外观，只承诺**空间关系**。

#### 由此确定的三条设计约束

**① 人物 = 几何体，不是人体**

用**胶囊/圆柱 + 一个球表示头**即可。不需要关节、不需要朝向细节、不需要表情。
需要保留的只有：**站位（x, z）· 相对机位的远近 · 大致高度**。

> 之前卡在"`look_back` 从背面机位看不出转向" —— 这个问题**在新范围里不存在**，
> 因为"朝向"本身不在参考信息里。

**② 场景 = 平面 + 体块**

地面用一个平面（带简单的场次标注），建筑/树/门用**盒体**。
不需要材质、不需要贴图、不需要光照模拟 —— 那些由 `art.bible`（美术指导）与
`lighting.plan`（灯光师）在**文本层**给出，白模不重复。

**③ 机位 = 一个视锥，不是一张"好看的图"**

白模帧要能看出：**摄影机在哪、朝哪、景别多宽**。
所以视锥/取景框必须画出来 —— 这是它**唯一的存在理由**。

#### 为什么这个收缩是对的

原来的白模目标里，**六个子项中有四个（姿态/纹理/精细度/3D增益）都卡住了**，
而它们恰好都不是"位置与机位参考"必需的。

> **一个卡住的目标，往往是因为目标里混进了不必要的东西。**
> 砍掉之后，剩下的部分**本机就能做**（几何体渲染零成本、无模型依赖）。

#### 与既有实现的关系

现状：白模帧由 `EpisodeRunner._previs_frame_for()` 的**内置启发式**选取
（按动作映射 + 取峰值帧），**未走多智能体协作**。

P2 要做的是把它变成**一个职位**：输入分镜 + 导演讲预算 + 灯光/美术的文本设定，
输出**每镜的几何体示意图 + 机位**。

| 没动 | 1 |
| 最差一次 | **−13.5 分** |

**这是「协作有代价」的直接证据。** 负反馈闭环（机制③）存在，
但**它并不总是改善结果** —— 多数情况下返工后分数更低。

**逐次明细见 `research/retry-cost/TABLE.md`**（10 次运行每一轮的分数，可复核）：

| 关键事实 | 数据 |
|---|---|
| 两次**「合格→不合格」** | run 5：**70.80 → 62.60**；run 7：**67.90 → 54.40** |
| 一次**真救回** | run 6：55.60 → **80.20**（+24.60） |
| 取末轮 vs 取最佳轮 | **平均损失 6.90 分**（最大 −17.60） |

**所以它不是"害处"，而是"赌博"** —— 10 次里 1 次大幅救回、2 次大幅破坏。

**当前实现已缓解**：`alpha.52` 起交付取 `best` 轮而非末轮（`_best_round()`），
代价是每集多消耗 1~2 轮推理（每轮约 330~350 秒）。

**可能的原因**（未验证）：返工指令只给「哪里不好」，没有给「往哪个方向改」，
模型容易在修一个问题的同时破坏另一个。

> **这条在论文里的价值高于再多一个成功案例** ——
> 大多数多智能体工作只报协作收益，**本项目有一组量化过的负面结果**。

#### ③ 端到端链路是**顺序流**，不是自由协商

除这四条机制外，职位之间主要是**顺序交接**。
本文不声称这是"多智能体协商"，而明确称为「**结构化分工 + 质量门禁**」。

### 5.10.8 裁定口径：三条决策 + 一个诚实的局限（2026-10-16）

接真模型后暴露的第一个问题**不是模型不行，是裁定规则不可用**。
本节记录三条口径与它们的实测依据。

#### 决策 ① 只有 `BLOCKER` 级意见阻断，其余是 `advisory`

| 版本 | 判据 | 实测结果 |
|---|---|---|
| 初版 | `verdict is PASS`（等价「**零意见**」） | 语义审核方一上就**永久堵死** |
| 二版 | 无 `BLOCKER` 级意见 | **仍不收敛** —— 一个能干的剧评人**总能找到下一条** |
| **三版** | 无 `BLOCKER` **且** 总分 >= **80** | ← 现行 |

**为什么初版不可用**：

> **一个尽责的剧评人几乎永远不会说「完全没问题」。**
> 它总能指出"这里节奏可以更好"。

于是"有意见 → REVISE → 不 accepted"导致**任何一轮都过不了**，
`EpisodeRunner.run` 在剧本阶段就 early return，
**分镜阶段根本执行不到** —— 这才是"分镜 0 个"的真正原因。

**两类判断必须分开**：

| 类型 | 例子 | 它说的是 | 有否决权吗 |
|---|---|---|---|
| **确定性门禁** | 分辨率、时长、角色数、格式 | 「**违规**」（客观、可复现） | ✅ |
| **语义批评** | 剧评人、文字编辑 | 「**可以更好**」（主观、连续） | ❌ 无条件否决 |

**⚠️ 但严重度定错过一次，值得记**：第一版把剧评人的结构意见定成
`MAJOR`（不阻断），**两个测试套件立刻失败** —— 因为编剧**故意**在首稿
留结构缺陷、剧评人抓出来、返工修好，那是**设计的闭环**。
定成不阻断等于第 1 轮就放行，闭环形同虚设。

**真正的判据不是「确定性 vs 语义」，而是「该修 vs 可以更好」**：

| 缺陷 | | 严重度 |
|---|---|---|
| 缺冲突/代价/转折 | **该修**（设计上就会去修） | `BLOCKER` |
| 服装与上镜不一致 | **该修**（观众看得出来） | `BLOCKER` |
| "这句可以更凝练"、"节奏可以更紧" | 可以更好 | `MAJOR`（advisory） |

> **同一个缺陷不该因为"谁报的"而有不同严重度 —— 严重度是缺陷的属性。**

#### 决策 ② 分数完全由代码算，不由模型自报

| 环节 | 谁做 |
|---|---|
| 「这一场有没有冲突」 | **模型**（判断） |
| 「那值几分」 | **代码**（算术） |

与 `blind.py` 的处理**同源**。理由：模型报的数字**信噪比低** ——
同一份稿两次调用可能给 70 与 85。**让模型做它不擅长的算术，
会把不可复现性引进整套判定。**

#### 决策 ③ 轮次用尽 → `ESCALATE`，不是继续 `REVISE`

**第 N 轮还不通过，说明这不是「再改一次就好」的问题。**
继续耗轮次只会重复同样的失败，而每轮都要付费调模型。
`CycleResult` 新增 `exhausted` 字段，让调用方能区分
**"还在改"** 与 **"改不动了"**。

#### ⚠️⚠️ 局限：**总分本身有噪声，阈值对它是脆的**

两次跑**同一集、同样 3 轮**：

| 运行 | 第 1 轮 | 第 2 轮 | 第 3 轮 | 阈值 80 下 |
|---|---|---|---|---|
| A | 74.3 | 77.8 | **81.1** | 通过 |
| B | 74.3 | 70.7 | **77.8** | 不通过 |

**第 3 轮在 77.8 ~ 81.1 摆动 —— 80 正好切在噪声带中间。**

> ⚠️ **本小节记录的是 2026-10-16 的裁定（阈值 80）。**
> 2026-10-17 已做 10 次标定并改为 **65**，见 **§5.10.13**。
> 保留原记录的理由：它记的是**「为什么要标定」那一步推理** ——
> 数字变了，推理没变。

根因要说准确（这里容易自我欺骗）：

| 环节 | 可复现吗 |
|---|---|
| 从**给定**的问题列表算总分 | ✅ 纯函数 |
| **问题列表本身**（LLM 报的） | ❌ **每次不同** |
| 所以**总分** | ❌ **不可复现** |

> **"算术可复现"不等于"结果可复现"。**
> 这正是本项目一直警惕的那类错误 ——
> **一个看起来严谨的机制，实际依赖不确定的输入。**

**应对（不是靠挪阈值假装判准了）**：

| # | 做法 |
|---|---|
| **1** | **如实记录噪声** —— 源码与文档都写明，**不宣称可复现** |
| **2** | **边界情况走 `ESCALATE`**（决策 ③）—— 一次判不准时，**交给人比调切点诚实** |
| **3** | **先收集分布再定阈值** —— 跑 ~10 次记录分数分布，才知道 80 该不该动。**没有分布就定阈值是拍脑袋** |

> **通过 ≠ 完美**：两条判据是「与」，通过时**可能仍带着 advisory 意见**。
> 所以证据链**原样保留所有意见** —— 否则会出现
> "通过了，但没人知道它其实带着 2 个已知缺陷"。

#### 附：这一节的实测价值

三次口径调整**都不是拍脑袋**，每一次都是被实测数据逼出来的：

| 现象 | 读出来的结论 |
|---|---|
| 任何一轮都不过 | 「零意见」对语义审核方不可能 |
| 改了 3 轮、分数 74.3→77.8→81.1 仍不过 | 「零阻断」也不够 —— **那串上升的分数是被浪费掉的收敛信号** |
| 同一集两次跑出 81.1 与 77.8 | 阈值切在噪声带，**判据本身有不可复现性** |

### 5.10.9 音轨（M3 的最后一环）—— ✅ **已接线并验收**（2026-10-18 通路 → 2026-10-18 `alpha.75` 完成）

> **本节结论已整体推翻重写。** 原写「`audio.tts` 编译规则已实现，
> 但**需要 API key**，成片无声」。
> 实际：**不需要任何云端 key** —— 本机 H3 是音画同出的。

#### 关键发现：H3 的 `FL2VA` = Video **+ Audio**

| 证据 | 内容 |
|---|---|
| `local-gen/app/engines/h3.py` | `from diffsynth.pipelines.**minimax_h3_audio_video** import MiniMaxH3Pipeline`<br>`video, audio = pipe(...)` → `write_video_audio(... audio=audio, ...)` |
| 权重目录 | `.../MiniMax-H3/**FL2VA**/processor` |
| 注册表 | `minimax-h3` 的 `capability.native_audio = **True**`（早就声明） |
| `h3-native-audio` 条目 | "零额外成本：音轨与视频同一遍前向产出" |

**但"代码看起来会出音频"与"产物里真有音轨"是两件事**（中间可能被丢弃、
mux 失败、或参数为 0 导致静音）。**所以不看代码，看文件。**

#### 实测确认（本机没装 ffprobe，自己解析容器）

```
vide handler : True     soun handler : True
编解码器      : ['avc1', 'mp4a']     trak 数量 : 2
```

#### 原来的缺口不是模型，是**一条能走通的通道**

| 后端 | 状态 |
|---|---|
| 本机 ComfyUI（8188） | ❌ 没起 |
| MiniMax 官方 API | ❌ 没有 `MINIMAX_API_KEY` |
| **local-gen（8100）** | ❌ **根本没登记** ← 缺的是这条 |

> **声明了却走不通，比没声明更糟** —— 它让人以为已经接好了。

#### 已做的接线（三处）

| 位置 | 改动 |
|---|---|
| `models/registry.py` | `minimax-h3` 加**第三个后端**：local-gen 异步通道 |
| `runtime/channels/http.py` | 提交时也认 **`job_id`**（local-gen 用的就是这个键） |
| `review/observe.py` + `ops.py` | 容器探测 `_media_flags` + 断言 **`audio_track_present`** |

**第二处是个真 bug**：只认 `id`/`task_id`，而 local-gen 返回 `{"job_id": ...}`
→ 任务会被判"服务端没给任务 id"而**每次提交都失败**，看起来像服务不可用。

#### 第 13 个断言 `audio_track_present`

`capability.native_audio=True` 只是一句**声明**。
在此之前**没有任何断言能验证"成片真的有声音"** ——
`audio.tts` 是一条编译规则（描述"该去合成语音"），
**不是"产物里必须有一条音频轨"**。

> **声明与验证是两件事。**

判据来自**容器字节**（不依赖 ffprobe）：MP4 找 `ftyp` + `soun`/`mp4a`，
Matroska 找 `A_*`，WAV 直接算有。
⚠️ 它**不判断音轨内容对不对** —— 只回答"有没有"。

#### 达成：3 镜有声成片

```
3 段 × ~330~340 秒  ->  ffmpeg concat  ->  audio_demo.mp4
13.41 秒 / 16.35 MB / h264 640x384 24fps + AAC 32kHz 立体声 176 kb/s
算子 audio_track_present: ✅ 通过（音轨与视频轨齐全）
```

**走 i2v 而不是 t2v**：把 Z-Image 静帧当首帧，得到"我们控制的构图 +
模型补的运镜 + 模型自带的音轨"。纯 t2v 会丢掉构图（`img2img` 否证过的同类问题）。
已抽帧验证构图完整保留。

### 5.10.13 阈值标定与度量修正（2026-10-17）

#### 起因

§5.10.8 留下的诚实话：**阈值只有 2 个样本（77.8 / 81.1），切在噪声带中间。**
"没有分布就定阈值是拍脑袋。"

#### 实测一：10 次剧本闭环

| 指标 | 首轮 | 末轮 | **取最好一轮** |
|---|---|---|---|
| 均值 | 61.5 | 63.4 | **70.3** |
| σ | 11.6 | 12.8 | **7.7** |
| p50 | 62.8 | 57.6 | **67.9** |

**关键发现一：返工多数在让质量变差。** 多轮的 9 次里：变好 **3** / 变差 **5** / 没动 1。
最差一次降了 **13.5 分**（67.9 → 54.4）。
→ **"取末轮"经常交出去的是几次里最差的一份**，已改为 `CycleResult.best`。

**关键发现二：阈值 80 太严。** 收敛率只有 **3/10 = 30%**。
按"取最好一轮"分布：65 → **60%** 通过。已改为 **65**。

#### 实测二：条件对比（短剧本 / 换题材）

| 组 | 场景 | 均值 | 命中 |
|---|---|---|---|
| A 基准（薰衣草） | ~5 | 70.3 | — |
| **B 短剧本**（同素材 / 2 场上限） | **2.0** | **52.6** | **-17.7 分** |
| C 换题材（都市悬疑） | 7.2 | 42.0（含 2 次作废） | 分布形态不同 |

**短剧本被系统性惩罚**：完整性是**比例**，2 场缺 1 场 = 50% 不完整，
8 场缺 1 场 = 12.5%；且短剧本会**撞 0 地板**（5 次里 4 次是同一个 41.4 分）。

→ **改度量**（不是改阈值）：`completeness = max(0, 100 − 25 × 缺陷场次数)`。
实测短剧本均值 **46.7 → 66.8**，地板消失。

#### 一个自我修正（重要）

`cast_consistent_with_text` 这条断言是为"角色表 vs 描述意图"造的，
在**桩路径上命中 50%**。于是我曾写"它抓到了真缺陷"。

**后来实测 163 镜（3 题材 × 2 次）：命中 0%。**

| 我说过 | 实际 |
|---|---|
| 抓到了真缺陷 | 抓到的**是桩路径的缺陷**（桩把整场卡司塞进每镜） |
| 50% 命中 → 不敢升 `hard` | 50% 是**夹具的属性**；真实内容 **0%** |

**教训：一个在夹具上命中的断言，不等于它在生产上会命中。**
夹具反映**我们的构造方式**，不是模型的行为。
→ 决定：**保持 `audit`**，不升 `hard`（升了也是空操作，却让人以为多了一层保护）。

#### 另一个"收益为 0"的诚实记录

给 `LlmClient` 加了传输层重试（只重试 429/5xx/网络异常）。
A/B 5 次：作废 2/5 → 0/5，**但重试一次都没触发** → **不能归因于重试**。
有效样本均值反而降了 6.1 分。

**重试仍保留**（它是正确的防御，机制已单测证明），
**但汇报必须写清"收益为 0，不是已验证有效"**。

### 5.10.14 两副本漂移与自我修正（2026-10-18）

#### 结构性问题

此前 `.git` 在**旧项目目录**（`ds.6`），而**新项目**在 `ds.8` 且无 git。
每次发版都要**手工把新代码拷到旧目录再提交** —— 漂移由此而生。

**两次事故**：

| 事故 | 代价 |
|---|---|
| `alpha.39`：`.gitignore` 的 `models/` 未锚定 | `src/little_crew/models/` **4 个文件从未入库**；任何人 clone 后 `import little_crew.models` 直接失败。而 `git status` 干净、本机测试全过 |
| `alpha.46` 盘点 | 三处漂移，其中 README 版本**藏了 16 个版本** |

> **`git status` 干净 + 本机测试全过 ≠ 仓库完整。**
> 要用 `git archive` 在**只含已提交内容**的环境验证。

#### 修正

`.git` 迁到 `D:\AI\ds.8\Little_Crew`（唯一代码目录）；`legacy/` 移出仓库；
`.gitattributes` 定换行符策略（否则 41 个假改动会淹没真改动）；
新增**存储守卫 ⑥**：`.gitignore` 里未锚定的规则不得匹配到源码包目录。

#### 方法学收获（可写进论文的"工程纪律"部分）

| 做法 | 为什么必要 |
|---|---|
| **干净快照验证** | 本机全过不等于别人 clone 能跑。已两次抓到真问题 |
| **守卫必须见过它失败** | 一条从不报错的守卫等于没有。§5.10.14 的守卫已用"故意复现旧规则 → 确认 FAIL"验证 |
| **汇总时显式检查预期样本数** | 曾写 `if r["bestScore"]` 把 `0.0` 当假值 → **两次失败运行被悄悄排除**，结果看起来比实际好得多 |
| **后台任务必须可观测** | 无 flush / 无增量落盘的脚本跑了 30 分钟、只用了 0.3s CPU，而**看不出它在跑还是在卡** |

**三条支路**（挂在主流程旁边）：

| 支路 | 入口 | 产出 |
|---|---|---|
| **停** | `--stop-after <阶段>` | `run.report.partial.json`（停在哪/已完成/还差/trace） |
| **看** | `console.html` ／ `report/index.html` | 19 块节点图（带缩略图）／ 40 镜逐镜卡 |
| **改一镜** | `studio.py` 起服务 → 点方块 → 点一镜 | 只重渲那一镜（实测 13.7 秒） |

**两条曾经的顺序错（`alpha.124` 修）**：`_run_previs()` 与 `_run_line_producer()`
曾被放在「合成」之后 —— **白模控制图永远来不及用**。
现已搬到出图之前，并用**源码行号守卫**（`partial_report_check` E3~E8）钉死。

### 5.10.24 受众分三档，三条路（**远期规划**，2026-10-29 立项）

> **本节只定方向与判据，不排进当前工期。**
> 当前优先级仍是 §5.10.23 的 P0：**证明「判定 + 退回 + 证据」有没有用**。

#### ① 为什么必须分档

把「给研究者用的」和「给小白用的」当成同一个东西，会得到两个坏结果：
**研究侧被外壳拖慢，产品侧被未验证的价值包装。**

所以先承认一件事：

> **同一个系统，对三类人应该有三张不同的脸。**
> 而「能不能给小白」取决于**有没有一条不需要本地安装的路** ——
> 不取决于我们愿不愿意做 UI。

#### ② 三档与三条路

| 档 | 是谁 | 他要什么 | 给什么 | 现状 |
|---|---|---|---|---|
| **A 研究者 / 自己** | 需要证据、要能复现 | 命令行 · 证据链 · 可换后端 | 现状（`episode_demo` + `delivery/` + 报告） | ✅ 够用 |
| **B 进阶创作者** | 会装软件、懂一点模型 | 一键启动 · 能看能改单镜 | 现状 + 导演台 + `studio.py` + **`start.ps1`** | 🟡 差启动脚本（半天） |
| **C 小白** | 什么都不想装 | 打开网页 → 输故事 → 看成片 | **云端后端 + 网页** | ❌ **是另一个产品** |

#### ③ 🔴 一条硬判断：**小白路线必须走云端**

| 项 | 现实 |
|---|---|
| 模型体积 | Z-Image 5.78 GB + ControlNet 1.88 GB + CLIP/VAE ≈ **8 GB 起** |
| 硬件 | 8.6 GB 显存刚够；6 GB 卡直接不行 |
| 环境 | 驱动 / CUDA / 版本组合，每人不同 |
| **ComfyUI 本身** | **已经是「非小白」门槛**（装 + 找节点 + 连工作流） |

> **若后端是 ComfyUI，「小白友好」在定义上就不成立。**
> 不可能一边要求用户装 ComfyUI，一边说这是给小白用的。

**所以 C 档的前置条件是 P3-2（接云 API），不是 P2-4（做前端）。**
先有「不装东西也能出图」的后端，前端才有意义。

#### ④ 顺序纪律（防止把未验证的价值包装成产品）

```
P0  证明这一层有用（判定 + 退回 + 证据）
P1  证据收口（盲判 / 返工扩样本 / 四条机制汇总）
      ↓ 只有 P0 / P1 立住，才谈产品化
P2  B 档成形（start.ps1 + 导演台 + studio）
P3  C 档成形（云 API → 网页 → 一键）
```

> **P0 / P1 没立住就做 C 档，等于把一个还没被证明的东西卖出去。**
> 对一个把「可验证」当核心的项目，这是最不能接受的顺序。

#### ⑤ 每档的「最小可用」定义（可验收，不是感觉）

| 档 | 最小可用 = 以下全满足 |
|---|---|
| **A** | 一条命令跑完一集；产物 + 证据 + 报告齐全；失败有明确分类 |
| **B** | **双击 `start.ps1`** → 自动检查 5 项依赖 → 缺什么说清装哪 → 全在则跑一集 → 跑完自动打开导演台 |
| **C** | 打开网页 → 填一句故事 + 选集数 → 等 → 能看不合格镜 → 能只重拍那一镜（**本地零安装**） |

**B 档的「5 项依赖」**：Python 与 `PYTHONPATH` · `FFMPEG` · `--blender` 路径 ·
ComfyUI(8188) · local-gen(8100)。
**这 5 项恰好就是现在让人卡死的地方** —— 实测记录：漏一个 `--llm`，
白模就静默不产，而报告显示「跑通 / 覆盖率 100%」（见 §5.10.23）。

#### ⑥ 明确不做（远期也不做）

| 不做 | 理由 |
|---|---|
| 本地安装包 / exe 打包 | 8 GB 权重 + CUDA 组合，做出来也维护不了 |
| 自研图编辑器 | 见 §5.10.23「明确不做」：我们的程序不是图，图只是影子 |
| 自研推理补齐控制/参考能力 | ComfyUI 有的能力应当**消费**，不是重造 |

#### ⑦ 一句话记住

> **A 档要证据，B 档要省事，C 档要「什么都不装」。**
> **三档共用同一份 IR —— 这是它们能同时存在的唯一理由。**
