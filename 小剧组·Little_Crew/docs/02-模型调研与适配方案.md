# AIGC 漫剧平台 · 主流模型调研与适配方案

> **一句话结论**：平台**不应内建任何模型知识**。模型通过 `ModelSpec` 声明式注册，
> 由**任务档案（TaskProfile）**声明需求，**路由算法**在能力矩阵的可行集内求解最优，
> **降级链**兜底。这样新增模型只需加一条注册，不改平台代码。
>
> 调研日期：2026-10-11 · 数据来源：ComfyUI 官方节点源码 + 第三方受控实测基准 + 本机 local-gen 实测

## 第 1 章 本机硬件与能力边界（实测）

### 1.1 硬件

| 项目 | 实测值 | 备注 |
|---|---|---|
| GPU | NVIDIA RTX 4060 **Laptop** | 计算能力 8.9（Ada / sm_89） |
| 显存 | **8188 MiB（8 GB）** | 可用约 6.2 GB |
| **内存** | **15.80 GB**（8GB × 2） | ⚠️ **最大瓶颈，不是显存** |
| CPU | i7-13700H | 14 物理核 / 20 逻辑核 |
| 硬盘 | NVMe SSD 954 GB | 单盘，C/D 同盘 |
| D 盘可用 | 105.9 GB | 模型与产物都在此 |

> ⚠️ **关键判断**：瓶颈是 **15.8 GB 内存**，不是 8 GB 显存。
> 8GB 显存配合 Disk Offload 能勉强跑；但 15.8GB 内存让所有"需要模型常驻内存"的能力全部出局。

### 1.2 实测跑通的能力（`D:\AI\local-gen`，不用 ComfyUI，纯 Python + FastAPI）

| 能力 | 引擎 | 实测耗时 |
|---|---|---|
| 文生图 1024×1024 / 8 步 | Z-Image-Turbo **4bit NF4**（diffusers） | **30~32 秒/张**（首次含量化加载 50~60 秒） |
| 图生图（参考图锁角色） | Z-Image img2img | **226 秒**（512×688 / 8 步 / denoise 0.5） |
| 文生视频 5 秒 | MiniMax H3 NF4（DiffSynth） | 8 步 **442~518 秒**（约 7~8.6 分钟） |
| 图生视频 5 秒 | 同上 | **441.9 秒** |
| 文生视频 10 秒 @832×480 | 同上 | 1 步 230~240 秒 |

**产物规格**：H.264 832×480 / 24fps / 124 帧 + **AAC 32kHz 立体声（原生音轨）**

### 1.3 硬性边界（实测，非估算）

**⚠️ H3 安全时长上限 = 10 秒**

| 分辨率 | 5s | 8s | 10s | 12s | 15s |
|---|:--:|:--:|:--:|:--:|:--:|
| 832×480（0.40 MP） | ✅ | ✅ | ✅ | ❌ OOM | ❌ OOM |
| 480×704（0.34 MP） | ✅ | ✅ | ✅ | — | ❌ OOM |
| 512×896（0.46 MP） | — | ✅ | — | ❌ OOM | ❌ OOM |

两个反直觉结论：

1. **降分辨率换不来更长时长** —— 0.34MP 与 0.40MP 上限完全相同（都是 10s 过、12s 挂）。**瓶颈是注意力的序列长度，不是像素数**（H3 开源版只有 full attention，稀疏注意力未放出）
2. **`PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` 实测无效** —— 12s 依然 OOM

> **对平台的直接推论**：**H3 的 10 秒上限与漫剧分镜天然对齐**。
> 设计文档 §10.3 写的"单镜时长 4–15s"必须改成 **4–10s**，且 >10s 的镜头必须自动拆为多段 + FFmpeg 拼接。
> 这不是妥协，而是更自然的结构——**一镜一段**。

### 1.4 明确跑不了的能力（实测失败或硬件不达标）

| 能力 | 原因 |
|---|---|
| H3 视频 > 10 秒 | 显存不足（各分辨率均 OOM） |
| **H3 ControlNet（白模驱动动作）** | 6.34 GB 必须**常驻内存**（官方明确不支持 Disk Offload），与 NF4 无搭配先例 |
| 混元 3D 图生白模 | 要求系统内存 ≥ 24 GB |
| **Z-Image LoRA 训练** | 官方脚本用全精度底模 **fp32 22.93 GB** > 15.8 GB 内存 |
| **H3 LoRA 训练** | 33B 模型反向传播，8GB 显存几乎不可能 |
| H3-Regenerate-2K（2K 上采样） | **未开源**，仅官方 API 提供 |
| Z-Image IP-Adapter | 仅社区魔改（SD3 权重硬套），**无官方权重** |

> ⚠️ **这是对一致性策略的重大约束**：本机**无法训练角色 LoRA**。
> 因此设计文档 §8.1 的一致性机制必须调整为：
> **优先参考图注入（img2img / ref2va）而非 LoRA**；LoRA 仅在云端训练后离线使用时才作为可选项。

### 1.5 同一时刻只能加载一个模型

8 GB 显存放不下两个模型，切换时自动卸载并清空显存。实测：zimage 加载 61.5s / h3 加载 1.0s。

> **对调度器的硬约束**：GPU 调度必须**按模型分批**（batch by model），
> 而非按镜头顺序。否则每镜都在两个模型间反复切换，加载开销吃掉全部收益。
> 这是设计文档 §9.5 "模型常驻"策略在本机的**强制形态**。

## 第 2 章 模型全景调研

### 2.1 文生文（剧本 / 分镜 / 审片）—— 走云端 API

本地跑 LLM 不现实（15.8GB 内存装不下有实用价值的模型），因此**文生文全部走云端 OpenAI 兼容 API**。

| 用途 | 候选 | 特点 | 平台中的 Agent |
|---|---|---|---|
| 长文本拆解 / 剧本 | DeepSeek 系列 | 中文强、成本极低、长上下文 | `ScriptIngestionAgent` / `ScriptWriterAgent` |
| 结构化输出（分镜 JSON） | Qwen 系列 | JSON 稳定性好 | `ShotComposerAgent` |
| 超长上下文（整本小说） | Kimi 系列 | 百万级上下文，无损解析长篇 | 素材解析 |
| 推理 / 评审 | 推理型模型（CoT） | 适合剧评、逻辑推演 | `DramaCriticAgent` / `ContinuityCheckAgent` |
| 通用兜底 | GLM / 豆包 / 混元 | 国内可直连 | 备选 |

> **平台侧设计**：`llm.complete` 是**单一 IR kind**，不暴露具体厂商。
> 厂商通过 `ModelSpec` 注册，`route()` 按 `task="text.structured"` + `max_cost_cny` + `min_context` 求解。
>
> **成本参考**：2026 年中国大模型 API 价格战已使前沿模型单价降至极低水平，
> 单集剧本 + 分镜的 LLM 成本可控制在 **¥1~5** 量级（见第 7 章测算）。

### 2.2 文生图

| 模型 | 授权 | 量化/体积 | 实测耗时 | 定位 |
|---|---|---|---|---|
| **Z-Image-Turbo** | 见仓库 | NVFP4 **4.51 GB**（全套 8.33 GB 可常驻） | **13.8 s** @1024²/8步 | 日常主力、可常驻零 offload |
| **Qwen-Image 2512 + Lightning** | **Apache 2.0** ✅ | fp8 20.43 GB（需 offload） | **12.2 s** @1328²/**4步** | 高分辨率 + **中文逐字 30/30 全对** |
| Qwen-Image 2.1 | Apache 2.0 | int8 17.3 GB | 72.7 s @1328²/25步 | 满质量档，同质量比 2512 快 2.8× |
| **ERNIE-Image** | **Apache 2.0** ✅ | 8B DiT + Turbo 8 步 | — | **文字渲染与排版开源第一**（LongTextBench 0.9733） |
| FLUX.2 Klein **4B** | **Apache 2.0** | fp8 4.07 GB | 42.3 s | 图像编辑，授权干净 |
| SDXL base 1.0 | CreativeML Open RAIL++-M | 6.9 GB | — | 兼容性最好、LoRA 生态最丰富 |

> **三个必须在平台侧处理的事实**：
>
> 1. **Z-Image 的 type 是 `lumina2`，FLUX.2 是 `flux2`** —— 同一个 `qwen_3_4b` 编码器在两个模型里用**不同 type 加载**，搞混就报错。这正是能力矩阵要记录的"软性约束"。
> 2. **中文文字渲染差异巨大** —— 若镜头里有招牌/信件/手机屏幕文字，必须路由到 Qwen-Image 或 ERNIE-Image。
> 3. **2K 级超分可用 PixelDiT `pid_flux2`**（2.73 GB / **5.4 s** 1024²→2048²、4 步），比让主模型直接出 2K 划算得多。

### 2.6 视觉语言模型（审片 / 一致性校验）

平台的 C3 创新点（确定性验收门禁）需要**跨模型族盲读**。候选方向：

| 用途 | 候选 | 平台角色 |
|---|---|---|
| 逐镜质量打分（八维） | 轻量 VLM（如 GLM-4.6V-Flash 类） | `ReviewBoardAgent` 的软门禁 |
| 面部/服装一致性校验 | 人脸检测（YuNet）+ 一致性嵌入 | `cr_face_*` 断言的观测量 |

> **跨模型族要求**：生成用 Qwen-Image 时，审核**不得**用同族 VLM，否则违反"不自我签收"原则。

## 第 3 章 三条会改变平台设计的发现

这一章是本次调研对设计文档的**修正项**，不是补充项。

### 发现 1：本机瓶颈是内存不是显存 → 一致性策略必须改

**原设计（§8.1）**：优先用角色 LoRA 锁定身份。

**实测约束**：Z-Image LoRA 训练需 fp32 底模 22.93 GB > 15.8 GB 内存；H3 LoRA 训练（33B 反向传播）在 8GB 显存上不可能。

**修正后的分层一致性策略**：

```
第 0 层（本机主力）：参考图注入
   ├─ Z-Image img2img（denoise 0.5，226s/张）
   ├─ H3 ref2va（官方节点 MiniMaxH3ReferenceToVideo）
   └─ 锚点集 + 定妆照 → 作为 reference 输入
第 1 层（云端训练后离线使用）：角色 LoRA
   └─ 需另找训练环境；平台侧仅需支持 loraFile 绑定（已实现）
第 2 层（无成本）：种子派生 + 提示词纪律
   └─ 已在设计文档 §8.4 覆盖
```

> 好消息：平台的 IR 与编译器**本来就支持** `identity.reference` 与 `identity.lora` 两条路径，
> 且已实现"缺 IPAdapter 时降级到 LoRA"的降级链。本机场景下**只需反转优先级**——
> 让 `identity.reference` 成为首选、`identity.lora` 成为降级目标。**零代码改动，只改规则表。**

### 发现 2：H3 的 10 秒上限与分镜粒度天然对齐 → 单镜时长上限改为 10s

**原设计（§10.3）**：单镜时长 4–15 秒。

**实测**：10 秒是硬上限，12 秒必 OOM，且降分辨率无效。

**修正**：单镜时长 **4–10 秒**；>10s 的镜头由 `ShotComposerAgent` 自动拆为多段，平台按 `chain` 模式拼接（上段末帧接下段首帧）。

> 这反而是**结构上的收获**：一镜一段意味着"镜头"与"生成单元"一一对应，
> 缓存粒度、时效清单粒度、门禁粒度三者完全对齐——不需要跨镜头切分产物。

### 发现 3：真正的稀缺资源是 GPU 时间，不是钱

**实测核算**（60 镜/集，全本地）：

| 步骤 | 单镜耗时 | 60 镜合计 |
|---|---|---|
| 文生图（关键帧） | 31 s | **31 分钟** |
| 图生视频（8 步） | 442 s | **7.4 小时** |
| 图生视频（**4 步 LoRA**） | ~244 s | **4.1 小时** |

**结论**：本机产出**一集需要 4~7.5 小时的纯 GPU 时间**，而成本接近零（只有电费）。

> 这彻底改变了工程的优先级排序：
>
> | 机制 | 原定位 | 修正后定位 |
> |---|---|---|
> | 三级内容寻址缓存 | 优化项 | **生死线**——改一个镜头只重跑一个镜头 |
> | 渲染检查点 / 断点续跑 | 优化项 | **生死线**——4 小时长跑必然中断 |
> | 草稿→定稿两阶段 | 优化项 | **生死线**——全片先跑 416P/4步草稿审片，通过后再跑定稿 |
> | 4 步蒸馏 LoRA | 未提及 | **重大收益项**——快 1.81×（实测 519s → 286s） |
> | 模型分批调度 | 优化项 | **强制**——同一时刻只能加载一个模型 |
>
> 设计文档 §9.1 的三级缓存与 §9.2 的检查点，从"工程优化"升级为"能否跑通一集的必要条件"。

## 第 4 章 模型适配层：ModelSpec

### 4.1 设计原则

> **平台不内建模型知识。模型声明自己的能力，平台求解最优组合。**

这是"统一 IR + 编译规则表"思路的必然延伸。若把模型清单硬编码进平台，
每出一个新模型就要改代码——这正是 kt-ai-Studio 式模板填充的死结。

### 4.2 ModelSpec 结构

```jsonc
{
  "modelId": "qwen-image-2512-lightning",
  "displayName": "Qwen-Image 2512 + Lightning",
  "task": "image.text_to_image",              // 任务域，路由的第一层筛选
  "backend": {                                 // 在哪跑、怎么跑
    "kind": "comfyui",                         // comfyui | http | local_python
    "endpoint": "local:8188",
    // ComfyUI 后端：声明所需节点与权重
    "requiredClassTypes": ["UNETLoader", "CLIPLoader", "VAELoader",
                           "EmptySD3LatentImage", "KSampler", "VAEDecode"],
    "clipType": "qwen_image",                  // ← 关键：编码器加载 type
    "weightFiles": ["qwen_image_2512_fp8.safetensors"],
    "loraFiles": ["Qwen-Image-Lightning-4steps.safetensors"]
  },
  "resources": {                               // 资源画像，供调度与路由
    "vramPeakMb": 20430,
    "vramResidentMb": 0,
    "needsOffload": true,                      // 主模型+编码器 > 显存 => 必须 offload
    "ramPeakMb": 6144,
    "diskGb": 30.1
  },
  "qualities": {                               // 能力画像，供任务匹配
    "maxResolution": [1328, 1328],
    "supportsNegativePrompt": true,
    "supportsChineseText": true,               // ★ 中文文字渲染能力
    "chineseTextScore": 1.0,                   // 0~1，来自实测（30/30 逐字全对）
    "supportsReferenceImage": false,
    "supportsLora": true,
    "nativeAudio": false,
    "maxDurationS": null,
    "stepsProfile": { "draft": 4, "final": 4 } // 草稿/定稿步数
  },
  "performance": {                             // 实测性能，供成本模型
    "measuredMs": { "1024x1024@8": 13800, "1328x1328@4": 12200 },
    "measuredOn": "RTX 5090 Laptop 24GB",      // ★ 必须标注测量环境
    "source": "third_party_controlled_ab"
  },
  "promptProfile": "qwen_image",               // 提示词纪律档案（见 §5.3）
  "cost": { "kind": "local", "cnyPerCall": 0.0, "powerCnyPerHour": 0.6 },
  "license": {                                 // ★ 授权与合规（见第 8 章）
    "id": "Apache-2.0",
    "commercialUse": true,
    "revenueThresholdUsd": null,
    "excludedRegions": [],
    "attributionRequired": false,
    "verified": true,
    "verifiedNote": "已核实"
  },
  "maturity": "production"                     // production | beta | experimental | deprecated
}
```

### 4.3 三个必须记录的字段（容易被忽略但会出事）

| 字段 | 为什么必须有 | 不记录的后果 |
|---|---|---|
| **`backend.clipType`** | 同一编码器在不同模型下用**不同 type 加载**（Z-Image = `lumina2`，FLUX.2 = `flux2`） | 编译出的图结构正确但加载报错 |
| **`performance.measuredOn`** | 实测数据强依赖测量硬件（本机 4060 与基准的 5090 差 5~10 倍） | 用别人的数据做预算，实际超支一个数量级 |
| **`license.*`** | 授权与"权重能下载"是两件事；同名模型授权可能相反 | 商用产品里用了禁商用模型，法律风险 |

### 4.4 平台已有的可复用机制

`capability.py` 里的 `PortRequirement` 已支持 `files`（文件型输入校验），
把它扩展为 `WeightRequirement` 即可覆盖 `weightFiles` / `loraFiles` 的在位校验——
**这正是"底模/LoRA 不在目标环境"这类致命故障的防线**，已实现并有测试覆盖。

## 第 5 章 IR 节点与真实模型映射

### 5.1 为什么不能把模型写进 IR

IR 是**语义层**，必须模型无关。若 IR 里写 `"class_type": "MiniMaxH3ReferenceToVideo"`，
则换模型就要改 IR，缓存键失效，语义约束无法跨模型复用。

**正确做法**：IR 只写 `kind`，模型选择发生在**编译期**，由路由算法决定。

### 5.2 IR kind → 真实 ComfyUI 节点（外部参考表）

以下取自 ComfyUI 官方源码（`comfy_extras/nodes_minimax_h3.py`，v0.31.1），是编译规则表的真实依据：

| IR kind | 真实 class_type | 端口映射 | 默认参数 |
|---|---|---|---|
| `video.i2v` | `MiniMaxH3ImageToVideo` | `clip` ← CLIP, `vae` ← VAE, `first_frame` ← IMAGE, `last_frame` ← IMAGE | `width=1344, height=768, length=124` |
| `video.ref2v` | `MiniMaxH3ReferenceToVideo` | `clip`, `vae`, reference images/videos/audio | `length` 按 17k+5 网格对齐 |
| `latent.av` | `EmptyMiniMaxH3LatentAV` | — | joint video+audio latent |
| `sample.sigma_shift` | `MiniMaxH3SigmaShift` | — | 协同设置 video/audio flow shift |
| `video.extend` | `MiniMaxH3Extension` | — | 时长扩展 |

**两个从源码得到的硬约束**：

```python
FPS = 24
def align_frame_count(n):        # 帧数必须对齐到 17k+5 网格
    while n % 17 != 5: n += 1
    return n
def adapt_canvas(w, h):          # 768 短边 + 768*1344 面积上限，逐轴 32 对齐
    ...
```

> **对平台的含义**：IR 里声明的"镜头时长 7 秒"在编译到 H3 时会被**吸附到最近的合法帧数**
> （7s × 24fps = 168 帧 → 吸附到 175 帧 = 7.29 秒）。
> 这个"吸附"必须作为 **`SUBSTITUTED` 降级通知**告知上游——
> 因为镜头时长变化会影响对白时间码与字幕卡点，进而影响连续性约束。
> **静默吸附会导致音画不同步**，这正是模板填充范式会犯的错。

### 5.3 提示词纪律档案（PromptProfile）

不同模型的提示词组织方式差异巨大，但**这个差异不该污染 IR**。

```jsonc
// prompt_profiles.json —— 与 IR 完全解耦
{
  "qwen_image": {
    "order": ["subject", "costume", "action", "composition", "lighting", "style"],
    "chineseTextMarker": "文字内容用引号显式标注",
    "negativeSupported": true
  },
  "minimax_h3": {
    "order": ["subject_definitions", "summary", "retention_analysis",
              "action", "camera", "audio"],
    "dialogueSpeakerId": "(S1)/(S2)",         // 对白必须带说话人 ID 才能分音色
    "referenceIsPrimary": true,               // 参考图是 H3 的主要依据
    "negativeSupported": true,
    "voiceLock": true                          // 音色锁定描述
  },
  "z_image": {
    "order": ["style", "subject", "details"],
    "negativeSupported": false,
    "chineseTextScore": 0.0
  },
  "wan22": {
    "order": ["scene", "subject", "motion", "camera"],
    "stepLoraHint": "4步 LoRA 时提示词需更简洁"
  }
}
```

> **设计要点**：IR 的 `semantic.intent` 保存**结构化的语义槽位**（主体/服装/动作/构图…），
> 编译时按 `promptProfile` 组装成该模型期望的文本。
> 这样"换模型"不会改变 IR，缓存键不受影响，而提示词质量由档案保证。

## 第 6 章 选型与路由

### 6.1 任务档案（TaskProfile）

```jsonc
{
  "task": "video.image_to_video",
  "must": {                                    // 硬性要求，不满足直接出局
    "nativeAudio": true,                       // 需要原生音轨
    "maxDurationS": { "gte": 8 }
  },
  "prefer": {                                  // 软性偏好，用于排序
    "promptAdherence": 0.9,
    "estimatedMs": { "weight": 1.0, "direction": "min" },
    "costCny": { "weight": 0.0 }
  },
  "budgetCny": 0.0,                            // 全本地 => 0
  "phase": "draft"                             // draft | final
}
```

### 6.2 路由算法

```
route(task_profile) -> ModelSpec:
  1. 可行集筛选（硬约束，任一不满足即出局）
     ├─ task 匹配
     ├─ capability 满足 must（含分辨率/时长/音轨/参考图）
     ├─ license 合规：commercialUse 允许 && 当前地区不在 excludedRegions
     ├─ 资源可行：vramPeakMb ≤ 可用显存 或 needsOffload 可接受
     └─ weightFiles 在目标环境存在（已有 PortRequirement 机制）
  2. 若可行集为空 -> 沿降级链（见 §6.4），并产出 DegradationNotice
  3. 可行集内按 prefer 加权打分排序
  4. 返回最优 + 备选列表（备选用于失败重试与"多引擎竞速"）
```

### 6.3 本机推荐的默认路由

| 任务 | 首选 | 备选 | 理由 |
|---|---|---|---|
| 剧本 / 分镜（文本+结构化） | DeepSeek 系（云端） | Qwen 系 | 成本极低、中文强、JSON 稳 |
| 关键帧（无文字） | **Z-Image-Turbo 4bit** | Qwen-Image 2512 | 本机实测 31 s，且 4bit 后约 6GB 可常驻 |
| 关键帧（**含中文文字**） | **Qwen-Image 2512** | ERNIE-Image | 中文逐字全对；Z-Image 无此能力 |
| 参考图锁角色 | **Z-Image img2img** | H3 ref2va | 本机唯一可用的身份锁定路径 |
| 图生视频（需音轨） | **MiniMax H3 + 4步 LoRA** | — | 唯一原生带音轨；4 步快 1.81× |
| TTS 对白 | 视节点包 | — | 配合 H3 原生音轨需注意去重 |
| 2K 定稿 | 云端 API（本地不行） | PixelDiT 超分 | H3-Regenerate-2K 未开源 |

### 6.4 降级链（本机实测约束驱动）

```
video.image_to_video (需音轨, 10s)
   ├─ 失败(MISSING_NODE) ──► MiniMaxH3ImageToVideo (t2va/fl2va)
   │                          └─ 帧数吸附 + SUBSTITUTED 通知
   ├─ 失败(OOM)          ──► 降分辨率 832×480 → 480×704
   │                          └─ 若仍 OOM → 降时长至 8s/5s
   ├─ 失败(OOM, 长镜头)  ──► 自动拆段（每段 ≤10s）+ FFmpeg 拼接
   └─ 失败(授权排除)     ──► Wan 2.2 14B MoE（无音轨，音轨另配 TTS）
                              └─ THRESHOLD_ADJUSTED: 音画一致性约束降级为 audit
```

> **注意最后一条**：当因**授权**而降级到无音轨模型时，平台必须把
> "音画同步"这条约束从 `hard` 降为 `audit`，否则门禁会对一个根本不存在的音轨判失败。
> **这正是阈值联动机制（已实现）的真实用例。**

### 6.5 多引擎竞速（可选增强）

若同时具备本地与云端能力，可对**关键镜头**并发提交到 2~3 个引擎，先通过门禁者胜出。
参考 wind-comic 的做法，但本平台的优势是：**竞速结果进缓存，且写入一致性嵌入的训练集**。

### 7.1 单集（60 镜）测算 · 全本地

| 步骤 | 单镜 | 60 镜 | 成本 |
|---|---|---|---|
| 剧本 + 分镜（云端 LLM） | — | — | **¥1~5** |
| 关键帧文生图 | 31 s | **31 分钟** | 电费 |
| 图生视频（8 步） | 442 s | **7.4 小时** | 电费 |
| 图生视频（**4 步 LoRA**） | ~244 s | **4.1 小时** | 电费 |
| 审片（VLM 云端） | ~3 s | ~3 分钟 | ~¥1 |
| **合计（4 步档）** | | **≈ 4.5 小时** | **≈ ¥5** |

### 7.2 结论：瓶颈是 GPU 时间，不是钱

> **本机产出 4 步档一集 ≈ 4.5 小时纯 GPU 时间，现金成本 ≈ ¥5。**
> 8 步档则是 7.9 小时。

**这决定了工程优先级**（与第 3 章发现 3 呼应）：

| 优化手段 | 收益倍数 | 优先级 |
|---|---|---|
| **草稿档（降低分辨率+步数）先审后定稿** | 草稿 4 步 + 定稿仅对通过镜头重跑 → 迭代成本降一个量级 | ⭐⭐⭐ |
| **4 步蒸馏 LoRA** | 1.81×（实测 519s → 286s） | ⭐⭐⭐ |
| **三级缓存** | 改 1 镜只跑 1 镜，而非全片 | ⭐⭐⭐ |
| **检查点续跑** | 4 小时长跑中断后不必重来 | ⭐⭐⭐ |
| **模型分批调度** | 消除模型加载开销（每次 1~62 s） | ⭐⭐ |
| 量化（fp8/int8/nvfp4） | 让模型**装得下**，间接提速 | ⭐⭐ |

### 7.3 混合云档（成本/画质权衡）

```
本地草稿（416P / 4 步）→ 审片 → 通过的镜头才走云端定稿（2K）
```

若一集 60 镜中 20% 需要重跑，本地草稿成本≈0，云端 2K 只对定稿镜头付费。
相比"全部云端"，可显著降低费用；相比"全部本地"，可获得本机做不到的 2K 画质。

### 8.2 平台必须实现的授权门禁

```jsonc
// 用户配置：部署地区 + 是否商用 + 年营收档
{ "region": "CN", "commercial": true, "annualRevenueUsd": 0 }

// 路由时的授权筛选（硬约束，不满足直接出局）
license_check(spec, ctx) -> (bool, reason):
  if ctx.commercial and not spec.license.commercialUse:
      return False, "模型授权禁止商用"
  if ctx.region in spec.license.excludedRegions:
      return False, f"授权排除地区 {ctx.region}"
  if spec.license.revenueThresholdUsd and ctx.annualRevenueUsd > threshold:
      return False, "年营收超过免费商用门槛"
  if not spec.license.verified:
      return False, "授权未核实，需人工确认"      // ← 未核实一律拒绝自动启用
  return True, ""
```

**三条强制行为**：

1. **未核实 = 拒绝**。`verified: false` 的模型不得进入自动路由（如 Lens、MiniMax Music 3 的信源冲突）。
2. **归属标注自动注入**。MiniMax H3 要求界面显著标注——平台应在成片尾帧/关于页自动加上，而非靠人记得。
3. **降级时重新过授权**。降级链的每一跳都要重跑 `license_check`，避免"为了避免 OOM 降级到了一个禁商用模型"。

> **本机场景的实际影响**：中国大陆在 MiniMax H3 授权范围内，年营收 < 2000 万美元即可商用，
> 个人与小团队的实际限制几乎为零。因此**本机的首选视频模型 H3 是合规的**，
> 但平台仍须实现上述门禁——因为一旦部署到欧美或商业化规模扩大，约束立即生效。
